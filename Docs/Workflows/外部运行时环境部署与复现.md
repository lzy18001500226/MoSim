# 外部运行时环境部署与复现

> 本文说明 MoSim 的两个可选外部环境：ROS1/Gazebo Classic/PX4/MAVROS 的 C99
> 运行时，以及 UE5 的场景显示环境。它们不替代 MWORKS 的模型检查、仿真和
> Result.msr 结果判定；不使用这两个环境也不影响 Studio、MWORKS 图形模型和
> MWORKS 内代码生成/SIL 的使用。

## 1. 交付层次与边界

| 层次 | 是否为基础使用前置 | 项目内入口 | 用途 |
| --- | --- | --- | --- |
| MWORKS / Syslab / Studio | 是 | `Models/MoSimQuadrotorModel/package.mo`、`apps/model_studio/` | 图形模型、FormalRunner、人工仿真和代码生成入口 |
| ROS1 / Gazebo Classic / PX4 / MAVROS | 否 | `Scripts/cmd/00_准备C99单机环境.cmd` | 自研 px4ctrl 的 C99 后端 `graphical_px4ctrl_c99` 的单机运行时复现 |
| UE5 场景显示 | 否 | `UE5/MoSimSceneLibrary/MoSimSceneLibrary.uproject` | 场景、相机和播放展示 |

运行时构建和 UE 窗口只分别说明对应环境可构建或可显示。控制性能、故障容错和
飞行状态必须仍以同次运行目录的日志、JSON、原始数据和定义的验收门为准。

## 2. ROS1 / Gazebo Classic / PX4 / MAVROS

### 2.1 固定版本与源码边界

当前 C99 单机运行时固定使用 Windows 主机上的 WSL2 `Ubuntu-20.04`、ROS1
Noetic、Gazebo Classic 和项目内 PX4 v1.14.0 源码。Windows 启动脚本会显式执行
`wsl.exe -d Ubuntu-20.04`，因此发行版名称、发行版版本和 WSL 版本均不能用默认
WSL 发行版替代。

项目必须位于 Windows 挂载盘可访问的目录；启动脚本通过 `wslpath` 将项目根映射到
WSL。PX4、Sunray、Gazebo 插件、FAST-LIO、MAVROS 适配器和 px4ctrl 运行时源均从
项目 `src/` 读取，不应另行创建旧工作区或把 `References/` 作为运行时源码输入。

| 组件 | 项目内位置 | 构建/检查角色 |
| --- | --- | --- |
| PX4 SITL | `src/flight_stack/px4/PX4-Autopilot` | `Scripts/sunray/build_local_px4_sitl.sh` |
| Sunray Gazebo 包 | `src/simulation/gazebo/sunray` | ROS1 foundation profile |
| Livox Gazebo 插件 | `src/simulation/gazebo/plugins/sunray` | ROS1 foundation profile；其中包含 `livox_laser_simulation` 源码 |
| MAVROS 适配器 | `src/flight_stack/mavros/sunray_uav_control` | flight_adapter profile |
| FAST-LIO | `src/perception/fast_lio` | perception profile |
| px4ctrl C99 运行时适配器 | `src/control/runtime_adapters/px4ctrl` | controller profile，后端为 `graphical_px4ctrl_c99` |

### 2.2 首次安装 WSL2 与 Ubuntu 20.04

在管理员 PowerShell 中先查看可用发行版；若系统尚未启用 WSL，则安装指定的
Ubuntu 20.04 发行版并按提示重启。Microsoft 的 WSL 安装方式见
[Install WSL](https://learn.microsoft.com/en-us/windows/wsl/install)。

```powershell
wsl --list --online
wsl --install -d Ubuntu-20.04
# 重启并完成 Ubuntu 首次创建用户后执行
wsl --set-version Ubuntu-20.04 2
wsl --list --verbose
```

最终输出必须包含名称为 `Ubuntu-20.04` 且版本为 `2` 的一行。若企业镜像未列出
该发行版，应按 Microsoft 的 WSL 手工导入流程安装 Ubuntu 20.04，而不是把运行脚本
改为调用另一发行版。

### 2.3 安装 ROS Noetic、Gazebo Classic 与构建工具

在 `Ubuntu-20.04` 内完成 ROS Noetic 二进制安装。ROS Noetic 的软件源与安装步骤应以
[ROS Noetic Ubuntu 安装页](http://wiki.ros.org/noetic/Installation/Ubuntu) 为准；PX4
v1.14 针对 Ubuntu 20.04 的 ROS/Gazebo 依赖说明见
[PX4 Ubuntu Development Environment](https://docs.px4.io/v1.14/en/dev_setup/dev_env_linux_ubuntu)。

在 ROS Noetic 软件源已经配置后，安装本项目使用的桌面、MAVROS 与基础构建包：

```bash
sudo apt update
sudo apt install -y \
  ros-noetic-desktop-full \
  ros-noetic-mavros ros-noetic-mavros-extras \
  build-essential cmake ninja-build \
  python3-pip python3-catkin-tools \
  protobuf-compiler libeigen3-dev libopencv-dev
```

随后打开一个新的 Ubuntu 终端，并完成以下核对。`catkin_make` 必须由 ROS Noetic
提供；`gzserver` 必须来自 Gazebo Classic，而不是新版 `gz sim`。

```bash
source /opt/ros/noetic/setup.bash
rosversion -d
test -f /usr/share/gazebo/setup.sh && echo 'Gazebo Classic setup: OK'
gzserver --version
command -v catkin_make
command -v cmake
command -v ninja
command -v python3
rospack find mavros
```

预期 `rosversion -d` 输出 `noetic`。如果 ROS Noetic 或 Gazebo Classic 的包源在目标
机器上不可用，应停止在此处并保留终端输出，使用上方官方安装页的当前归档/镜像说明，
不要改用 ROS2 或 Gazebo Harmonic 来替代当前 C99 路线。

### 2.4 配置项目路径并构建本地工作区

先从 Windows 侧设置项目根，再确认项目能映射到指定 WSL 发行版。下面命令仅检查路径
和构建前置条件，不启动 PX4、Gazebo、ROS 节点或飞行任务。

~~~powershell
$env:MOSIM_ROOT = (Resolve-Path '<MoSim 项目目录>').Path
Set-Location $env:MOSIM_ROOT
python Scripts/quality/check_project_path_registry.py --project-root . --require-canonical-active
python Scripts/quality/check_local_source_activation.py --project-root .
wsl.exe -d Ubuntu-20.04 --exec wslpath -a -u $env:MOSIM_ROOT
~~~

在 Ubuntu 终端中进入同一项目目录后，执行下列顺序。只有 PX4 脚本报告缺少
kconfiglib 或 future 时，才在第一条构建命令上追加 --bootstrap-python。

~~~bash
export MOSIM_ROOT="$(pwd -P)"
cd "$MOSIM_ROOT"

bash Scripts/sunray/build_local_px4_sitl.sh --build --jobs 2
bash Scripts/sunray/prepare_local_ros1_workspace.sh --profile foundation --build --verify --jobs 1
bash Scripts/sunray/prepare_local_ros1_workspace.sh --profile flight_adapter --build --verify --jobs 1
bash Scripts/sunray/prepare_local_ros1_workspace.sh --profile perception --build --verify --jobs 1
bash Scripts/sunray/prepare_local_ros1_workspace.sh --profile controller --build --verify --jobs 1 --px4ctrl-backend graphical_px4ctrl_c99
bash Scripts/sunray/check_sunray_ros1_runtime_preflight.sh
~~~

Windows 用户可以直接执行同等的封装入口；它会保持终端可见，并按相同顺序构建和预检：

~~~powershell
cmd /c Scripts/cmd/00_准备C99单机环境.cmd
~~~

预检成功时末行必须为 SUNRAY_ROS1_PREFLIGHT=PASS。该结果只说明本机系统依赖、
项目内源树、PX4 插件和生成 ROS1 工作区完整，不代表已经执行了飞行任务。

### 2.5 大型资产与可移植交付

源码包还必须包含或另附经清单校验的大型 Sunray 资产：

| 资产包 | 位置 | 当前清单规模 | 为什么不能省略 |
| --- | --- | --- | --- |
| Sunray 网格、贴图、扫描 CSV 和 Blender 源 | `src/simulation/gazebo/sunray/ASSET_MANIFEST.json` | 487 个文件，1,005,559,590 字节 | Sunray Gazebo 模型和传感器资源 |
| Livox 扫描模式 CSV | `src/simulation/gazebo/plugins/sunray/ASSET_MANIFEST.json` | 6 个文件，156,521,030 字节 | MID-360 Gazebo 扫描模式 |

这些文件因体积被 Git 忽略。便携交付时应将其连同各自 ASSET_MANIFEST.json 一并提供；
缺少它们时，00_准备C99单机环境.cmd 的预检应视为阻断，而不是以旧 Results 记录替代。

### 2.6 运行和结果复核

通过 00 预检后，一次只运行一个 C99 演示入口：

~~~powershell
cmd /c Scripts/cmd/01_运行C99单机起飞悬停降落.cmd
cmd /c Scripts/cmd/02_运行C99风扰闭环.cmd
cmd /c Scripts/cmd/03_运行C99电机故障恢复闭环.cmd
~~~

每次运行都必须使用终端本次打印出的新 Results/sunray_ros1/<run_id>/ 目录核验。名义
任务读取 PX4CTRL_BASIC_MISSION_METRICS.json；风扰和电机任务读取 DEMO_STATUS.json
及对应的注入确认 JSON。只有同一新目录中这些文件的 status=passed、
RUN_MANIFEST.json 和 px4ctrl_build_backend.txt 一致时，才能记录本次复现通过。

## 3. UE5 场景显示环境

### 3.1 项目、引擎与插件

MoSim 的项目级 UE 入口是 UE5/MoSimSceneLibrary/MoSimSceneLibrary.uproject，其工程描述
显式绑定 Unreal Engine 5.5。先通过 Epic Games Launcher 安装 UE 5.5，再打开该项目；
Epic 的常规安装和项目打开流程见
[Installing and Setting Up a Project](https://dev.epicgames.com/documentation/en-us/unreal-engine/installing-and-setting-up-a-project)。

首次打开前，在 PowerShell 检查项目和本地桥接插件是否齐全：

~~~powershell
$ueProject = Join-Path $env:MOSIM_ROOT 'UE5/MoSimSceneLibrary/MoSimSceneLibrary.uproject'
Test-Path $ueProject
Test-Path (Join-Path $env:MOSIM_ROOT 'UE5/Bridge/QuadrotorMworksBridge.uplugin')
Test-Path (Join-Path $env:MOSIM_ROOT 'Docs/Skills/Unreal/mcp/unreal-engine-mcp/FlopperamUnrealMCP/Plugins')
Start-Process $ueProject
~~~

项目含有 C++ QuadrotorMworksBridge 插件。若 UE 提示编译模块，先安装与 UE 5.5 匹配的
Windows C++ 工具链并在 Unreal Editor 中重新生成/编译项目；不要删除工程中的
AdditionalPluginDirectories 或通过禁用桥接插件来掩盖构建错误。

### 3.2 导入场景资产

基础源码包只带 UE 项目壳、配置和桥接源码，不承诺包含 Fab/Marketplace 导入的场景
Content。通过 Epic Launcher 或 Fab 手动执行 Create Project 或 Add To Project；
每次导入均按 UE5/MoSimSceneLibrary/Docs/import_checklist.md 记录资产名称、引擎版本、
内容根目录、主 .umap、所需插件、地图可打开状态和障碍物碰撞状态。

场景导入后，在项目根运行只读审查脚本：

~~~bash
python3 Scripts/UE5/audit_scene_source.py --maps
python3 Scripts/UE5/plan_scene_truth_export.py --query <scene-name>
~~~

这两步用于登记地图和生成后续场景真值导出计划。完成导入并不代表 Gazebo 中同名地图、
规划器或控制器已经运行。

### 3.3 便携交付与显示边界

UE5/MoSimSceneLibrary/Content、Plugins、Binaries、Intermediate、Saved 和
DerivedDataCache 均可能是本机生成或被 Git 忽略的内容。需要复现具体视频或场景时，
交付包必须另外包含相应 Content 资产及导入清单，或明确要求操作者重新从有权访问的
Fab/Marketplace 库导入；仅复制 .uproject 无法还原场景。

UE 负责场景渲染、相机/传感器画面和演示回放。MWORKS 仍是模型与控制权威，Gazebo/PX4/
MAVROS 日志和 RViz 仍分别负责运行时、话题和坐标审查；UE 画面不作为控制闭环或性能通过
的唯一判据。

## 4. 常见阻断的定位顺序

| 现象 | 首先检查 | 正确处理 |
| --- | --- | --- |
| 00 找不到 Ubuntu-20.04 | wsl --list --verbose | 安装或转换为名称和版本均匹配的 WSL2 发行版 |
| 预检提示 ROS Noetic、Gazebo Classic、MAVROS 缺失 | /opt/ros/noetic/setup.bash、/usr/share/gazebo/setup.sh、rospack find mavros | 完成对应系统包安装后，从 00 重新构建/预检 |
| PX4 或 ROS1 工作区路径不在 src | Config/runtime/ros1_local_source_manifest.v1.json | 修复缺失的项目内源文件；不要指向 References 或旧 WSL 工作区 |
| Livox/Sunray 资源缺失 | 各目录 ASSET_MANIFEST.json | 补齐外部资产包并重新运行预检 |
| UE 提示引擎或模块不兼容 | .uproject 的 EngineAssociation、插件路径和 UE 编译日志 | 使用 UE 5.5 和匹配的 C++ 工具链，保留插件配置后重新构建 |
| UE 打开但没有预期场景 | Content、导入清单、主 .umap | 导入或恢复相应资产包；不要把项目壳误认为完整场景包 |

任何阻断都应保留首次出现的终端或 Editor 日志，再处理根因。不要用历史结果、窗口截图或
其他运行时路线的成功记录覆盖当前机器的阻断状态。
