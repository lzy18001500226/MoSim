**问题 1：本次软件构造课程设计主要维护了什么内容？**

**答：** 维护对象不是单个控制算法，而是模型、配置、控制器接口、Runner、生成代码、测试脚本和结果证据组成的完整软件链路。重点工作包括动力学模块目录收敛、Runner 分层、旋翼命令时序和符号映射修正，以及图形入口和代码交付清单维护。

**问题 2：为什么不能把模型检查通过直接写成系统性能通过？**

**答：** 模型检查只能说明模型结构或语法满足检查条件。性能结论还需要有效的 MWORKS 原始结果、非空变量序列、指标文件和对应的运行清单；ROS、QGC、RViz 或 UE 的界面状态也不能替代这些正式证据。

**问题 3：本次维护工作的主要认识是什么？**

**答：** 软件维护不仅是修复报错，还要把隐含约定变成接口合同，把配置、生成产物和结果来源记录下来，并保留失败、超时和阻塞记录。这样后续修改才能知道影响范围，报告结论也不会超过实际证据。

**问题 1：Sunray150 机体模型中的参数如何分类？**

**答：** 参数分为几何、质量、惯量、气动、电机和传感器等层。几何和质量参数尽量保留实物装配或称量来源；惯量、气动系数和电机动态在没有完整辨识数据时标记为工程种子，并保留后续替换边界，不能写成已经完成实机辨识。

**问题 2：为什么要把物理参数 Profile 和实验场景 Profile 分开？**

**答：** 物理 Profile 描述机体和执行器，实验 Profile 描述轨迹、风扰、参数失配和电机效率等条件。分开后可以复用同一机体和控制器，避免把场景扰动误当成控制器参数，也便于回溯每次实验使用的配置。

**问题 3：模型能够证明哪些结论，不能证明哪些结论？**

**答：** 模型源码和结构检查可以证明模型组织、接口和参数连接情况；有效的 MWORKS 原生结果可以支撑声明范围内的仿真分析。它们不能单独证明真实飞行、参数已经完成实机辨识，或所有运行时控制器都已经验收通过。

**问题 1：项目为什么定义多种控制器输出边界？**

**答：** 不同控制器可能输出姿态与总推力、机体角速度与总推力、六维力矩或四路旋翼命令。定义 ATTITUDE_THRUST、BODY_RATE_THRUST、WRENCH 和 ROTOR_COMMAND 四类边界，可以让不同控制器通过 Adapter 接入同一个公共 Plant，减少比较条件漂移。
