# 自主探索与集群规划实施路线

状态：G10之后的探索/集群规划实施路线，2026-07-01。

本文回答：G9/G10控制器和增强层闭环收口后，如何按“单机自主探索 ->
多机自主探索 -> 多机集群/队形规划”的顺序继续推进，并保证所有结果仍以
Gazebo/Sunray/PX4/MAVROS/RViz可复现实验为准。

## 1. 当前结论

本地参考已经足够支撑下一阶段，不需要先从零手写探索栈：

| 阶段 | 首选参考 | 作用 |
| --- | --- | --- |
| 单机全覆盖探索 | `References/Lab/exploration_coverage/FALCON-ros1-noetic` | 单UAV自主探索、覆盖路径引导、Factory室内全覆盖主线 |
| 单机局部探索基线 | `References/Lab/exploration_coverage/FUEL` | 已验证局部frontier/B-spline链路；不作为Factory全图主线 |
| 多机未知探索 | `References/Lab/exploration_coverage/RACER`, `References/Lab/exploration_coverage/fast_multi_robot_exploration` | RACER/FAME家族，多UAV分布式探索、共享地图/任务分配 |
| 已知场景覆盖备选 | `References/Lab/exploration_coverage/FC-Planner` | 已知/半已知场景覆盖和重建；主线失败时作为工程兜底 |
| 大场景/地下探索参考 | `References/Lab/exploration_coverage/tare_planner-melodic-noetic`, `References/Lab/exploration_coverage/gbplanner_ros-gbplanner2` | 参考/对照，不作为当前第一落地入口 |
| 多机轨迹协商 | `References/Lab/swarm_coordination/mader`, `References/Lab/swarm_coordination/rmader` | 通信延迟、轨迹去冲突和动态障碍候选；Gurobi依赖使其不作为第一入口 |
| 队形/集群规划 | `References/Lab/swarm_coordination/Swarm-Formation` | 已知目标和队形保持/穿越，不是探索 |

当前推进顺序冻结为：

```text
FALCON单机全覆盖探索
  -> 若FALCON阻塞，FC-Planner或脚本化分块覆盖建图兜底
  -> RACER/FAME三机未知探索全覆盖
  -> 若RACER/FAME阻塞，三机分区/脚本化覆盖建图兜底
  -> 需要时补MADER/RMADER轨迹协商
  -> Swarm-Formation式集群/队形规划
  -> UE地图导入Gazebo与QGC二次开发调研/尝试
```

2026-07-03 Factory L2室内全覆盖结论：

```text
Factory室内边界约175.7m x 64.0m。
RACER单机120s和三机60s均能在clean Factory链路运行，但覆盖率只停留在
中心局部，不能宣称全室内覆盖。
FUEL已分类为Factory大范围探索的局部单机基线，不作为全室内主路线。
FALCON具备单UAV自主探索和覆盖路径引导语义，已完成source-first接入、
短时runtime和Factory室内coverage判定。当前结论是：FALCON可以在MoSim

RACER/FAME家族保留为多机未知探索主线，但必须先解决大Factory覆盖扩张问题。
FC-Planner或脚本化lawnmower/分块目标覆盖建图是已知场景兜底路线；该路线
可以完成全室内累计建图任务，但必须标注为known-scene/scripted coverage
mapping，不能冒充未知环境自主探索。
```

当前不得再用以下证据替代全覆盖：

```text

短时间路径span；
RViz看起来有点云或frontier；
cloud_bounds_proxy上界；
只证明不越界/不撞机的三机运行结果。
```

## 2. 统一接入边界

任何探索、规划或集群参考都只能进入以下链路：

```text
state source / sensor source
  -> planner or exploration reference
  -> Planner Adapter
  -> Trajectory Server
  -> controller core / generated controller
  -> MAVROS / PX4
  -> Gazebo / Sunray plant
  -> logs / metrics / RViz evidence
```

禁止链路：

```text
planner直接发布最终MAVROS控制命令
planner直接读取Gazebo truth或UE truth作为正式规划输入
上游自带simulator成功后宣称MoSim闭环成功
PCD全局地图输入冒充未知环境在线探索
RViz非空画面替代覆盖率、轨迹、控制误差和碰撞证据
```

## 3. Profile要求

每次探索或集群实验必须记录：

```text
planner_profile
state_source_profile
sensor_profile
map_input_profile
trajectory_profile
controller_profile
augmentation_profile when used
safety_profile when used
communication_profile for multi-UAV
formation_profile for Swarm-Formation
evaluation_profile
display_profile
run_id and evidence_dir
```

地图输入必须显式区分：

| `map_input_profile` | 含义 | 能否作为正式闭环证据 |
| --- | --- | --- |
| `online_sensor_cloud` | 来自Gazebo/Sunray传感器或FAST-LIO/局部地图链路 | 可以 |
| `sensor_renderer_from_pcd` | PCD只用于生成深度/点云测量，不直接交给规划器 | 可以，但必须记录renderer边界 |
| `pcd_oracle_debug` | 规划器或地图层可直接看到全局PCD | 只能调试，不能作为正式探索成功 |
| `gazebo_truth_debug` | 使用Gazebo truth辅助状态或地图 | 只能调试或评价，不能作为正式规划输入 |
| `ue_truth_debug` | 使用UE真值/场景导出辅助 | 只能后续地图导入/对齐调试，不能替代Gazebo证明 |

### 4.1 Factory FUEL单机探索准备

Factory地图进入自主探索时，不把FUEL内部地图直接设为无限大。内部planner map
必须先按阶段放大，否则内存、RViz显示和规划失败会混在一起，无法归因：

| 阶段 | FUEL内部地图 | 审核累计点云/栅格 | 目标 |
| --- | --- | --- | --- |
| FUEL-F0 | `30 x 30 x 5 m`，围绕Factory安全锚点 | 点云200万体素、栅格100万体素 | 验证大于旧柱子场景的小范围探索能跑通 |
| FUEL-F1 | `50 x 50 x 8~10 m` | 根据F0资源占用提升到500万或`0`不裁剪 | 验证中等Factory区域累计显示和动态规划 |
| FUEL-F2 | 依据F0/F1结果扩展，不默认全厂无限 | 允许高上限或不裁剪压力测试 | 判断是否需要分区/抽稀/离线地图压缩 |

历史可复跑入口已归档，等待单独恢复验证后才可重新提升为当前入口：

```text
Scripts/cmd/Archive/legacy_unverified/启动Factory单机FUEL自主探索审核.cmd
Scripts/sunray/start_factory_fuel_single_exploration_review.ps1
```

该历史入口默认使用clean candidate Factory world、安全锚点`(0, 120, 0.2)`、FUEL
`30 x 30 x 5 m`地图、两个RViz窗口和60秒探索执行。它只证明对应run的
Gazebo/PX4/MAVROS/FUEL/RViz日志和显示结果，不自动证明全Factory覆盖完成。

审核层和规划层必须分开：

```text
FUEL planner input:
  /uav1/livox_world -> /sdf_map/occupancy_all

RViz review-only accumulation:
  /uav1/livox_world -> /mosim/goal4/livox_world_accumulated
  /sdf_map/occupancy_all -> /mosim/goal4/occupancy_accumulated
```

`Scripts/ros/accumulate_pointcloud_review.py`中的`--max-accumulated-points 0`
只表示审核层不裁剪；它不得被解释为FUEL内部地图无限，也不得作为完整覆盖率证明。
Factory FUEL审核需要同时看到：累计点云、累计occupancy boxes、实际轨迹、
执行命令轨迹、FUEL planner marker、机体三轴和run metrics。

FUEL失败时的处理：

```text
先查odom frame/timestamp、cloud frame、sensor_pose、B-spline时间基准和
Trajectory Server求值，不直接改控制器；当前D3保留的接口约束是：
FUEL B-spline起始时间按接收时刻对齐，raw FUEL命令保留为诊断topic，
px4ctrl-facing `/position_cmd` 经过可配置连续性平滑；
若FUEL map输入无法和MoSim传感器契约对齐，不继续把FUEL升级为全图主线；
Factory全覆盖优先转入FALCON source-first门禁。
```

## 5. FALCON单机全覆盖探索路线

目标：优先用开源FALCON完成Factory室内单机未知探索/全覆盖建图判定。FALCON
通过前，不进入“多机全覆盖已完成”声明；FALCON阻塞时再切FC-Planner或
脚本化分块覆盖。

FALCON已知源码边界：

```text
References/Lab/exploration_coverage/FALCON-ros1-noetic
```

当前source-first假设：

```text
FALCON支持ROS Noetic；
README/launch中存在custom map配置、bbox/map size、T_m_w等地图/坐标参数；
exploration.launch将/odom_world、depth image、sensor pose等输入接入
exploration/voxel mapping/trajectory server链路；
输出不得直接接MAVROS，必须经MoSim Planner Adapter和Trajectory Server。
```

需要先查清的风险：

```text
FALCON是否强依赖深度图而不能直接消费MID360点云；
voxel_mapping/map_render是否可用在线传感器或必须由PCD/mesh渲染；
CMake、NLopt、Open3D、CUDA/渲染资源路径是否能在当前ROS1环境构建；
FALCON输出轨迹/pos_cmd时间基准是否能与px4ctrl/Sunray链路对齐。
```

门禁：

```text
FALCON-F0 source audit:
  读取README、launch、config和关键源码；
  记录输入/输出topic、地图边界、覆盖/终止语义、依赖和禁止声明。

FALCON-F1 build/dependency preflight:
  在隔离ROS1 workspace检查CMake、NLopt、Open3D、CUDA相关依赖；
  能构建则记录构建产物和roslaunch静态解析；
  不能构建则给出最小缺口和是否值得安装/改造。

FALCON-F2 MoSim topic bridge dry-run:
  MoSim odom/sensor pose/cloud或depth-render输入 -> FALCON输入；
  FALCON轨迹/pos_cmd -> MoSim Planner Adapter / Trajectory Server；
  不启动Gazebo飞行，不发布MAVROS最终控制命令。

FALCON-F3 Factory single-UAV runtime:
  clean Factory Gazebo + Sunray/PX4/MAVROS + FAST-LIO/px4ctrl链路；
  固定z策略先保持[0.9,1.6]m；
  记录truth/odom/pointcloud/occupancy、planner轨迹、控制执行和coverage packet。

FALCON-F4 full-coverage review:
  覆盖率达到Factory室内边界阈值，建议首轮仍用0.80；
  无XY越界、无碰撞、无高度/姿态安全违规；
  RViz点云/栅格/轨迹和日志指标可以复核。
```

但 `0.1 m` 分辨率使 `exploration_node` 占用约 95% CPU，单次规划达到
2.597 s，五分钟上限前仅输出 1 段 B-spline，局部 coverage 代理约
2.49%。因此禁止直接跑 80 m/0.1 m；下一步先验证 40 m/0.2 m，在计算
负载可接受后再扩大范围。

后续验证已经完成并推翻了“必须先做滑动窗口”的假设。`0.2 m` 栅格配合
1 Hz 全图 occupancy 审核发布后，80 m 运行的平均规划时间降至约 0.024 s，
CPU 降至约 10-14%，且安全通过。全图发布降频只作用于 RViz/审核输出，
不降低点云地图更新或规划频率。

完整 Factory 室内边界 `175.65987 x 63.99956 x 3 m` 也已完成短门禁。
`0.3 m/s`、`0.2 m/s^2` 配置运行 30.002 s，产生 56 段 B-spline 和
3777 条 planner command，规划均值/最大值约 0.030/0.081 s，无姿态、
高度或降落安全 blocker。证据目录为：

```text
Results/sunray_ros1/factory_l2_fuel_mid360_full176x64_res02_map1hz_v03_a02_30s_20260712/
```

该次传感器足迹覆盖代理为 3.55%，只能证明短时持续扩展，不能声明全厂
覆盖完成。此前日志中的 `new_frontiers=0` 出现在 30 s execute 窗口结束后的
降落/清理阶段；当时 FUEL 仍保留 28 个可访问 frontier，因此算法没有自行
停止。Factory 专用启动器后续默认使用完整室内边界、0.2 m、MID360 水平
全向、1 Hz 全图审核发布和 0.3/0.2 安全运动限制。下一步是使用同一基线
执行长时覆盖增长，不再回到 16 m 深度相机口径，也不先手写滑动窗口。

长时任务还必须按 ROS 仿真时间与墙钟时间分开验收。首次 120 s 增长运行在
仿真时间约 97.5 s、仍有 12 个 frontier 且仍发布轨迹时被旧的 300 s 墙钟
超时强制结束，退出码 124；这不是 FUEL `FINISH`。Factory 完整地图当前
real-time factor 约为 0.2-0.3，启动器默认墙钟上限因此改为
`execute_s / 0.20 + 180`，并保留显式总超时覆盖参数。后续不得把 124 或
execute 时间未跑满的记录计入覆盖停滞结论。

修正墙钟超时后的长时重跑又暴露了独立的控制接口问题：FUEL raw reference
与实际飞机位置拉开超过 3 m，而适配器仍继续按时间推进且清零速度/加速度
前馈，最终实际速度约 0.83 m/s、真值横滚超过 45 度。该问题不能归因于
MID360 或 frontier。Factory FUEL 入口现启用已有 odom-target guard，将发送
给 px4ctrl 的 XY 参考限制在 MAVROS odom 前方 0.6 m 内；raw FUEL command
保持不变并继续记录。该门禁只约束执行层，不能用于冒充规划器输出。

后续空间审计证明，仅有时间戳同步仍不够。raw FAST-LIO `camera_init`
里程计与 Factory/MAVROS local 存在刚体旋转和平移；此前 FUEL 使用 raw
`/Odometry` 和 `/cloud_registered` 选取 frontier，而执行端遗漏同一空间变换。
`fastlio_odom_alignment_adapter.py` 现以同一个初始化刚体变换同时输出 aligned
odom 与保留原字段的 aligned cloud，FUEL 只消费这两个对齐后的输入。

对齐后的 120 s 首次运行又暴露出执行命令动力学不一致：位置被平滑为
`0.3 m/s`，但仍保留原始 B-spline 的速度/加速度前馈，真值姿态峰值达到
约 `68.96 deg`。适配器现在根据最终发布位置差分重算速度，并将加速度、
jerk 清零。30 s 动态回归位于：


该回归 `status=passed`、无 blocker、正常降落；aligned cloud 为 `1048/1048`
帧，最终命令最大速度 `0.300000 m/s`、最大 adapter 单步 `0.015 m`，探索阶段

frontier。因此剩余问题是全局 frontier 目标与受限执行/重规划节奏之间的推进
效率，不再是雷达为空、相机 FOV、时间戳、空间 frame 或安全前馈未收口。
