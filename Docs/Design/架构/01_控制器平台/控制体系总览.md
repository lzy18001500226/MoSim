## 0.1 控制链路分层与算法归属（摘要）

后续算法不能被混成同一层的“可选控制器”。本节只保留算法目录的阅读摘要；当前
实施以 `MWORKS控制器关系与组合架构.md` 的责任链，以及
`控制平台接口与闭环实施规范.md` 的机器注册和槽位组合为准。

```text
任务/场景/轨迹
  -> 编队参考生成（可选；每机 ReferenceFrame）
  -> Reference Governor（可选；参考约束）
  -> 名义控制器（恰好一个）
  -> 受控增强/扰动补偿（0..1，或已登记固定集成链）
  -> 命令安全过滤（恰好一个）
  -> 后端姿态/角速度与分配
  -> Command Adapter
  -> 电机/机体/传感器

故障管理从执行器响应和状态健康侧接入，可发布故障事件、重构后的电机命令
或安全降落动作；它不是名义控制器之后的一条普通串联算法。
```

| 层级/槽位 | 职责与可替换边界 | 已登记的典型输出 | 当前报告应如何描述 |
| --- | --- | --- | --- |
| 任务、轨迹与规划 | 产生单机原始`ReferenceFrame`，不计算控制命令 | `p/v/a/yaw`，可选`jerk/snap` | 轨迹来源，不计为控制器 |
| 编队参考 | 从多机任务和多机状态生成每机参考，不替换单机名义控制器 | `MULTI_UAV_REFERENCE` | P8 是编队参考路线；不能写成电机级编队控制 |
| 参考约束 | 在进入名义控制器前整形参考，如 Reference Governor | governed `ReferenceFrame` | 注册表中归入 safety profile，但功能位置在名义控制器之前 |
| 名义控制器 | 一次运行仅一个，完成主跟踪控制并输出一个`CommandFrame` | `ATTITUDE_THRUST`、`BODY_RATE_THRUST`或`WRENCH` | 只有此层的模块才可称为“替换主控制律”；不得由算法名称推断其内部每一子环 |
| 增强/补偿 | 对已选名义命令加有界前馈、估计或残差修正 | 通常仍为`ATTITUDE_THRUST` | AWFF、L1、ADRC、INDI、ILC、anti-windup等不单独替换名义控制器 |
| 命令安全 | 限幅、CBF、地理围栏、失效状态机等通过/修改/拒绝候选命令 | 受约束的同类型命令 | 安全模式不与 PID/MPC 计作同级对比算法 |
| 姿态/角速度、分配与执行 | 完成姿态/角速度后端、力矩/总推力到转子命令的分配，以及植物和传感器 | `WRENCH`、`ROTOR_COMMAND`和物理状态 | 当前`ATTITUDE_THRUST`运行由 PX4 姿态/角速度环和分配器拥有；不是每个 MWORKS 模块自带电机级闭环 |
| 故障检测、容错与重构 | 从转子响应/健康状态形成 FDI、重构或降落决策 | `FAULT_EVENT`、`ROTOR_COMMAND`或`ROTOR_COMMAND_AND_LAND_ACTION` | 必须说明注入、检测、隔离、重构和恢复证据，不能把故障注入本身写成 FTC |
| 评价与证据 | 从日志、结果和截图提取指标，不参与控制 | 指标、图、manifest | 仅证明相应证据层，不提升控制层结论 |

`ATTITUDE_THRUST`名义模块的统一契约是“状态和参考 -> 期望姿态与物理总推力”；
它通常承担项目侧的位置/速度跟踪和姿态指令生成，而当前 PX4 仍拥有姿态/角速度
后端与控制分配。`BODY_RATE_THRUST`模块输出角速度参考与推力，绕过 PX4 姿态
环但仍使用 PX4 角速度环和分配；`WRENCH`模块还必须有已验证的分配器，当前不
能因离线模型存在而宣称 ROS1 运行时可选。各算法是否显式含位置、速度、姿态或
角速度子环，必须以其源码、模型端口和 profile 为准，不能只按 PID、MPC 或神经
网络名称推断。

因此，每个后续算法文档必须先声明它占用的槽位、输入输出边界、下游 owner 和
证据层级。不能把安全过滤、故障注入、神经网络补偿和名义控制器当作同一种
“控制器切换项”处理。67 条路线的逐类事实表见`控制器证据矩阵.md`。

当前真机化收尾边界：

```text
Docs/Design/架构/03_测试调参与证据/真机化与C++化.md
```

该文档冻结当前原则：不推倒重写已经跑通的 Sunray/PX4/Gazebo 基准链路，
但必须把实时闭环关键路径从临时脚本中剥离出来。控制器核心、FAST-LIO
状态源对齐、PX4 external odometry、trajectory server、Controller Adapter
和安全状态门禁应进入 C/C++ 或可编译组件；Python 保留为 launch、metrics、
plot、review pack、offline compare 等工具层。任何后续“可真机部署”或
“飞行级闭环”声明，都必须说明相关节点属于 T0/T1/T2/T3 哪一层。

MoSim控制系统由哪些层组成

# 2. MoSim项目定位

MoSim是当前竞赛阶段的：

> 基于MWORKS、ROS 1、Gazebo和PX4的四旋翼位姿控制、故障容错与编队协同建模仿真平台。

MoSim当前聚焦：

```text
四旋翼动力学
单机位姿控制
轨迹跟踪
鲁棒与自适应控制
执行器故障容错
控制分配
编队控制
ROS 1 + Gazebo联合仿真
PX4 SITL与板载部署
MWORKS控制器代码生成
统一测试与性能评价
```

MoSim暂不承担未来CoSim中的全部内容。

以下内容属于未来CoSim扩展方向：

```text
固定翼
垂直起降固定翼
涵道与火箭模型
地面车辆
机器狗
多域异构集群
大规模强化学习训练
通用多机器人任务系统
```

因此：

```text
MoSim：四旋翼控制与部署平台
CoSim：未来多域无人系统综合仿真平台
```

# 4. 控制体系设计原则

## 4.1 原子算法与组合方案分离

原子算法是：

```text
PID
SE3
DFBC
LMPC
NMPC
INDI
L1
AWFF
QP控制分配
```

组合方案是：

```text
DFBC + INDI
SE3 + L1
NMPC + INDI + L1
SE3 + 故障诊断 + 故障QP分配
```

组合方案只保存在Profile中，不复制算法源码。

---

## 4.2 控制层级明确

必须区分：

```text
轨迹规划
编队参考生成
位置与速度控制
姿态控制
角速度控制
力矩控制
控制分配
电机执行
```

不得把所有算法统一称为“控制器”。

---

## 4.3 物理接口优先

MoSim内部优先使用：

```text
m
m/s
m/s²
rad
rad/s
N
N·m
rad/s电机转速
```

归一化油门、PWM和DShot只存在于执行器或PX4适配层。

---

## 4.4 运行后端解耦

算法核心不得直接依赖：

```text
ROS消息
MAVROS消息
PX4 uORB结构体
Gazebo插件
MWORKS运行时API
```

各平台通过适配器连接。

---

## 4.5 单一最终控制权

系统可以同时运行主控制器、影子控制器和备用控制器，但同一时刻只能有一个最终控制命令生产者。

---

## 4.6 安全优先

控制优先级为：

```text
飞行稳定
>
执行器与碰撞安全
>
故障降级
>
任务完成
>
跟踪精度
>
控制能耗
```

```text

```

上述结构是目标责任链，不是“所有列出的算法均已完成”的声明。当前 P8 的九条
编队参考路线由一个集中式、固定三机状态输入的 reference generator 实现；实际
三机整机模型是领航机 8 字轨迹加固定三角偏置，并为每架机接入同类 LinearMPC
跟踪器。当前源码没有邻机消息端口、通信拓扑、延迟或丢包模型，故不得把它写成
已完成的分布式通信或共识网络验证。真正的分布式编队验证还必须补齐每机局部观测、
邻机消息契约、拓扑、延迟/丢包和闭环证据。

`控制器证据矩阵.md` 的逐行 `claim_ceiling` 为准。除明确标为当前基线的项目外，
P01-P16 的简短说明均不得单独解读为已完成整机闭环或已替换 PX4 后端。

Profile，必须补齐每机局部状态、邻机消息、通信拓扑/时序，以及 Consensus 输出到
每架 SE3 名义控制器的同一 run 证据。现有 P8 只证明集中式三机参考生成。

## P18 Consensus + CBF + SE3

候选组合，不是当前 P8 的已验收结论。除 P17 的通信闭环要求外，还必须证明 CBF
在每机参考/命令上的实际挂接位置、冲突约束和机间安全门，不能以集中式间距计算
替代分布式 CBF 证据。

## P19 Diff-Planner swarm / EGO-Swarm参考 + DFBC

候选组合，不是当前已注册或已验收的 Profile。Diff-Planner 或 EGO-Swarm 在此只能
占用任务/规划层并输出每机 `ReferenceFrame`；DFBC 才是每机下游名义控制候选。
要进入正式路线，必须补齐规划器到参考的坐标系、时间戳和重规划语义，明确每机
名义控制器、安全过滤和后端 owner，并提供同一 run 的多机参考、间距、碰撞和跟踪
证据。不能把现有离线全局规划或 P8 固定三机参考证据外推为该 Profile 已完成。

## P20 SUPER + NMPC

候选组合，不是当前已注册或已验收的 Profile。SUPER 若作为高速安全规划器，只能
向 NMPC 名义控制器提供受约束的轨迹/参考，不能绕过 Reference Governor、命令安全
过滤、PX4 姿态/角速度后端和控制分配。进入正式路线前必须冻结求解频率、失败
fallback、碰撞约束及规划到 NMPC 的接口，并以同一 run 证明求解时限、约束触发和
实际跟踪；不能以单独规划轨迹或离线求解成功代替飞行闭环证据。

# 36. 强制性总体规则

1. 规划器、编队控制器和单机控制器必须分层。

2. 基础控制器和增强模块必须分离。

3. 完整组合只保存在Profile中。

4. 控制器核心不得依赖ROS、PX4和Gazebo消息类型。

5. 所有控制器必须使用统一输入输出契约。

6. 内部统一使用SI单位和物理控制量。

7. PX4坐标和推力语义由适配层处理。

8. 同一时刻只能有一个最终控制命令生产者。

9. Controller Manager负责控制器切换和失败降级。

10. 控制分配必须与轨迹控制器解耦。

11. 故障诊断、容错控制和故障控制分配必须形成完整链路。

12. 编队控制不得直接输出电机命令。

13. 安全过滤优先级高于队形保持和轨迹精度。

14. MWORKS生成代码不得手工长期维护。

15. 同一控制器必须尽可能复用于MWORKS、ROS和PX4。

16. 所有控制器必须经过统一Test Harness。

17. 开源算法必须记录来源、许可证和修改内容。

18. 未通过SITL和实时性测试的控制器不得进入真机。

19. 前端不得绕过安全管理直接控制执行器。

20. 当前MoSim严格聚焦四旋翼，不提前吞并未来CoSim全部范围。

# 37. 文档结论

MoSim控制体系不是若干PID、MPC和故障模型文件夹的简单集合，而是一套完整的分层控制架构：

```text
轨迹与规划
   ↓
编队参考（可选）与参考约束
   ↓
单机轨迹控制
   ↓
鲁棒与自适应增强
   ↓
命令安全过滤
   ↓
后端姿态/角速度与控制分配
   ↓
执行器

故障检测、容错与重构：从执行器/状态健康侧横向介入，不是固定串联末端
```

同时由：

```text
统一接口
Controller Manager
参数与Profile
MWORKS代码生成
ROS 1与Gazebo
PX4部署
Test Harness
```

形成完整工程闭环。

最终目标是使：

```text
PX4原生控制器
px4ctrl
PID
LQR/LQI
SO3/SE3
DFBC
SMC
LMPC/NMPC
INDI
L1
AWFF
故障容错控制
编队控制
CBF安全控制
```

能够在同一套MoSim平台中被统一建模、统一接入、统一切换、统一部署和统一评价。
