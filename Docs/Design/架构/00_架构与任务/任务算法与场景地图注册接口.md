# MoSim任务算法与场景地图可插拔接口设计

> 状态：产品与接口冻结设计，2026-07-17。
>
> 本文定义任务算法、场景地图、QGC二维地图和ExperimentProfile之间的稳定接口。
> 它不证明任一算法、地图或多机任务已经通过runtime验收。

## 1. 目标

MoSim必须允许在不修改GUI和Orchestrator核心代码的前提下扩展：

- 单点/航点/局部避障规划器；
- 单机未知环境自主探索算法；
- 多机协同未知探索算法；
- 已知地图覆盖算法；
- 编队参考与编队控制算法；
- Factory、城市、园区和后续自定义Gazebo/UE场景；
- QGC二维任务地图、UE三维显示和RViz工程审核图层。

扩展的基本单位是“注册模块 + Adapter + 参数Schema + 证据状态”，不是GUI硬编码按钮，
也不是把算法源码复制进每个场景。

## 2. 权威对象与分层

```text
SceneMapRegistry
  -> 地图资产、坐标、边界、出生点、Gazebo/UE/QGC绑定

MissionAlgorithmRegistry
  -> 任务算法类别、能力、输入输出、Adapter、参数和运行后端

ControlModuleRegistry
  -> 名义控制器、增强、安全、故障、内环、分配和命令适配

ExperimentProfile
  -> 引用上述注册对象，冻结一次可复现实验

Profile Validator
  -> 解析兼容性、拒绝原因、证据等级和Launch Plan
```

注册表描述“有哪些模块、模块需要什么、当前能否使用”；Profile描述“本次实验具体选择
什么”；Adapter负责把原生算法接口转换为MoSim统一帧；GUI只读取注册表和Profile。

## 3. MissionAlgorithmRegistry

### 3.1 算法类别

```text
goal_planner
  waypoint / A* / Diff-Planner / EGO-Planner / local replanner

single_uav_exploration
  FUEL / FALCON / GBPlanner / frontier / NBV

multi_uav_exploration
  RACER / FAME / multi-agent NBV / graph exploration

known_map_coverage
  partition coverage / sweep / inspection route

formation_reference
  Leader-Follower / Virtual Structure / Consensus / Containment
  Formation Tracking / Reconfiguration / Formation CBF / Distributed MPC
```

`known_map_coverage`不得标记为未知环境自主探索。多机同时运行相同单机算法也不得自动
标记为`multi_uav_exploration`；后者必须具有共享地图、任务分配或去重契约。

### 3.2 注册项最小Schema

```yaml
algorithm_id: fuel_ros1
display_name: FUEL
kind: single_uav_exploration
version: upstream-commit-or-project-version
status: implemented
selectable: false
claim_ceiling: fixed64_runtime_accepted

vehicle_count:
  min: 1
  max: 1

environment_knowledge: unknown
map_capabilities:
  consumes_live_occupancy: true
  consumes_static_prior_map: false
  publishes_frontiers: true
  publishes_coverage: true

requirements:
  sensors: [mid360]
  state_sources: [fastlio_px4_fused]
  frames: [world, body, lidar]
  trajectory_representations: [bspline]

adapter_id: fuel_ros1_adapter_v1
parameter_schema: Config/mission_algorithms/fuel/schema.json
default_parameters: Config/mission_algorithms/fuel/factory_l2.yaml
runtime_backend_id: fuel_ros1_noetic
latest_evidence: Results/...
disabled_reason: full_factory_runtime_gate_pending
```

实际机器格式可以采用JSON或YAML，但字段语义必须稳定。算法名称不能替代`kind`：例如
Distributed MPC注册为编队参考还是多机探索优化器，必须由注册项明确。

### 3.3 统一输入帧

| 帧 | 最小内容 | 规则 |
| --- | --- | --- |
| `LifecycleContext` | run、profile hash、reset、enable、dt、deadline | 所有算法必须确定性reset |
| `StateFrame` | 单机状态、时间戳、frame、健康状态 | 不允许混合未声明的truth和估计状态 |
| `SwarmStateFrame` | 逐机状态、成员健康、通信新鲜度 | 多机算法必须按`vehicle_id`隔离 |
| `MapFrame` | live occupancy、分辨率、原点、边界、版本和时间戳 | 未知探索只能消费允许的实时地图 |
| `MissionFrame` | 任务类型、目标、区域、结束条件、优先级 | 不能把GUI点击直接转成裸ROS命令 |
| `GoalSet` | 单机或逐机目标、合法性和有效期 | 多机目标必须显式绑定成员 |

### 3.4 统一输出帧

| 帧 | 用途 |
| --- | --- |
| `TrajectorySet` | 单机或逐机可执行轨迹，包含表示类型、时间参数和有效期 |
| `ReferenceFrame` | 进入Trajectory Server/控制器的标准参考 |
| `FrontierSet` | 前沿簇、候选点、收益、可达性和分配状态 |
| `CoverageFrame` | 已知/未知/自由/占据体素、覆盖率定义和统计边界 |
| `AssignmentFrame` | 多机任务分配、owner、租约、冲突和重分配原因 |
| `FormationReference` | 队形、slot、拓扑、每架飞机参考和重构状态 |
| `AlgorithmDiagnostics` | 生命周期、规划耗时、失败原因、输入新鲜度和证据计数 |

算法可以不产生与其无关的输出，但必须在能力字段中声明。GUI根据能力显示图层，不能假设
每个规划器都有frontier或coverage。

### 3.5 Adapter与生命周期

每个原生算法通过项目自有Adapter接入：

```text
native ROS topics/actions/services
  -> Mission Algorithm Adapter
  -> MoSim统一输入输出帧
  -> Trajectory Validator
  -> Trajectory Server
  -> Controller Host
```

Adapter只做类型、frame、时间戳、namespace和生命周期转换，不重写算法决策。统一生命周期：

```text
configure -> initialize -> ready -> start -> running
          -> pause -> resume -> stop -> reset
          -> failed / degraded
```

启动、暂停、停止和失败必须产生结构化ACK。算法进程存在不等于`ready`；只有输入新鲜、输出
契约有效且声明的依赖满足后才能进入`running`。

## 4. 算法选择与切换

### 4.1 运行前选择

Model Studio和Flight Console按以下顺序过滤算法：

```text
SceneMap
  -> 任务类型
  -> 单机/多机数量
  -> 已知/未知地图语义
  -> 传感器和状态源
  -> 支持的轨迹输出
  -> runtime backend
  -> 证据等级
```

界面状态：

```text
accepted + compatible + scene/runtime evidence valid -> enabled
implemented但缺当前场景或runtime证据             -> visible_disabled
blocked/planned/audit_only                         -> research_only
incompatible                                      -> rejected_with_reason
```

改变任务算法必须生成新的ExperimentProfile和hash，不能保留旧算法内部状态。

### 4.2 飞行中切换

默认禁止任意热切换。允许的受控切换流程：

```text
请求切换
  -> 当前任务进入安全悬停
  -> 停止并确认旧算法不再发布轨迹
  -> 清理Trajectory Server待激活轨迹
  -> 初始化新算法和地图/状态输入
  -> 验证ready与首条轨迹
  -> 人工确认或预先验收的自动回退策略
  -> 恢复任务
```

已知/未知地图语义不同、单机/多机模式不同、地图坐标不同或车辆数变化时必须结束当前run，
不能热切换。备用局部规划器切换只有在切换边已经单独验收时才能自动执行。

## 5. SceneMapRegistry

### 5.1 地图不是单个world文件

一个可选择场景由同一`map_id`下的一组资产和坐标合同组成：

```yaml
map_id: factory_l2
display_name: Factory L2
version: v1
status: accepted

coordinate_contract:
  world_frame: world
  linear_unit: meter
  vertical_axis: z_up
  world_bounds: [xmin, ymin, zmin, xmax, ymax, zmax]
  gazebo_to_ue_transform: Config/maps/factory_l2/gazebo_to_ue.json
  world_to_pixel_transform: Config/maps/factory_l2/world_to_pixel.json
  calibration_hash: sha256:...

gazebo:
  world_path: Results/.../factory_l2.sdf
  model_paths: [...]

unreal:
  project_path: UE5/...
  level_name: Factory

qgc_2d:
  provider: local_metric_map
  raster_asset: Assets/maps/factory_l2/floorplan.png
  vector_overlay: Assets/maps/factory_l2/structure.geojson
  thumbnail: Assets/maps/factory_l2/thumbnail.png

mission:
  spawn_zones: [...]
  exploration_boundary: [...]
  altitude_bands: [...]
  geofence: [...]
```

Gazebo、UE和QGC资产缺一项时可以按能力降级显示，但不得把另一个场景的资产静默拼进来。

### 5.2 三类地图必须隔离

```text
operator_display_map
  -> QGC/UE给用户查看的静态底图，不自动进入规划器

planner_prior_map
  -> 仅known-map任务可读取的先验地图

live_occupancy_map
  -> MID360/FAST-LIO/建图前端实时产生，未知探索只能读取该类地图
```

QGC显示完整Factory二维底图不等于FUEL/RACER获得Factory先验。Profile Validator必须检查
`environment_knowledge=unknown`时`consumes_static_prior_map=false`，并在Run Manifest记录。

### 5.3 地图切换

地图切换只允许在run开始前进行，并同时解析：

- Gazebo world、model path和物理碰撞资产；
- UE project/level和显示坐标变换；
- QGC二维底图、比例尺、边界和图层默认值；
- 起飞区、初始姿态、任务区域、探索边界和高度带；
- Planner/Exploration兼容性、状态源和传感器需求；
- Geofence、Safety和证据合同。

切换地图会生成新的ScenarioProfile、ExperimentProfile和hash。运行中“换地图”只能作为
显示调试，不得改变当前plant或任务坐标；正式切换必须停止run并重新预检。

## 6. QGC二维任务地图

### 6.1 实现原则

保留QGC地图工作流，但使用项目自有`MoSimMapView`和离线Provider。复用QGC/Qt/QML已有的
拖动、缩放、选择、图层和多机标记基础能力，不从零重写地图引擎，也不依赖在线地图服务。

中央显示模式：

```text
UE 3D
2D Mission Map
UE + 2D split view
```

### 6.2 Factory首张二维地图

Factory二维底图从已验收的Factory几何和坐标标定产物生成，不使用任意截图。至少保存：

```text
world_bounds
image_width / image_height
meters_per_pixel
world_origin
world_to_pixel_3x3
gazebo_to_ue_transform_hash
source_scene_hash
calibration_evidence
```

建议同时提供栅格底图和矢量结构层：栅格负责稳定显示，矢量层负责墙体、门、区域和交互命中。

### 6.3 标准图层

| 图层 | 数据来源 | 默认行为 |
| --- | --- | --- |
| 静态结构 | `SceneMapRegistry.qgc_2d` | 常开，只作显示 |
| Geofence/任务边界/高度带 | ScenarioProfile | 常开，可查看不可越权编辑 |
| 起飞点、目标点、航点 | MissionFrame/GoalSet | 按任务显示 |
| 单机/多机位置和朝向 | StateFrame/SwarmStateFrame | 常开，按`vehicle_id`着色 |
| 实际轨迹 | 状态记录器 | 常开，可调长度/全量 |
| 当前/候选轨迹 | TrajectorySet | 默认开启当前轨迹 |
| 点云/占据投影 | live MapFrame | 可选，不替代RViz三维审核 |
| Frontiers | FrontierSet | 仅算法声明能力时显示 |
| Coverage | CoverageFrame | 统一图例和统计边界 |
| 多机分配 | AssignmentFrame | 按owner着色并显示冲突 |
| 编队拓扑 | FormationReference | 编队任务时显示 |
| 故障/告警 | Diagnostics/Fault events | 事件发生时显示 |

图层缺失显示`not_available`，不能用静态示意线或伪造数据填充。

### 6.4 城市和后续地图

Provider接口至少支持：

```text
local_metric_map
  -> Factory、仓库、室内园区；本地米制坐标 + 栅格/矢量资产

georeferenced_offline_map
  -> 城市、园区、室外；GeoTIFF/离线瓦片/GeoJSON + ENU原点
```

城市地图新增时只增加SceneMap注册项、资产包、坐标合同和兼容性证据，不修改
`MoSimMapView`页面结构。经纬度、ENU、Gazebo world和UE world之间的变换必须版本化并校准。

## 7. ExperimentProfile集成

ExperimentProfile至少引用：

```yaml
scenario_profile: factory_l2_v1
scene_map_id: factory_l2
mission_profile: unknown_exploration_fixed64
mission_algorithm_id: fuel_ros1
planner_parameter_set: fuel_factory_fixed64_v1
state_source_profile: fastlio_px4_fused_v1
sensor_profile: sunray150_mid360_v1
controller_profile: px4ctrl_l1_awff_v1
formation_profile: pass_through_single
display_profile: ue_qgc2d_rviz_on_demand_v1
evaluation_profile: exploration_coverage_v1
```

Profile Validator至少拒绝：

- 单机算法配多机车辆数；
- 未知探索算法读取静态先验地图；
- 算法需要的传感器、状态源、frame或轨迹表示缺失；
- 地图边界、出生点、高度带或坐标合同不完整；
- QGC、UE和Gazebo使用不同`map_id`或未校准版本；
- 算法、场景或车辆数超过当前证据等级；
- 多机探索没有namespace、地图共享、分配或最小分离合同。

## 8. GUI消费规则

Model Studio负责选择和生成Profile：

```text
地图 -> 任务类型 -> 车辆数 -> 算法 -> 状态/传感器
     -> 控制链 -> 安全/故障 -> 显示Profile -> 参数集
```

Flight Console只允许选择已发布Profile，或在不改变组合语义的范围内选择已发布的同类Profile。
它显示地图、任务算法、控制器和证据状态，但不直接编辑注册表、ROS topic或launch命令。

AI助手以后可以读取注册表、兼容性、当前地图和算法诊断并提出结构化建议，但仍需人工确认
和Profile Validator复核，不能自行切换地图、算法或发布轨迹。

## 10. 实施顺序与门禁

### M0 Schema与Validator

- 冻结MissionAlgorithmRegistry和SceneMapRegistry JSON Schema；
- 将现有Diff、FUEL、RACER、已知覆盖和Swarm-Formation映射为注册项；
- 对缺失证据的项保持`visible_disabled`；
- 增加Profile兼容性和未知地图泄漏检查。

### M1 Factory二维地图

- 从已验收Factory几何生成栅格底图和矢量结构；
- 固化`world_to_pixel`与现有Gazebo/UE标定hash；
- 用三个非共线点、比例尺、边界和逐机位置验证二维映射；
- 证明显示底图没有进入未知探索算法输入。

### M2 QGC地图页

- 在QGC二次开发源码中实现`MoSimMapView`和本地Provider；
- 完成UE/二维/分屏切换；
- 接入位置、轨迹、目标、frontier、coverage、assignment和formation图层；
- 无对应数据时明确不可用，不显示示意假数据。

### M3 算法切换

- 先验证同一Factory地图下Waypoint、Diff和FUEL的运行前切换；
- 再验证单机FUEL与三机RACER的车辆数/依赖拒绝；
- 再接入已知覆盖和Swarm-Formation；
- 每个组合使用独立Profile、run、hash、日志和指标。

### M4 第二张地图

- 增加一张城市或园区地图；
- 不修改GUI页面，只增加注册项和资产包；
- 通过Gazebo/UE/QGC三端坐标、出生点、边界、算法过滤和运行预检；
- 通过后才证明地图扩展接口成立。

## 11. 完成定义

只有同时满足以下条件，才能宣称平台支持可扩展地图和任务算法切换：

1. GUI算法和地图列表完全由注册表驱动；
2. 新增算法不修改GUI核心代码，只增加注册、Adapter、参数和证据；
3. 新增地图不修改GUI核心代码，只增加资产、变换、Profile和证据；
4. Factory二维地图与Gazebo/UE世界坐标通过可复现校准；
5. 未知探索无法读取operator display map或静态prior map；
6. 运行前切换产生新的Profile/hash，运行中不允许无审计热切换；
7. 禁用项、拒绝原因和证据上限由机器状态驱动；
8. 至少两种任务算法和两张地图通过同一接口运行，才证明扩展能力而非单例特判。
