# MoSim参数、信号、自动调参与运行可观测性详细设计

> 状态：产品与接口设计，2026-07-17。
>
> 本文定义Model Studio自动调参、Flight Console低延迟信号查看、MWORKS实时分析镜像、
> UE/Gazebo链路延迟和所有长操作的进度/取消/恢复合同。算法级调参规则仍以
> `Docs/Design/架构/03_测试调参与证据/调参与参数优化.md`为准。

## 1. 冻结结论

1. Flight Console和MWORKS都能查看同一run的参数与信号；前者是低延迟运行视图，后者是
   可降采样的分析镜像，二者都不进入实时控制链。
2. 自动调参属于Model Studio。Flight Console可以启动已发布调参任务、查看进度和结果，
   但不能在飞行中无门禁地让优化器改控制器参数。
3. 所有耗时操作都进入统一Operation Center。按钮点击后立即返回`operation_id`，持续显示
   真实阶段、已用时间、心跳、超时预算、日志和取消能力。
4. 进度条只能由结构化阶段ACK推进。不能用定时器伪造0至100%，也不能把进程存在当作完成。
5. 同一`request_id`重复点击必须返回同一操作；客户端重启后重新附着，不能启动第二份Gazebo、
   PX4、训练或调参任务。
6. 延迟按源、桥接、传输、队列、应用和渲染分解。UE帧率、接收频率和端到端延迟是不同指标。
7. 任何GUI、MWORKS镜像、绘图、Agent或UE卡顿都不能反压控制链；控制频率按已冻结Profile
   执行，当前50 Hz已验证基线与200 Hz待验证目标分别显示。

## 2. 解决的用户痛点

| 痛点 | 产品解法 |
| --- | --- |
| 点击启动后长时间无反馈 | Operation Center显示当前阶段、elapsed、ETA/预算、心跳和日志 |
| 用户重复点击造成多实例 | 按钮即时锁定、幂等request、服务端单飞锁和重复请求附着 |
| 只知道“失败”，不知道卡在哪 | 子系统级阶段、reason code、建议动作和证据路径 |
| 参数和曲线散落在多个工具 | Signal Registry + Flight Console Inspector + MWORKS Mirror |
| 实时画面卡，但不知道是ROS、桥接还是UE | 分段延迟、频率、丢包、乱序、插值缓冲和FPS |
| 调参靠手工改值、重复启动和整理结果 | Auto Tuning Study、自动矩阵、排行榜、Top-K验证和冻结 |
| GUI关闭后不知道任务是否还在 | Orchestrator持有任务，GUI按operation/run重新附着 |
| 停止后残留Gazebo/PX4/ROS进程 | 停止/清理也显示阶段与残留检查，不在按钮松开时假报完成 |
| 两个GUI或Agent同时操作 | 统一Action API、operation owner、冲突提示和人工接管 |
| 多机只显示整体成功 | 每架飞机单独进度/ACK，团队状态不掩盖partial failure |

## 3. 四个产品表面

### 3.1 Flight Console Live Inspector

面向运行监控，目标是低延迟和快速判断：

- 可搜索的信号树、收藏、单位、当前值、健康和来源；
- 多曲线叠加、左右轴、缩放、暂停、时间窗和事件标记；
- 10至100 Hz输入按显示能力降采样，不改变记录频率；
- 保存“悬停”“8字”“故障恢复”“多机编队”等布局；
- 从曲线异常跳到对应run事件、参数集和结果目录；
- 原生QGC Parameter Editor和MAVLink Inspector保留在高级入口。

### 3.2 MWORKS Live Analysis Mirror

面向比赛展示和模型对照：

- 订阅同一Signal Registry，默认2至10 Hz低频镜像；
- 显示数据源、run、源时间戳、镜像频率、当前数据年龄和镜像延迟；
- 允许勾选变量并与MIL/SIL/generated-C参考曲线并列；
- 实验结束后从低频live mirror切换为完整分辨率离线结果；
- MWORKS阻塞或关闭只降低分析显示状态，不影响Gazebo/PX4/日志。

### 3.3 Model Studio Auto Tuning

面向参数搜索与冻结：

- 参数组、范围、尺度、关联约束和初始安全集；
- 调参集、验证集、场景矩阵、seed和扰动/故障工况；
- 目标函数、硬约束、退化限制和停止条件；
- Grid、Random、LHS、PSO、CMA-ES、Bayesian和局部搜索；
- 预算、并行数、单case超时、总超时和资源配额；
- 实时排行榜、Pareto视图、失败分类、Top-K复核和参数冻结。

### 3.4 Operation Center

两个GUI共享同一后台任务中心，至少显示：

```text
operation_id / request_id / run_id
动作名称与发起者
queued / validating / running / waiting / finalizing / terminal
当前阶段与阶段说明
真实进度或indeterminate
elapsed / ETA / deadline
last heartbeat / stale
可取消 / 不可取消 / 仅可安全停止
逐机与逐子系统状态
最新结构化日志
证据目录与失败建议
```

关闭弹窗不取消操作。窗口重启后按`operation_id`恢复显示。

## 4. Signal Registry与双端查看

每个信号必须注册：

```yaml
signal_id: uav1.tracking.position_error.x
display_name: Position error X
group: controller/tracking
vehicle_id: uav1
source_layer: px4ctrl
source_topic_or_artifact: /uav1/...
frame_id: world
unit: m
value_type: float64
source_rate_hz: 100
record_rate_hz: 100
flight_console_rate_hz: 30
mworks_mirror_rate_hz: 5
freshness_limit_ms: 200
evaluation_allowed: true
writable: false
```

信号至少覆盖：

- PX4/MAVROS模式、位置、速度、姿态、角速度和电池；
- FAST-LIO状态、频率、时间差、协方差和地图健康；
- 规划器目标、轨迹、速度、加速度、jerk、耗时和失败原因；
- 控制器参考、误差、控制量、饱和、积分器、观测器和增强层状态；
- Safety、CBF、FDI、FTC、控制分配和Failsafe；
- Gazebo truth、碰撞、风扰和电机实际效能；
- 多机最小间距、编队误差、任务分配和通信新鲜度；
- UE/RViz/MWORKS显示链路健康、延迟和帧率。

高频信号使用环形缓冲、服务端降采样和批量传输。GUI隐藏曲线不应继续请求全频绘图数据；
记录器仍按Profile保存原始数据。慢消费者只能丢显示帧，不能阻塞生产者。

## 5. 参数查看与修改权限

参数分为：

| 类型 | 查看 | 修改规则 |
| --- | --- | --- |
| PX4原生参数 | QGC与两个Inspector | 复用QGC Parameter Editor，增加白名单、ACK和回滚 |
| Controller/Planner运行参数 | 两个GUI只读查看 | 从发布ParameterSet派生新版本，默认下次run生效 |
| 允许在线调节参数 | Flight Console高级模式 | 仅Profile白名单、范围检查、飞行状态门禁和物理ACK |
| MWORKS模型参数 | Model Studio/MWORKS | 修改后产生新模型/参数hash并重新走MIL/SIL/codegen |
| truth与诊断量 | 只读 | 永远不可作为参数写回 |

MWORKS Live Mirror默认只读。两个GUI不得同时成为参数写入权威；所有修改都生成
`ParameterChangeTransaction`并经过Orchestrator。

## 6. 自动调参操作合同

### 6.1 TuningStudy

```yaml
study_id: tuning_001
base_profile_hash: sha256:...
parameter_space_id: px4ctrl_l1_awff_v1
tuning_scenarios: [hover, figure8, wind]
validation_scenarios: [figure8_holdout, mismatch_holdout]
optimizer: bayesian
budget: 100
parallelism: 8
seed: 42
objective: weighted_rmse_energy
hard_constraints: [attitude, saturation, landing]
stop_policy: no_gain_or_budget
runtime_ladder: [mworks_mil, sil, gazebo_top_k]
```

### 6.2 用户流程

```text
选择基线Profile
-> 选择参数与范围
-> 选择调参集/验证集和目标
-> 搜索空间预检
-> 估算case数量、时间和资源
-> 开始Study
-> 实时排行榜与失败分类
-> Top-K进入SIL/Gazebo
-> 独立验证集复核
-> 人工接受或拒绝
-> 生成不可变ParameterSet与新Profile
```

调参结果永不自动替换当前ParameterSet，也不自动切换当前Profile。即使Top-K全部通过，仍必须
由用户显式点击`接受参数集`；拒绝或关闭页面不会改变当前运行配置。

按钮：

```text
创建调参任务 | 预检 | 开始 | 暂停 | 恢复 | 安全停止
打开实时曲线 | 查看排行榜 | 验证Top-K | 接受参数集 | 回滚
```

Agent调用相同Action，不拥有额外权限。验证集不得参与搜索目标。飞行中的在线自适应控制器
是控制算法本身，不等于平台自动调参。

## 7. 长操作与真实进度

### 7.1 OperationProgress Schema

```yaml
operation_id: op_001
request_id: req_001
run_id: run_001
action: start_gazebo
owner: flight_console
status: running
stage_id: wait_mavros
stage_label: Waiting for MAVROS connection
stage_index: 4
stage_count: 9
progress_mode: determinate
progress_percent: 42
created_at: 0
started_at: 0
elapsed_ms: 18000
eta_ms: 26000
deadline_ms: 90000
last_heartbeat_at: 0
cancel_mode: safe_cancel
retry_mode: attach_or_retry_failed_stage
queue_position: null
vehicle_progress: {}
reason_code: null
log_tail: []
```

状态机：

```text
queued
  -> validating
  -> reserving_resources
  -> executing
  -> waiting_readiness
  -> finalizing
  -> completed

任一非终态
  -> cancel_requested -> cancelling -> cancelled
  -> degraded
  -> failed
  -> timed_out
```

### 7.2 启动阶段示例

`start_gazebo`不能是一个黑盒按钮，至少拆为：

```text
1 Profile与资源预检
2 获取runtime单飞锁
3 启动ROS master / 基础环境
4 加载Factory Gazebo world
5 spawn Sunray/PX4
6 等待MAVROS connected
7 等待传感器、状态源和控制器ready
8 等待规划器/任务Adapter ready
9 绑定UE/RViz/记录器并完成ready摘要
```

多机阶段按`vehicle_id`显示，例如`uav1 ready / uav2 waiting MAVROS / uav3 failed sensor`。
团队进度不能用平均值掩盖失败成员。

### 7.3 百分比规则

- 百分比由Launch Plan阶段权重和真实ACK计算，必须单调不回退；
- 不知道内部完成度的阶段显示spinner、阶段名和elapsed，不伪造每秒增长；
- `99%`不能表示未知等待；等待readiness必须显示具体依赖和deadline；
- ETA优先使用同一Profile/机器历史P50/P95，没有历史时显示“估算中”；
- 完成只在最终readiness、manifest和证据初始化通过后显示100%；
- 失败保留已完成阶段、失败阶段、日志和重试建议。

### 7.4 防重复点击

按钮行为冻结为：

```text
首次点击
  -> 客户端生成request_id
  -> 立即禁用按钮并显示pending
  -> 服务端返回operation_id
  -> GUI订阅OperationProgress

重复点击/网络重试
  -> 使用相同request_id
  -> 返回同一operation_id和当前状态
  -> 不创建第二个进程或run
```

客户端`busy`只是交互保护，服务端幂等和runtime锁才是最终保护。超时不等于失败；请求超时后
先查询operation，再决定重新附着、重试失败阶段或清理，禁止盲目再启动。

### 7.5 取消、停止和清理

- 预检/排队阶段可以立即取消；
- Gazebo/PX4启动中执行有序取消和残留检查；
- airborne后普通“取消”转换为悬停/降落/安全停止，不直接杀进程；
- `stop_run`显示降落、disarm、日志flush、显示detach、进程退出和残留检查；
- 清理未完成时不能显示“已停止”，也不能开放新的冲突run。
- ROS、UE和RViz等可幂等基础设施阶段最多自动重试一次；两次尝试都写入同一operation事件流；
- codegen、自动调参和任务执行失败后不自动重跑，等待用户查看原因并显式重试；
- airborne后禁止自动重启任务、控制器或runtime，恢复动作只能进入悬停、降落或安全停止。

### 7.6 加载动画与交互

- 点击后100 ms内按钮切换为“提交中”并显示spinner，服务端目标2秒内返回operation；
- 有真实百分比时显示0至100%进度条，无内部百分比时显示不定进度动画和阶段计数；
- 紧凑状态条持续显示`当前阶段 | elapsed | ETA/预算`，点击展开完整Operation Center；
- 长操作不使用阻塞模态窗口，用户可以查看地图、日志和其他只读页面；
- 当前动作按钮改为“查看进度”，允许的取消/安全停止单独显示，其他冲突按钮禁用并说明原因；
- 完成后进度条保留短暂成功状态并进入事件时间线，失败状态保持到用户查看或确认；
- 同一操作在Model Studio、Flight Console和Agent中显示一致状态，不各自播放独立动画。

## 8. 延迟与显示健康

### 8.0 同run系统测量矩阵

每次正式测试必须在同一个`run_id`和共同稳态窗口内同时记录，而不是分别截图后拼接：

| 链路 | 必测指标 | 第一版采集入口 |
| --- | --- | --- |
| MWORKS <-> ROS Adapter | rate、RTT、command age、jitter、loss、payload/wire bandwidth | RT1序号与单调时钟计数器 |
| MAVROS <-> PX4 | setpoint/heartbeat rate、序号丢失、command age、bandwidth | MAVROS diagnostics + MAVLink序号 |
| Gazebo运行时 | real-time factor、physics/sensor rate、CPU、内存 | Gazebo metrics/stats + OS进程计数器 |
| Gazebo/ROS -> UE | source/receive rate、pose age、RTT、loss、bandwidth | DisplayFrame序号 + UE接收ACK |
| UE渲染 | FPS、Frame/Game/Draw/GPU ms、hitch | `stat fps/unit/net/startfile` |
| ROS -> RViz | topic rate、delay、bandwidth、queue drop、display FPS | `rostopic hz/bw/delay` + RViz状态 |
| PX4 -> QGC | telemetry rate、message loss、RTT、bandwidth、UI FPS | MAVLink Inspector/Link statistics |
| 主机资源 | CPU/GPU/内存/网卡/磁盘 | Windows与WSL系统计数器 |

跨Windows/WSL/UE时钟域没有同步证据时，只报告RTT、各端本地队列耗时和数据年龄；不得用
RTT/2冒充单向延迟。带宽同时报告应用payload与接口wire/总字节，避免把ROS序列化、UDP/IP、
MAVLink或其他并发流量隐藏掉。短预检、60秒稳态和300秒长测采用共同Schema。

### 8.1 时间戳链

```text
t_source       Gazebo/PX4/ROS状态产生
t_bridge_in    Bridge接收
t_bridge_out   Bridge发送
t_ue_receive   UE接收
t_ue_apply     Actor应用
t_present_ack  可获得时的渲染提交/呈现回执
```

指标：

```text
source_to_bridge_ms
bridge_queue_ms
transport_ms
ue_queue_apply_ms
source_to_apply_ms
estimated_present_age_ms
update_rate_hz
sequence_gap_ratio
out_of_order_count
interpolation_buffer_ms
ue_fps
mworks_mirror_age_ms
```

Windows、WSL和UE跨clock domain时，单向延迟只有经过时钟偏移校准才可宣称。未校准时显示
本地队列延迟、RTT和`one_way_unavailable(clock_unsynchronized)`，不能用RTT/2冒充精确单向
延迟。GPU真正present时间不可获得时必须标记`estimated`。

### 8.2 Flight Console状态条

```text
Runtime 100 Hz | FAST-LIO 20 Hz | UE 60 Hz
UE latency 24 ms P50 / 41 ms P95 | loss 0.02% | buffer 16 ms
MWORKS mirror 5 Hz | age 380 ms
```

阈值由DisplayProfile配置。超过阈值显示warning/stale，但显示故障不能自动终止飞行；只有
Profile明确把显示作为人工审核门禁时，run结束后进入`review_required`。

## 9. 其他必须解决的产品问题

1. **资源预检**：启动前显示CPU、GPU、内存、磁盘、端口、WSL、许可证和runtime锁。
2. **操作所有权**：两个GUI和Agent显示当前owner；高风险接管需要确认和审计。
3. **后台通知**：长操作完成、失败、超时或需要审核时发送桌面通知和项目稀疏邮件。
4. **崩溃恢复**：GUI或Orchestrator重启后识别attached/degraded/orphaned，不自动重复执行。
5. **错误可解释性**：显示reason code、用户语言说明、相关子系统、日志和下一步，不只弹“失败”。
6. **数据过载**：曲线数量、采样率和时间窗有预算；慢界面丢显示帧，记录链保持完整。
7. **配置未保存**：切换Profile、地图、控制器或关闭窗口前提示草稿差异，不覆盖发布版本。
8. **部分成功**：多机、注入、显示和训练矩阵都报告逐项结果，不能整体绿色掩盖失败。
9. **权限模式**：普通模式只显示安全操作；高级模式增加诊断，不绕过服务端门禁。
10. **证据一致性**：进度、曲线、延迟、参数变化和结果都绑定同一run/profile/artifact hash。
11. **显示会话批量清理**：提供关闭全部MoSim RViz会话的操作，逐会话ACK并检查残留；不得误关
    非MoSim所有的RViz进程。
12. **媒体录制显式化**：UE视频默认不录制，开始/停止按钮、录制时长、文件路径、磁盘余量、
    flush和失败状态必须可见；录像不进入控制链。

## 10. 实施顺序

### O0 Schema与回放fixture

- 冻结Signal Registry、OperationProgress、TuningStudy和LatencyFrame；
- 用录制数据验证双Inspector、进度恢复和延迟显示；
- 不启动Gazebo即可完成GUI逻辑测试。

### O1 Operation Center

- 先接`prepare_run/start_run/stop_run`真实阶段；
- 验证重复点击、客户端重启、请求超时、取消和残留清理；
- 再覆盖codegen、训练、调参和结果分析。

### O2 Flight Console Live Inspector

- 复用QGC Fact System、MAVLink Inspector和图表能力；
- 增加ROS/控制器/规划器/安全/故障信号Adapter；
- 完成布局保存、事件标记和导出。

### O3 MWORKS Live Analysis Mirror

- 以低频同源信号进入Syslab APP/结果显示；
- 显示mirror标识、数据年龄和延迟；
- 完成live到离线全量结果切换。

### O4 延迟闭环

- 补齐发送、接收、应用和可用的present时间戳；
- 完成clock-domain校准、P50/P95/Max、丢包和stale告警；
- 用同一run验证Flight Console、UE和MWORKS显示一致。

### O5 Auto Tuning

- 将现有调参规范映射为TuningStudy和Action API；
- 先跑MWORKS MIL/SIL，再开放Gazebo Top-K；
- 完成暂停恢复、预算、排行榜、验证集和ParameterSet冻结。

## 11. 完成定义

只有同时满足以下条件，才能宣称本设计完成实现：

1. 所有长操作在2秒内出现operation和当前阶段，不存在一分钟无反馈；
2. 连续点击同一按钮不会产生第二个run、Gazebo、PX4、训练或调参进程；
3. 进度只由真实ACK推进，失败阶段、elapsed、deadline和日志可见；
4. GUI重启后可以附着到原操作，取消和停止完成残留检查；
5. Flight Console和MWORKS显示同一Signal Registry且带run/profile/time；
6. UE链路显示分段延迟、P50/P95、频率、丢包、插值缓冲和clock状态；
7. 自动调参完成搜索、Top-K验证、独立验证集和不可变ParameterSet冻结；
8. MWORKS镜像或任一显示端卡顿对控制和原始日志的阻塞为零；
9. 多机、矩阵和注入的partial failure逐项可见；
10. 文档、源码、测试、运行证据、提交和推送满足项目closeout门禁。
