# 模型库全量重构审核方案

状态：待审核

范围：`Models/` 下的全部目录、Modelica 包、模型源、资源文件和恢复副本。
本文件只描述当前快照和建议的重构目标；不移动、不删除、不修改任何模型源。

## 1. 审核结论

`Models/` 应当保持一个正式 Modelica 根：
`Models/MoSimQuadrotorModel/package.mo`。整个库不能再按控制器、场景、
图形化入口或临时排障需要增加并列根。

当前根下有八个顶层领域：`Common`、`Parameters`、`Vehicle`、`Control`、
`Guidance`、`Experiment`、`Visualization`、`Deployment`。这些顶层领域本身合理；
问题在于很多模型按实现历史、显示形式或一次性诊断而非责任边界归类。重构应保留
一个根和大部分现有领域名称，只增加确有独立语义的 `Environment`。

`Models/MoSimQuadrotorModel_backup/crash_recovery/...` 是恢复快照，而不是第二个
模型库。它必须从 `Models/` 的可发现范围退出，不能与正式根并存供 MWORKS 扫描。

## 2. 当前结构事实

| 项目 | 当前状态 | 结构含义 |
|---|---|---|
| 正式 Modelica 根 | `MoSimQuadrotorModel` | 唯一允许加载的项目根 |
| 正式 `.mo` 文件 | 579 | 包含根 `package.mo` |
| 恢复快照 `.mo` 文件 | 578 | 位于 `MoSimQuadrotorModel_backup/crash_recovery/` |
| 顶层最大域 | `Control` 235、`Experiment` 227 个 `.mo` 文件 | 需要首先消除混合责任 |
| 跨域组合 | `Guidance` 有整机与闭环模型；`Visualization` 有大量 smoke | 应进入 `Experiment` 的组合/诊断层 |
| 资源 | 机体网格、地图网格、硬件图片混放在 `Vehicle.Resources` | 应按资产所有权集中管理 |
| 包容器 | 多个 `package.mo` 内嵌大量模型实现 | 目录、命名空间和业务模型未分离 |

已观察到的边界问题：

- `Guidance.Planning.OpenBlocksLinearMPCVehicle` 等模型直接组装 `Vehicle` 和
  `Control`，应视为规划试验组合，而不是 Guidance 算法。
- `Visualization.Diagnostics` 的 Factory trace smoke 是联线排障入口，不是通用
  可视化组件。
- `Common.Models` 同时含通用 trace block 与 MCP/trace smoke，后者不应留在基础层。
- `Vehicle.Examples`、`Vehicle.GroundModel`、`Vehicle.Mechanics`、`Vehicle.Blocks`
  等包容器内存在大段实现，需要拆成独立的公开类文件。
- `Control.Baselines`、`Control.Implementations`、`Control.Adapters`、
  `Control.Bridges` 同时表达算法、表示形式、接口边界和生命周期，分类轴互相交叉。

## 3. 目标结构

```text
MoSimQuadrotorModel/
  Common/                    # 类型、函数、限幅、无业务语义复用件
  Parameters/                # Profiles、Records、Provenance
  Environment/               # Maps、Obstacles、Frames、场景真值
  Vehicle/                   # Assembly、Mechanics、Dynamics、Actuation、Sensing、Visual
  Control/                   # Contracts、Algorithms、Realizations、Integration、Allocation、Legacy
  Guidance/                  # References、Planning、Formation、Safety
  Experiment/                # Fixtures、Formal、Graphical、Reference、Scenarios、Diagnostics、Legacy
  Visualization/             # Components、Scenes、MapReview
  Deployment/                # Runtime、Interfaces、Validation
  Resources/                 # 非 Modelica package 的资产目录
```

顶层 `package.order` 应按依赖方向排序：
`Common -> Parameters -> Environment -> Vehicle/Control/Guidance -> Experiment -> Visualization/Deployment`。
排序只服务浏览和依赖阅读，不是运行或验收声明。

### 3.1 依赖方向

```text
Common, Parameters
        |
        +--> Environment
        +--> Vehicle
        +--> Control
        +--> Guidance
                 |
                 +--> Experiment
                          +--> Visualization
                          +--> Deployment
```

- `Common` 和 `Parameters` 不依赖上层领域。
- `Vehicle` 不依赖 `Control`、`Guidance`、`Experiment`、`Visualization` 或 `Deployment`。
- `Control` 只面向稳定 contract，不直接依赖整机试验。
- `Guidance` 只输出参考、规划和安全结果，不装配控制器或整机。
- `Experiment` 是唯一常规的跨领域整机组合层。
- `Visualization` 只负责显示；会改变控制、状态或接线的 smoke/harness 属于
  `Experiment.Diagnostics`。
- `Deployment` 是下游实时/代码生成边界，不能反向成为领域模型的依赖。

## 4. 各领域重构规则

| 当前域 | 目标子域 | 处理规则 |
|---|---|---|
| `Common` | `Types`、`Functions`、`Limits`、`Utilities` | 保留纯复用件；MCP、trace replay、smoke 移至 `Experiment.Diagnostics` 或 `Fixtures`。 |
| `Parameters` | `Profiles`、`Records`、`Provenance` | 参数来源与参数值分离；每个公开 record 独立文件。 |
| 新增 `Environment` | `Maps`、`Obstacles`、`Frames` | 接管 Factory/OpenBlocks/走廊等场景真值；不接管机体接触力学。 |
| `Vehicle` | `Assembly`、`Mechanics`、`Dynamics`、`Actuation`、`Sensing`、`Visual` | 只保留飞行器物理本体；整机示例、诊断和世界地图退出本域。 |
| `Control` | `Contracts`、`Algorithms`、`Realizations`、`Integration`、`Allocation`、`Legacy` | `Interfaces` 改为 `Contracts`；`Adapters` 与 `Bridges` 按边界职责归入 `Integration`；`Baselines` 拆分。 |
| `Guidance` | `References`、`Planning`、`Formation`、`Safety` | 仅保留可复用算法；全机、闭环、地图审阅模型移到试验或显示域。 |
| `Experiment` | `Fixtures`、`Formal`、`Graphical`、`Reference`、`Scenarios`、`Diagnostics`、`Legacy` | 取消 `Runners` 中间层；执行入口按使用目的直接归类。 |
| `Visualization` | `Components`、`Scenes`、`MapReview` | 只保留显示构件和场景审阅；诊断闭环模型退出。 |
| `Deployment` | `Runtime`、`Interfaces`、`Validation` | 保留 MWORKS Live/C 外部 I/O/代码生成；RT0/RT1 probe 明确为部署验证。 |

### 4.1 `Control` 的具体准则

```text
Control/
  Contracts/                 # Partial*Controller 和稳定端口约定
  Algorithms/                # PID、鲁棒、几何、优化、学习、滑模等控制律
  Realizations/              # Equation、Sysblock、Graphical、CFunction 控制器核心
  Integration/               # Adapters、Mappers、Equation bridges
  Allocation/                # 姿态/推力/力矩至执行器命令
  Legacy/                    # 必须保留加载能力的旧图形示例
```

真实 AWFF/PID 等控制律进入 `Algorithms`；`OfflineWrenchController` 等只用于
确定性边界的夹具进入 `Experiment.Fixtures.Controllers`。`P4`、`G5`、`P10` 等
阶段代号不作为新的规范 FQN，保留在 `Documentation`、provenance 或 legacy 名称中。

### 4.2 `Experiment` 的具体准则

```text
Experiment/
  Fixtures/                  # WholeAircraft、Controllers、Modules、TraceSources
  Formal/                    # 当前正式可比较控制器入口
  Graphical/                 # 当前图形化整机入口
  Reference/Golden/          # Golden 回归与参考链路
  Scenarios/                 # Planning、Robustness、Faults、Formation
  Diagnostics/               # Integration、Plant、Trace、Visualization
  Legacy/                    # 历史 direct-Sysblock、固定输入、旧 Example
```

`Runners` 应移除。它描述“如何运行”，而不是审阅者要打开的对象；`FormalWrenchRunnerBase`
一类复用整机骨架进入 `Fixtures.WholeAircraft`，正式控制器入口直接进入 `Formal`。
`Golden` 是参考地位，不是 runner 类型。`Experimental` 也不是稳定目录轴，应按模型
实际用途归入候选正式入口或诊断。

### 4.3 `Guidance`、`Vehicle` 与 `Visualization`

- `Guidance.References` 只保留 Hover、Figure8、Spiral、Step、quintic 等参考源。
  Wind、motor fault、parameter mismatch 是试验注入或环境扰动，不与参考轨迹混放。
- `Guidance.Planning` 保留规划器、平滑器、CBF 和规划输出；所有
  `*Vehicle`、`*ClosedLoop`、`*MapAudit` 移至 `Experiment.Scenarios`。
- `Vehicle.GroundModel.TouchModel` 是机体接触/力学件，可留在 `Vehicle.Mechanics`
  的地面接触子域；地图、障碍和世界坐标不属于 Vehicle。
- `Vehicle.Examples.Example1/2/3` 为整机可执行旧示例，迁入
  `Experiment.Legacy.OfficialExamples`。
- `Visualization.Diagnostics.FactoryTraceIso*` 和 `Visualization.Scenarios.*Smoke`
  迁入 `Experiment.Diagnostics.Visualization` 或 `Experiment.Legacy`；显示组件本身留在
  `Visualization`。

## 5. 资源、包文件与命名规则

### 5.1 资源目录

```text
Resources/
  Vehicle/Geometry/          # 机体、旋翼、视觉外壳网格
  Environment/Maps/          # Factory、OpenBlocks、障碍、地形
  Hardware/Images/           # GPS、ESC、ORIN、V6X、电池等图标
```

`Resources/` 不创建 `package.mo`。资源转移必须在同一提交中更新所有
`modelica://MoSimQuadrotorModel/...` URI，并在 MWORKS 中审阅渲染结果。

### 5.2 文件与 FQN

- `package.mo` 只放包声明、简短文档、注释、图标和可控的兼容声明；不放算法、方程、
  大型图形或多个业务类。
- 每个公开 `model`、`block`、`record`、`function` 使用与类同名的独立 `.mo` 文件。
- `package.order` 必须与实际公开子项一致，且按稳定浏览顺序维护。
- 名称采用 `用途 + 对象 + 算法/边界 + 场景`；`Smoke`、`Probe`、`Harness`、
  `Diagnostic` 只允许出现在诊断/验证目录。

## 6. Legacy、Archive 与恢复副本

| 状态 | 位置 | 规则 |
|---|---|---|
| 当前可复用 | 正式领域包 | 正常可见、受 FQN 契约约束 |
| 需加载复现的旧模型 | 所属领域的 `Legacy/` | `__MWORKS(hide=true)`，保留来源说明 |
| 真正冻结退出的源码/恢复副本 | 外部 `E:\刘致远18001500226\MoSim_Archive` | SHA-256、原仓库相对路径、归档说明、原址 tombstone |
| 结果、图表、原始数据 | `Results/` | 不随模型源码目录重构移动 |

不创建 `MoSimQuadrotorModel.Archive`，也不创建全库杂物桶 `Archive/`。归档是
生命周期状态，不是领域模型。

## 7. 迁移步骤

1. 冻结现状：为所有正式 FQN、资源 URI、配置入口、脚本引用建立清单和哈希。
2. 隔离写入：当前模型树存在大量未提交改动；全库迁移仅在独立工作树执行。
3. 建立基础层：抽离 `Common` smoke、整理 `Parameters`、建立 `Environment` 和
   顶层 `Resources`。
4. 整理领域层：依次处理 `Vehicle`、`Control`、`Guidance`，先消除反向/横向组合。
5. 整理下游层：重构 `Experiment`、`Visualization`、`Deployment`，取消 `Runners`。
6. 更新所有当前配置、脚本、入口索引、用户文档和 `package.order`；历史报告保留旧 FQN
   并附迁移对照，不篡改历史证据。
7. 在依赖审计完成后，将恢复副本移出 `Models/`。不以名称、日期或目录大小直接归档。

兼容别名只能用于无法与本次迁移同批更新的外部依赖，必须隐藏、登记到期时间和删除
条件；最终结构不保留 `Runners` 空壳或永久兼容根。

## 8. 验收门槛

- 静态：所有当前 FQN、配置入口、脚本和资源 URI 均可解析；当前源中不存在被废弃的
  命名空间引用。
- 包：每个 `package.order` 与物理子项一致；不存在第二个可加载项目根。
- MWORKS：先对所有活跃入口执行 `check_model`，再运行代表性正式、Golden、图形化、
  规划、故障、编队和部署验证模型。
- 行为：纯结构迁移必须以重构前后原始结果序列比较验证，不把静态检查或截图写成
  闭环、实时或部署验收。
- 图形：所有资源 URI 在 MWORKS 图形审阅中非空、无错误链接；视觉检查与仿真结果
  分别记录。

## 9. 审核决策

请审核以下架构决策后再开始迁移：

1. 保持一个正式根，并把恢复副本移出 `Models/`。
2. 新增 `Environment`，把世界/地图从 `Vehicle` 中剥离。
3. `Experiment` 取消 `Runners`，成为唯一常规跨域组合层。
4. `Guidance`、`Visualization` 和 `Common` 退出整机 smoke/闭环职责。
5. 所有 `package.mo` 无业务实现化，公开类一类一文件。
6. 不在 Modelica 根内设置 `Archive`；以 `Legacy` 和外部可验证归档区分状态。
