# MoSim需求总览

> 状态：当前需求入口，2026-06-24。
>
> 本文只回答“MoSim准备实现哪些能力、优先级是什么、验收看什么”。
> 架构、接口、代码、参数、启动命令和实验流程由后续设计与工作流文档负责。

## 1. 需求来源与边界

MoSim面向A8四旋翼赛题，核心目标是基于MWORKS完成四旋翼控制系统建模、
仿真、优化、代码生成和工程闭环验证。项目不是通用机器人导航栈，也不是
只复现某一个定位/规划/集群仓库。控制算法设计与验证是主线，感知、规划、集群、
UE/前端和自动评估是支撑完整系统展示与证据闭环的能力。

需求来源分为：

```text
官方赛题需求：
  四旋翼位姿控制、控制算法优化、MWORKS建模仿真、指标对比、
  鲁棒性验证、多机编队、报告和交付。

项目扩展需求：
  Sunray/PX4/Gazebo工程闭环、MID360/FAST-LIO定位评价、Diff-Planner规划、
  Diff-Planner swarm三机集群、EGO/EGO-Swarm参考对照、UE/前端实验平台、
  真机对标和代码生成部署路线。
```

工程任务和答辩口径必须同时成立。SLAM、规划、集群、UE/前端不是“可忽略的
旁路”，它们本身也是agent需要完成、验证和维护的工程模块；但在赛题叙事和
最终验收中，它们必须接回MWORKS控制系统建模、代码生成、部署验证和报告证据
闭环，不能变成脱离MWORKS主线的通用机器人导航项目。

当前阶段强调“对标真机”，不是宣称已经完成真机部署。对标真机的含义是：

```text
机型、传感器、飞控接口、控制频率、日志、参数Profile和C++/生成代码路径
尽量贴近后续真机；但当前验收仍以MWORKS、PX4/MAVROS、Gazebo、RViz和UE
等仿真/展示证据为主。
```

## 2. 需求优先级

| 优先级 | 含义 |
| --- | --- |
| MUST | 当前比赛主线必须完成或必须明确冻结边界 |
| SHOULD | 强烈建议完成，能显著增强作品完整性和说服力 |
| COULD | 可作为增强项，取决于时间和前置门禁 |
| RESEARCH | 研究候选或远期路线，只记录需求，不承诺第一阶段实现 |

每条需求进入实现前，必须进一步拆成任务卡：

```text
需求ID:
名称:
类别:
优先级:
阶段:
目标:
输入:
输出:
验收:
对应赛题价值:
依赖:
禁止声明:
```

需求状态不得只靠优先级表达。后续任务和报告必须为每条进入实施的需求补齐：

```text
status:
  BACKLOG / DESIGNED / IMPLEMENTED / MEASURED / ACCEPTED

phase:
  最小闭环 / 控制器族 / MWORKS代码生成 / 规划集群 / 展示交付

evidence:
  结果目录、日志、指标、截图、视频、模型hash、代码hash或阻塞记录
```

### 6.7 历史控制器批次边界

> 下文 G9、G9.5、G9.6 和 G11 是历史研究批次标签，只保留候选范围和证据追溯，
> 不定义当前 G1-G7 的执行顺序。当前 46 条路线审计、47 个目标 Profile 的原子迁移和
> 实验收敛以 `Docs/Workflows/mainline_operations_board.md` 与
> `Docs/Workflows/controller_evidence_closeout.md`、
> `架构/01_控制器平台/MWORKS控制器关系与组合架构.md` 为准。

控制器需求只表示候选范围，不表示一次性全部实现。以下为历史批次冻结口径：

```text
先复现两篇高性能/鲁棒控制论文，验证控制效果是否真实提升；
再完成增强层矩阵；
再让所有进入implemented/accepted的控制器和增强组合走完MWORKS/codegen闭环；
最后再考虑UE真值地图、Gazebo地图一致性和UE/QGC展示集成。
```

G11不冻结单一“最佳控制器栈”。G11的目标是把每个有价值的控制器或控制器+
增强组合都形成可复现的模型到代码闭环；最终展示或比赛使用哪个组合，由后续
指标矩阵和人工审核决定。

| 批次 | 控制器/模块 | 目标 |
| --- | --- | --- |
| 第一批必须实做 | px4ctrl、官方PID、SE3 Basic | 证明ATTITUDE_THRUST模板和MWORKS Golden Slice |
| G9首批长任务 | 官方PID、SE3 Basic、DFBC、SMC、INDI/PID-INDI、NMPC | 形成控制器族替换验证和UI-ready工程接口，不要求完整UI |
| G9.5/G9.6论文复现 | 高性能名义DFBC/NMPC对照、抗风鲁棒DFBC | 先看是否能把轨迹跟踪精度显著做上去，再决定后续增强和codegen工作量 |
| G10增强层矩阵 | DOB/ESO、L1/AWFF、INDI标准增强、安全过滤、故障分配、参数调度、NN/Fuzzy补偿候选 | 作为可组合增强，不掩盖基准控制问题；每一类关键增强至少形成一个可门禁实现 |
| G11全控制器代码生成闭环 | G9/G9.5/G9.6/G10中进入implemented或accepted的控制器和增强组合 | 全部按MWORKS模型、生成C/C++、离线一致性、ROS/Sunray回灌和Gazebo回归验收 |
| 后置展示与地图 | UE真值地图导入/对齐、UE渲染、QGC二次开发界面和UE集成 | 在控制器和codegen闭环稳定后推进，不反向阻塞当前控制器主线 |
| 研究候选 | Fuzzy、NN/RBF、RL、mu-synthesis、Tube MPC | 先做规格和链路定位，不承诺第一阶段闭环 |

## 18. 需求到架构和任务的映射原则

需求文档是项目能力源头。后续文档职责如下：

```text
赛题.md
  -> 官方要求和答辩口径来源。

需求.md
  -> MoSim准备实现哪些能力、优先级、验收口径。

架构.md
  -> 需求如何映射成系统分层、模块关系和当前路线。

架构/00_架构与任务/任务路线图.md
  -> 需求如何拆成S0-S12能力块、Goal、后置分支和验收门禁。

架构/00_架构与任务/系统集成接口与编排.md
  -> 需求如何落到Profile、Orchestrator、Launch Plan和跨模块接口。

专题规范
  -> 具体接口、模型、参数、代码生成、运行门禁和实验细节。
```

禁止：

```text
把需求清单当成已实现清单；
把RESEARCH需求包装成当前完成项；
把规划器或展示功能包装成控制器创新；
把SLAM、规划或集群任务当成不需要agent实现的旁路；
把SLAM、规划或集群成果脱离MWORKS/codegen/部署验证闭环单独宣称项目主线完成；
把单次仿真截图替代统一指标；
把Gazebo truth静默混入定位后宣称FAST-LIO闭环；
把Python临时脚本长期作为正式控制关键路径。
```
