# 04 接口数据契约与时钟频率

Status: source design, 2026-06-10.

## 1. Contract Principle

MoSim modules communicate through typed contracts, not through hidden access to
each other's internal state.

Every runtime payload should carry:

```text
run_id
timestamp
clock_domain
frame_id
source
authority
validity
backend
```

## 2. RunState

```yaml
RunState:
  run_id: string
  scenario_id: string
  scene_id: string
  map_id: string
  vehicle_id: string
  controller_id: string
  planner_id: string
  sensor_profile_id: string
  localization_backend: string
  flight_control_backend: string
  clock_domain: string
  status: initialized | running | completed | blocked | failed
```

Multi-UAV runs add a swarm-level state and per-member identity. These fields
are required before any formation run can be accepted:

```yaml
SwarmRunState:
  run_id: string
  swarm_id: string
  scenario_id: string
  formation_id: string
  uav_count: integer
  clock_domain: string
  formation_route: leader_follower | virtual_structure | decentralized
  status: initialized | running | completed | blocked | failed
```

```yaml
UavMember:
  run_id: string
  swarm_id: string
  uav_id: string
  role: leader | follower | spare | observer
  vehicle_profile_id: string
  controller_id: string
  flight_control_backend: string
  plant_backend: string
  sensor_profile_id: string
  result_namespace: string
```

## 3. TruthState

```yaml
TruthState:
  timestamp: double
  clock_domain: string
  frame_id: world
  position_m: [x, y, z]
  velocity_mps: [vx, vy, vz]
  attitude_quat_wxyz: [w, x, y, z]
  angular_velocity_radps: [p, q, r]
  source: mworks_plant | replay_truth
  authority: plant_truth
  validity: valid | degraded | invalid
```

TruthState may drive visualization and sensor simulation. It must not be handed
to planner as local-map evidence unless the run is explicitly truth-debug.

    - x_m

## 7. PlannerSetpoint

```yaml
PlannerSetpoint:
  timestamp: double
  clock_domain: string
  frame_id: world
  position_ref_m: [x, y, z]
  velocity_ref_mps: [vx, vy, vz]
  acceleration_ref_mps2: [ax, ay, az]
  yaw_ref_rad: double
  valid: bool
  mode: trajectory | hover | land | return | fallback
  source: planner_adapter | mission_manager | safety_fallback
```

P0 target stream is 20Hz. A backend must define stale-command timeout behavior.

Formation runs use a formation-level reference that is translated into one
`PlannerSetpoint` stream per UAV:

```yaml
FormationReference:
  run_id: string
  swarm_id: string
  formation_id: string
  timestamp: double
  clock_domain: string
  frame_id: world
  route: leader_follower | virtual_structure | decentralized
  members:
    - uav_id: string
      role: leader | follower
      position_ref_m: [x, y, z]
      velocity_ref_mps: [vx, vy, vz]
      acceleration_ref_mps2: [ax, ay, az]
      yaw_ref_rad: double
      valid: bool
      source: formation_manager | safety_fallback
```

FormationReference must not be treated as plant truth or motor command.

## 8. CommandPacket And RuntimeEcho

```yaml
CommandPacket:
  run_id: string
  command_id: string
  command_type: set_scene | set_controller | set_planner | set_fault |
    set_wind | set_sensor_profile | arm | start | pause | stop | land
  requested_by: mosim_studio | ue_console | cli | qgc | automation
  payload: object
  timestamp: double
```

```yaml
RuntimeEcho:
  run_id: string
  command_id: string
  accepted: bool
  reason: string
  active_scene_id: string
  active_controller_id: string
  active_planner_id: string
  active_flight_control_backend: string
  authority_adapter: string
  timestamp: double
```

No frontend may treat a request as active until RuntimeEcho confirms it.

Static command/echo code, schemas, fixtures, and build-readiness checkers may
prove only that a future build-only gate is ready. Build-only readiness is not
Unreal build success, and build success is not runtime command acknowledgment.
Runtime acknowledgment requires a later bounded live probe with authoritative
producer identity, pending-request capture, authoritative echo capture,
request/echo match report, no-pose-overwrite report, false-ack negative report,
and timeout cleanup evidence.

## 8.1 Controller ABI

All controller backends must map to one public controller ABI before they are
connected to ROS2, PX4, generated runtime wrappers, or future Simulink
replacement.

The public shape is:

```text
ControllerInput
  -> state estimate
  -> reference / setpoint
  -> fault state
  -> safety state
  -> parameter profile
  -> ControllerBackend
  -> ControllerOutput
      -> motor command or attitude/thrust command
      -> mode/status/saturation
```

Do not expose MWORKS-only internal variable names as the public runtime
contract. MWORKS, generated C/C++, Simulink, and PX4-compatible adapters must
translate their backend-specific signals into this ABI. The detailed ABI and
migration policy live in:

```text
Docs/Design/14_ROS2正式接入与控制器后端迁移设计.md
```

## 9. Clock And Rate Targets

| Signal | Target | Authority |
|---|---:|---|
| MWORKS solver/control step | >= 100Hz preferred, backend-specific accepted value required | MWORKS |
| planner/setpoint stream | 20Hz | PlannerAdapter / FlightControlAdapter |
| truth state | 20-100Hz | PlantRuntime |
| IMU | 200Hz target | SensorObservationLayer |
| MID-360 baseline LiDAR | 10Hz | SensorObservationLayer |
| enhanced LiDAR | optional 20Hz with evidence | SensorObservationLayer |
| TF / transform stream | >= 20Hz where ROS2 is used | ROS2Bridge |
| FAST-LIO odometry/cloud/path | backend dependent, must be measured | LocalizationAdapter |
| local map | 5-20Hz target, must be measured | LocalMapAdapter |
| UE render/video | visual frame rate, not control evidence | UE5 |

## 10. Frame And Extrinsic Rules

- Keep mechanical mount pose, point-cloud origin, built-in IMU position,
  FAST-LIO extrinsic, and UE raycast frame separate.
- Do not write a mechanical CAD/DAE mount directly into a FAST-LIO extrinsic
  without frame review.
- Every transform used by localization or planning must have a source label.
- If frames are mixed, the run is blocked or debug-only.
