# 14 ROS2 正式接入与控制器后端迁移设计

Status: source design, 2026-06-13.

## 1. Decision

MoSim should use ROS2 as the formal robotics integration layer for the complete
system route.

This does not mean ROS2 owns plant truth or controller correctness. It means
ROS2 becomes the stable runtime surface for:

- TF and frame grounding;
- LiDAR/IMU transport;
- RViz2 review;
- FAST-LIO-family localization;
- 3D local map / occupancy / voxel products;
- planner packages such as EGO-style local replanning;
- bag/topic evidence for robotics claims.

MWORKS remains the current competition and modeling backend. Simulink can later
replace or coexist with MWORKS if both backends obey the same controller ABI,
runtime contracts, scenario manifests, and evidence gates.

## 2. Target Full-System Architecture

```text
Scenario / RunManager
  -> MWORKS or Simulink modeling backend
      -> controller design, plant/reference simulation, model evidence
      -> optional generated C/C++ controller artifact
  -> UE scene/sensor oracle
      -> camera/depth/LiDAR/collision observations
  -> ROS2 bridge
      -> /tf, /tf_static
      -> /mosim/imu
      -> /mosim/lidar_points
      -> /mosim/truth_debug only when explicitly labelled
  -> FAST-LIO / localization backend
      -> odometry, path, registered cloud
  -> local map backend
      -> point cloud / occupancy / ESDF / voxel map
  -> planner backend
      -> trajectory / 20Hz setpoint stream
  -> FlightControlAdapter
      -> one active controller backend
  -> PlantRuntime
      -> truth, sensors, events, metrics
```

The route intentionally separates four things that are easy to confuse:

| Concern | Authority |
|---|---|
| Plant truth | `PlantRuntime`, currently MWORKS-hosted |
| Scene geometry and raycast oracle | UE / MoSimSceneLibrary |
| Robotics middleware and estimator/planner state | ROS2 / RViz2 / FAST-LIO / planner |
| Control authority | `FlightControlAdapter` with exactly one backend per run |

## 3. Current State And Blockers

The current project already has ROS2 design and source/static repair work, but
the accepted live evidence is not enough for a full robotics claim.

Known current boundary:

- ROS2 is ready to integrate as a designed backend.
- The latest accepted source/static work prepares a future
  `camera_init -> map/world/ue_world` grounding probe.
- The current live evidence still lacks a same-run non-fake chain from
  `camera_init` to `map`, `world`, or `ue_world`.
- Therefore planner handoff, closed-loop ROS2 runtime success, and FAST-LIO
  localization acceptance remain blocked until a new live evidence bundle
  proves the chain, topic rates, timestamps, extrinsics, and output quality.

Do not treat visible point clouds, nonzero topics, static launch files, or RViz
display state as localization/planner acceptance.

## 4. Controller Backend Strategy

MoSim must not bind ROS2 directly to MWORKS internal variable names. All
controller backends must pass through a stable controller ABI.

Backends:

| Backend | Role |
|---|---|
| MWORKS-native / Equation controller | Current executable backend for competition and model optimization. |
| Graphical Sysblock controller | Structure and review artifact; should remain behavior-equivalent to the executable controller. |
| Generated C/C++ from MWORKS/Sysblock | Future SIL/HIL/ROS2/PX4-compatible runtime backend after codegen and SIL gates pass. |
| Simulink / Simulink Coder | Future modeling/codegen backend that can replace MWORKS if it emits the same ABI. |
| PX4 Offboard/SITL/HIL | Future flight-control backend when PX4 semantics are in scope. |

Current codegen status:

- The codegen path is proven on the narrow `AWFF_PID_Sysblock_Demo` route.
- That proves API/harness viability, not production readiness for every
  controller.
- The accepted current optimized controller
  `AWFF_LinearMPCOnlineFaultAllocationController_Sysblock` still needs its own
  codegen, compile, runtime smoke, and nonzero/time-varying SIL equivalence gate
  before generated runtime authority can be claimed.

## 5. Controller ABI

The controller ABI is the seam that lets MWORKS, generated C/C++, Simulink, and
future PX4-compatible wrappers share one runtime contract.

### 5.1 Inputs

```yaml
ControllerInput:
  run_id: string
  controller_instance_id: string
  timestamp: double
  dt_s: double
  clock_domain: string
  frame_id: body_or_world_contract_id
  state_estimate:
    position_m: [x, y, z]
    velocity_mps: [vx, vy, vz]
    attitude_quat_wxyz: [w, x, y, z]
    angular_velocity_radps: [p, q, r]
    validity: valid | degraded | invalid
    source: truth_debug | fast_lio | native_estimator | replay
  reference:
    position_ref_m: [x, y, z]
    velocity_ref_mps: [vx, vy, vz]
    acceleration_ref_mps2: [ax, ay, az]
    yaw_ref_rad: double
    mode: trajectory | hover | land | return | fallback
    valid: bool
  fault_state:
    rotor_efficiency: [e0, e1, e2, e3]
    disturbance_label: optional
    validity: valid | degraded | invalid
  safety_state:
    geofence_ok: bool
    collision_margin_m: optional
    estimator_ok: bool
    stale_setpoint: bool
  parameters_ref: string
```

### 5.2 Outputs

```yaml
ControllerOutput:
  run_id: string
  controller_instance_id: string
  timestamp: double
  clock_domain: string
  backend: mworks_equation | mworks_graphical | mworks_codegen_c |
    simulink_codegen_c | px4_offboard | other
  motor_command:
    normalized: [u0, u1, u2, u3]
    omega_ref_radps: optional [w0, w1, w2, w3]
  attitude_command:
    roll_ref_rad: optional
    pitch_ref_rad: optional
    yaw_rate_ref_radps: optional
    thrust_ref_n: optional
  controller_mode: nominal | degraded | fault_allocation | safety_fallback |
    land | return
  saturation:
    any: bool
    per_motor: [bool, bool, bool, bool]
  status:
    accepted: bool
    reason: string
```

### 5.3 Required Runtime Functions

Generated or external controller backends should expose equivalent lifecycle
semantics:

```text
initialize(config)
reset(reset_reason)
step(input) -> output
get_status()
shutdown()
```

The concrete generated C API may still be `Init()` / `Step()` with global input
and output structs. The adapter must map that generated shape into the ABI
above.

## 6. ROS2 Message And Topic Contract

Initial ROS2 integration should expose the following minimum topics:

| Topic | Type / representation | Rate target | Source |
|---|---|---:|---|
| `/tf` | transforms | >=20Hz | ROS2 bridge / estimator |
| `/tf_static` | static transforms | startup + changes | ROS2 bridge |
| `/mosim/imu` | `sensor_msgs/Imu` | 200Hz target | SensorObservationLayer |
| `/mosim/lidar_points` | Livox/MID-360-shaped `PointCloud2` or accepted `CustomMsg` | 10Hz baseline, 20Hz optional with evidence | UE raycast / replay / sensor bridge |
| `/mosim/truth_debug` | debug truth only | 20-100Hz | PlantRuntime |
| `/mosim/localization/odom` | odometry | backend measured | FAST-LIO/localization |
| `/mosim/localization/path` | path | backend measured | FAST-LIO/localization |
| `/mosim/cloud_registered` | registered cloud | backend measured | FAST-LIO |
| `/mosim/local_map/voxels` | `PointCloud2` or `MarkerArray` occupancy/voxel view | 5-20Hz | LocalMapAdapter |
| `/mosim/planner/setpoint` | planner setpoint / trajectory adapter | 20Hz target | PlannerAdapter |
| `/mosim/controller/status` | controller status/echo | 20Hz or event | FlightControlAdapter |

The exact topic names may be namespaced per UAV in multi-UAV runs:

```text
/mosim/uav_001/...
/mosim/uav_002/...
```

## 7. FAST-LIO And Local Map Gate

The correct order is:

```text
1. Publish coherent IMU, LiDAR, TF, and static TF.
2. Verify topic rates, timestamps, frame ids, and extrinsics.
3. Run FAST-LIO or selected localization backend.
4. Verify odometry/path/registered-cloud outputs.
5. Evaluate localization quality against truth where truth is available.
6. Build local 3D point cloud / occupancy / voxel map.
7. Feed planner only through localization/local-map contracts.
```

Stop conditions:

- missing or fake `camera_init -> map/world/ue_world` grounding;
- arbitrary static transforms inserted only to make RViz look connected;
- LiDAR point density too low for the claimed estimator;
- missing per-point timing where the selected FAST-LIO route requires it;
- estimator output is nonzero but truth-error is unacceptable;
- planner consumes global UE truth or MWORKS truth without a debug label.

## 8. Simulink Replacement Policy

Future Simulink replacement is feasible if MoSim treats MWORKS as one backend,
not as the system identity.

Rules:

1. Scenario configs, run manifests, metrics, ROS2 topics, and controller ABI
   must not contain MWORKS-only internal variable names as their public contract.
2. MWORKS and Simulink may each own backend-specific adapters.
3. A Simulink controller becomes accepted only after it passes the same gates:
   compile/codegen where claimed, SIL equivalence, ABI wrapper, runtime smoke,
   and scenario metrics.
4. MWORKS-generated C and Simulink-generated C should both terminate at the same
   `ControllerInput -> ControllerOutput` adapter.
5. Simulink should not be introduced by bypassing existing MWORKS evidence; it
   should be introduced as a comparable backend on the same scenario and
   metric bundle.

## 9. Implementation Sequence

Recommended next execution sequence:

```text
Stage A: freeze ROS2 contracts
  -> topic names, frames, ABI, run manifest fields, evidence bundle schema

Stage B: sensor bridge
  -> publish 10Hz baseline LiDAR, 200Hz IMU target, >=20Hz TF
  -> RViz2 point-cloud and 3D voxel/occupancy preview

Stage C: grounding probe
  -> same-run raw /tf and /tf_static
  -> prove camera_init to map/world/ue_world without fake transforms

Stage D: FAST-LIO
  -> selected backend accepts the exact MoSim LiDAR/IMU messages
  -> odometry/path/cloud_registered
  -> truth-error or quality report

Stage E: local planner
  -> EGO-style local map/planner path
  -> 20Hz setpoint stream
  -> stale/fallback status

Stage F: controller handoff
  -> FlightControlAdapter consumes planner setpoints
  -> MWORKS-native controller remains active backend first
  -> runtime echo and controller traces recorded

Stage G: generated runtime
  -> generate current accepted controller C/C++
  -> compile, runtime smoke, nonzero/time-varying SIL equivalence
  -> wrap generated runtime behind Controller ABI

Stage H: Simulink backend
  -> reproduce ABI and selected scenarios
  -> compare generated/runtime outputs and metrics
```

## 10. Evidence Required Before Claims

| Claim | Minimum evidence |
|---|---|
| ROS2 sensor bridge works | topic list, rates, timestamps, frame ids, sample messages, bag or log bundle |
| RViz point cloud / voxel map works | native RViz2 screenshots plus topic/source evidence |
| FAST-LIO works | IMU/LiDAR/TF inputs, registered cloud, odometry/path, rate/timestamp checks, quality/truth-error report |
| Planner ready | local-map source, odometry source, setpoint trace, stale/fallback behavior, no global-truth shortcut |
| Controller handoff works | selected backend, accepted setpoint input, controller output trace, runtime echo, plant response |
| Generated controller ready | target controller source, generated code hash, compile, runtime smoke, nonzero/time-varying SIL equivalence |
| Simulink replacement ready | same ABI, same scenario config, comparable outputs/metrics, backend-specific adapter evidence |

## 11. Non-Goals For This Design Step

This document does not approve:

- publishing live setpoints into a running controller without a scoped live gate;
- claiming FAST-LIO/localization success from static files or visible RViz alone;
- replacing MWORKS evidence with Simulink claims before Simulink gates pass;
- using ROS2 as plant truth;
- using UE global scene truth directly as planner input;
- treating the PID demo codegen probe as proof for the accepted LinearMPC
  online fault-allocation controller.
