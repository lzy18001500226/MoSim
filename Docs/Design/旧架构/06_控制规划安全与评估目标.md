# 06 控制规划安全与评估目标

Status: source design, 2026-06-10.

## 1. Control Goal

MoSim should support a controller ladder while preserving one stable
FlightControlAdapter contract.

Controller candidates:

- official Tongyuan PID baseline;
- improved PID / AWFF PID with anti-windup, derivative filtering, feedforward,
  and saturation handling as selectable improvements;
- PID-INDI or INDI attitude inner loop;
- linear MPC fallback;
- NMPC outer loop;
- sliding-mode controller candidate for robust attitude or position control;
- fuzzy-control correction or scheduling candidate;
- neural-network residual/disturbance compensation candidate;
- L1-inspired adaptive disturbance compensation;
- safety filtering and fault-aware allocation;
- composite controllers that combine a nominal controller with compensation,
  safety, or allocation reconstruction.

The design should not assume every candidate is implemented or accepted. Each
controller must be evaluated through the same scenario, setpoint, plant, and
evidence contracts.

The official PID baseline is not a competitor to be overwritten. It is the
reference used for scenario coverage, metric comparison, ablation, and fallback
decision making.

## 2. Official PID Baseline Analysis

Baseline analysis is a required system function.

Required baseline scenes:

- hover / steady hold;
- step response for attitude, altitude, or position channels as applicable;
- spiral climb;
- figure-8 trajectory;
- disturbance or perturbation variants selected for robustness comparison.

Required baseline observations:

- control input/output trace;
- position, velocity, attitude, and angular-rate truth trace;
- actuator effort and saturation state;
- tracking error and steady-state error;
- overshoot and settling time where the scenario contains a step-like command;
- RMSE and maximum error for trajectory tracking;
- failure, oscillation, saturation, or sluggish-response notes when observed.

The baseline result should be kept as a labelled reference bundle so optimized
controllers can be compared without changing scenario definitions.

## 3. Sysblock Optimized Controller Route

Optimized controllers should be implemented as MWORKS.Sysblock modules or
Sysblock-compatible model components whenever the task is a formal controller
claim.

Required controller-module behavior:

- keep the same external state/setpoint/control interface as the baseline
  controller or document a typed adapter;
- expose controller id, parameter profile, sample time, and fallback mode;
- produce controller status echo and saturation/failsafe flags;
- support model check, closed-loop simulation, and result export;
- support code-generation or SIL equivalence evidence when generated runtime is
  claimed.

Gazebo deployment of an optimized MWORKS controller must follow this order:

```text
1. Keep the Sunray ROS1/Gazebo baseline as the external plant/acceptance
   environment.
2. Export the target MWORKS/Sysblock controller with GenerateModelCode.
3. Prove generated Init/Step interface, sample time, compile, and SIL
   equivalence against the MWORKS controller model.
4. Wrap generated code behind the same setpoint/state contract used by the
   Sunray baseline.
5. Run takeoff-hover-land first; only after hover passes, run figure-8 and
   spiral.
6. If Gazebo needs retuned parameters, record the delta separately from the
   ideal MWORKS parameter set.
7. If the Gazebo plant exposes parameter mismatch, update the MWORKS plant
   model only through a labelled identification/simulation-fit step.
```

Do not replace this route with a Python behavior-equivalent controller, static
plot, or direct Gazebo actuator fixture when claiming MWORKS controller
deployment.

Interface-first error reduction order:

```text
1. Freeze the current frequency baseline:
   Gazebo physics 1000Hz, Sunray control 200Hz, MAVROS state about 100Hz,
   MID360 IMU 200Hz, MID360 LiDAR 10Hz until a separate timing review changes
   it.
2. Test L0 trajectory-setpoint output first:
   publish continuous position/velocity/acceleration/yaw references through
   the Sunray/PX4 position-control surface.
3. Test L1 attitude-thrust output next:
   bypass the runtime outer position loop while keeping PX4 attitude/failsafe
   semantics.
4. Test L2 body-rate-thrust output only after L1 is stable:
   bypass more of the runtime controller and prove takeoff-hover-land before
   figure-8 or spiral.
5. Only after the best interface level is selected, apply algorithm changes:
   anti-windup, phase reset, trajectory lead/latency compensation, feedforward,
   INDI/body-rate inner loop, or adaptive/disturbance compensation.
6. Tune parameters last, and record tuning deltas separately for the ideal
   MWORKS plant and the Gazebo/Sunray validation plant.
```

The purpose of this order is to avoid tuning around an interface mismatch. If
L0 fails but L1 or L2 removes most of the error, the MWORKS controller should
be adjusted at its output/interface layer first. If all levels show the same
error pattern, the issue is more likely trajectory generation, plant
parameters, estimator delay, or the control law itself.

Each level must use the same scenario family and produce a comparable evidence
bundle:

| Gate | Required evidence |
|---|---|
| L0 takeoff-hover-land | command trace, PX4/Sunray echo, state trace, RMSE/P95/max, landed-slide/yaw check |
| L0 figure-8/spiral | reference trace, actual trace, phase timing, RMSE/P95/max, shape checks |
| L1 takeoff-hover-land | attitude/thrust command trace, saturation flags, failsafe/mode proof, hover metrics |
| L1 figure-8/spiral | same as L0 plus attitude/thrust smoothness and saturation review |
| L2 takeoff-hover-land | body-rate/thrust command trace, mode/failsafe proof, tilt/rate limits, hover metrics |
| L2 figure-8/spiral | same as L1 plus body-rate and thrust-limit review |

Do not move a lower-level interface into figure-8, spiral, FAST-LIO feedback, or
planner work until the takeoff-hover-land gate is stable.

Candidate algorithms should be handled as design options, not marketing labels:

| Candidate | Intended Role | Minimum Evidence Before Acceptance |
|---|---|---|
| improved PID / AWFF PID | first optimized baseline replacement | at least one core metric improves without new instability in baseline scenes |
| PID-INDI / INDI | attitude inner-loop robustness and disturbance rejection | attitude response or trajectory RMSE improves against official PID |
| linear MPC | stable fallback for constrained outer-loop control | complex trajectory tracking improves or constraints are better respected |
| NMPC | advanced outer-loop candidate for nonlinear constraints | credible solver timing, convergence, and trajectory metric evidence |
| sliding mode | robust-control candidate under bounded disturbance | chattering/effort and tracking metrics are both reviewed |
| fuzzy control | scheduling or nonlinear correction candidate | rule base, operating range, and comparative metrics are labelled |
| neural compensation | residual or disturbance compensation candidate | training/source data, bounded output, and fallback behavior are labelled |
| composite controller | nominal controller plus compensation/safety/allocation | ablation shows which added module caused the improvement |

## 4. MWORKS-Native Control Backend

Competition-closure backend:

```text
PlannerSetpoint / MissionSetpoint
  -> flight mode and setpoint arbiter
  -> MWORKS-native controller
  -> control allocation
  -> motor/actuator model
  -> plant dynamics
```

Required control-side concepts:

- flight mode;
- mission phase;
- active setpoint source;
- estimator/localization validity;
- stale-command handling;
- failsafe reason;
- controller status echo;
- control allocation state;
- actuator saturation and health.

## 5. PX4-Compatible Control Backend

PX4/QGC are part of the full design, but they are post-competition expansion
backends unless a later competition requirement explicitly needs them.

Future backend:

```text
PlannerSetpoint / MissionSetpoint
  -> PX4-compatible adapter
  -> Offboard/SITL/HIL semantics
  -> arming/mode/failsafe/heartbeat/status
  -> QGC monitoring where useful
```

Shared semantics with MWORKS-native backend:

- streamed setpoints;
- mode state;
- arming/enable state;
- timeout behavior;
- estimator validity;
- geofence/collision status;
- failsafe/land/return command;
- accepted/rejected command echo.

## 6. Planning Goal

Planning should evolve from a minimum credible route to advanced local
optimization:

- waypoint / manual mission source;
- minimum-snap or polynomial trajectory;
- local A* plus smoothing fallback;
- EGO-inspired local planning;
- GCOPTER/MINCO-style advanced trajectory optimization;
- multi-UAV/swarm planning where needed.

All planner outputs should pass through PlannerAdapter and produce
`PlannerSetpoint` or trajectory traces. Planner output must be traceable to
local map and localization inputs.

## 7. Safety And Fault Goal

Safety functions:

- altitude, velocity, attitude, and thrust constraints;
- collision and geofence status;
- stale-command timeout;
- localization invalid/degraded handling;
- return/land/failsafe actions;
- motor efficiency degradation and actuator saturation;
- fault injection and event logging.

Fault and safety modules should be optional by phase but compatible with the
same run config and evidence bundle.

## 8. Model Credibility Goal

The plant should progressively move from seed parameters to identified or
validated parameters.

Important model issues to address:

- command-to-speed mapping;
- motor first-order lag;
- motor speed limit;
- thrust coefficient and yaw moment coefficient;
- rotor-center moment;
- body drag and angular damping;
- rotor gyroscopic effects where needed;
- battery/ESC/thrust margin;
- sensor bias/noise/delay.

Each parameter should declare provenance:

```text
DAE_geometry
SDF_migration
literature_seed
manual_estimate
bench_identified
ulog_identified
simulation_fit
```

## 9. Metrics Goal

Metrics should cover:

- tracking error;
- RMSE and maximum error for trajectory tracking;
- steady-state error;
- overshoot and settling time for step-like responses;
- attitude response;
- controller effort and saturation;
- disturbance/fault response;
- robustness retention under parameter perturbation, wind disturbance, and
  external disturbance;
- recovery time after disturbance;
- safety violations;
- localization quality;
- local-map/planner quality;
- mission completion;
- run reproducibility;
- visual/review artifact completeness.

Metrics should be report-ready but must preserve claim boundaries. A video can
show the scenario; metrics and logs prove the technical claim.

Syslab is the preferred quantitative comparison environment. If another metric
pipeline is used for a specific run, the output must still carry source labels
and remain equivalent to the Syslab metric contract.

## 10. Formation And Multi-UAV Goal

Formation control is a required competition extension after the single-UAV
controller line is stable. It should not block the single-UAV control closure,
but it is part of competition closure rather than a distant platform-only
feature.

Design should preserve:

- leader-follower route;
- virtual-structure route;
- formation switch;
- inter-UAV collision constraints;
- communication delay/dropout labels where used;
- formation metrics;
- multi-UAV run identity and evidence separation.

Minimum accepted formation route:

```text
leader trajectory
  -> follower relative-position references
  -> per-UAV controller backend
  -> per-UAV traces
  -> formation error and minimum inter-UAV distance metrics
```

Formation evidence must distinguish controller stability, formation
cohesiveness, and collision/safety behavior. A multi-UAV animation alone is not
formation-control evidence.

The detailed architecture source for this section is
`09_多机编队架构与数据设计.md`. Multi-UAV work must preserve:

- `swarm_id`, `formation_id`, `uav_count`, and per-UAV `uav_id`;
- one active `FlightControlAdapter` backend per UAV;
- separated per-UAV truth, controller, actuator, fault, and sensor traces;
- `FormationReference` as a reference generator output, not a motor command;
- formation metrics derived from raw per-UAV traces;
- no runtime database dependency for the first MWORKS-hosted formation route.
