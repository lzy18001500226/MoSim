# 01 系统目标与需求边界

Status: source design, 2026-06-11.

## 1. Product Goal

MoSim is a layered-authority UAV simulation and verification system for the A8
quadrotor task. Its near-term priority is to finish the competition functional
loop first, including single-UAV control optimization and multi-UAV formation
verification, before expanding into the broader MoSim platform roadmap.

The final system should support this user flow:

```text
select scenario / vehicle / controller / planner / disturbance / fault / sensor
  -> run a reproducible UAV experiment
  -> inspect control, perception, localization, planning, and visual evidence
  -> export metrics, figures, screenshots, videos, and report conclusions
```

MoSim is not just a control-algorithm demo and not just a UE rendering demo. It
is a full simulation verification environment whose credibility comes from
clear authority boundaries, typed contracts, source labels, and evidence gates.

## 2. Users And Use Cases

Primary users:

- control-system developers who need repeatable quadrotor dynamics and
  controller evidence;
- simulation-system developers who need scenario, sensor, rendering, and
  robotics integration evidence;
- reviewers who need to understand why a run is accepted, blocked, or only a
  visual demonstration;
- post-competition migration users who need the same scenario/control/planning
  contracts to connect to PX4, QGC, SITL/HIL, or hardware.

Primary use cases:

1. compare controller variants on the same scenario;
2. test disturbances, faults, and safety fallbacks;
3. generate sensor observations from realistic scenes;
4. run localization/local-map/planner pipelines without leaking global truth;
5. produce report-ready metrics and video evidence;
6. after competition closure, switch from MWORKS-native control to
   PX4/QGC-compatible control backends without redesigning the rest of the
   system.

## 3. Competition Function Mapping

The A8 competition line is first a quadrotor control-design and verification
system. MoSim must explicitly cover these functional requirements:

| Competition Requirement | MoSim Functional Capability | Authority / Evidence |
|---|---|---|
| Analyze the Tongyuan-provided quadrotor case, including dynamics and control model. | Import, label, and preserve the official plant/controller baseline as the reference case before adding project-specific controllers. | MWORKS/Sysplorer model source, baseline run manifest, raw traces. |
| Evaluate the existing PID controller on typical flight scenes. | Run the official PID baseline on hover, step, spiral climb, figure-8, and selected disturbance scenes. | MWORKS simulation outputs plus Syslab metric extraction. |
| Design and implement optimized attitude/position controllers in MWORKS.Sysblock. | Provide replaceable Sysblock controller modules for improved PID, PID-INDI/INDI, MPC/NMPC, sliding-mode, fuzzy, neural-compensation, or composite-control candidates. | Sysblock model evidence, controller interface contract, codegen/SIL evidence where runtime claims are made. |
| Integrate optimized control algorithms into the MWORKS UAV system model. | Ensure each accepted controller can replace the baseline controller through the same FlightControlAdapter and scenario/run configuration. | model check, closed-loop trace, controller input/output trace, actuator and plant state evidence. |
| Research and verify formation-control algorithms. | Add multi-UAV scenario identity, leader-follower minimum route, formation reference generation, inter-UAV safety constraints, and formation metrics. | per-UAV traces, formation error, minimum inter-UAV distance, accepted run bundle. |
| Quantitatively compare controllers in MWORKS.Syslab. | Provide the metric pipeline for overshoot, settling time, steady-state error, RMSE, robustness retention, disturbance recovery, and saturation/effort. | Syslab scripts or exported metric files with source labels. |

The comparison report itself is a downstream deliverable. The design requirement
here is that the system can generate the functional evidence needed by that
report without changing architecture.

Competition closure means these functions are implemented and evidence-backed:

```text
official baseline preserved
  -> baseline scenes and limitations measured
  -> optimized Sysblock controller integrated
  -> robustness and trajectory metrics computed
  -> multi-UAV formation route verified
  -> competition evidence bundle produced
```

Platform expansion beyond this loop is intentionally second-order work.

## 4. System Scope

MoSim includes:

- scenario and run configuration;
- vehicle and sensor profiles;
- MWORKS/Sysplorer/Sysblock/Syslab Modeling/MIL-SIL sources, controller
  design, current MWORKS-native flight-control backend, current MWORKS-hosted
  Runtime Plant backend, simulations, and Syslab metrics;
- UE5 scene rendering, UAV visual, camera, collision, and sensor oracle;
- localization and local-map adapters;
- planner adapters and 20Hz setpoint stream;
- flight-control adapter with multiple backends;
- evidence bundle generation;
- MoSim Studio / CLI / UE console surfaces that act through command/echo
  contracts.

MoSim does not require every backend to be implemented at the same time. The
design must support them now.

Current implementation decision:

```text
Current C0/C1/C2 implementation:
  MWORKS-hosted Modeling / MIL-SIL
  MWORKS-native Flight Control backend
  MWORKS-hosted Runtime Plant backend
  Syslab-compatible metrics
  no ROS2 dependency by default
  no PX4/QGC dependency by default
  no generated C/C++ dependency by default
```

ROS2, PX4/QGC, generated C/C++, HIL, and real-sensor routes remain designed
interfaces for later platform expansion. They become required only when a task
or acceptance claim explicitly says that backend is in scope.

## 5. Non-Goals

These are rejected as product routes:

- UE actor teleport as proof of control;
- planner access to UE global scene truth as if it were a local map;
- fake/static point clouds as FAST-LIO or planner evidence;
- browser/HTML point-cloud demos as the active robotics review surface;
- QGC/PX4 status display as a substitute for MWORKS metrics or run evidence;
- a pure script collection with no run identity, source labels, or evidence
  bundle;
- treating current implementation status as timeless system design.

## 6. Priority Capability Map

### C0: Minimum Competition Control Loop

C0 proves the architecture with the smallest honest competition-relevant run:

```text
scenario/run config
  -> MWORKS-hosted Runtime Plant backend
  -> MWORKS-native Flight Control backend
  -> official PID baseline scenario
  -> Syslab-compatible trace export
  -> MWORKS flight-control adapter
  -> evidence bundle
```

C0 must not depend on PX4/QGC. It may use ROS2/FAST-LIO only if a specific
competition scenario needs credible sensor/localization/planner evidence.
C0 also must not depend on generated C/C++ controller code. The control law can
run through the MWORKS-native or Equation-backed controller path as long as the
run declares the active backend and records the required evidence.

C0 success means one baseline scenario can be replayed and audited through its
run bundle. It does not mean optimized performance, formation completion, PX4
integration, or hardware readiness.

### C1: Competition Single-UAV Control Closure

C1 completes the single-UAV control requirements:

- official PID baseline analysis on hover, step, spiral climb, and figure-8;
- Sysblock optimized-controller replacement through the same interface;
- Syslab metric extraction for controller comparison and robustness checks;
- disturbance, fault, and safety scenario families;
- repeatable metrics and report asset generation;
- controller backend switching within MWORKS-native control where needed for
  the competition comparison.

### C2: Competition Multi-UAV And Formation Closure

C2 completes the multi-UAV/formation requirement after the single-UAV
controller line is stable:

- multi-UAV run identity and per-UAV evidence separation;
- leader-follower minimum accepted route;
- optional virtual-structure or formation-switch route;
- inter-UAV distance and collision/safety constraints;
- formation error and minimum-distance metrics;
- scenario replay and evidence bundle for the accepted formation claim.

### X: Post-Competition Platform Expansion

After competition closure, the same contracts can be expanded into a broader
MoSim platform:

- PX4 Offboard/SITL/HIL backend;
- MAVLink, MAVROS2, uXRCE-DDS, or px4_msgs route review;
- QGC status/monitoring integration;
- real LiDAR/IMU calibration and playback;
- HIL safety, latency, dropout, and failsafe review;
- planner backend switching;
- local map and sensor profiles;
- UE command console through command/echo;
- ROS2/RViz2/FAST-LIO evidence path stabilization beyond the competition need.

Post-competition work must reuse the contracts designed for C0/C1/C2. It must
not require a rewrite of scenario configuration, setpoint semantics, evidence
bundles, or authority rules.

## 7. Core Requirements

Functional requirements:

1. configure a reproducible run with scenario, vehicle, sensor, controller,
   planner, disturbance, fault, and backend choices;
2. simulate plant dynamics through the Runtime Plant contract and controller
   behavior through exactly one authoritative Flight Control backend;
3. generate or replay sensor observations with timestamps, frames, source
   labels, and validity flags;
4. localize and build local planning inputs without direct global-truth leakage;
5. plan or replay a trajectory and stream setpoints with stale-command
   handling;
6. record accepted/rejected command echoes for UI and automation actions;
7. preserve the official Tongyuan PID case as the baseline reference;
8. support Sysblock optimized-controller replacement under the same adapter;
9. support single-UAV and formation-control experiment identities;
10. compute control-effect and robustness metrics through Syslab or an
    equivalent labelled metric pipeline;
11. produce a complete evidence bundle for every accepted run.

Non-functional requirements:

- authority separation;
- reproducibility;
- backend replaceability;
- typed contracts;
- source and parameter provenance;
- failure visibility;
- report-ready outputs;
- gradual migration toward PX4/QGC/HIL without architecture rewrites.
