# 04 接口数据契约与时钟频率

Status: source design, 2026-06-10.

## 1. Contract Principle

MoSim modules communicate through typed contracts, not through hidden access to
each other's internal state.

Every runtime payload should carry:

```text
run_id
timestamp
clock_domain
frame_id
source
authority
validity
backend
```

## 2. RunState

```yaml
RunState:
  run_id: string
  scenario_id: string
  scene_id: string
  map_id: string
```

## 3. TruthState

```yaml
TruthState:
  timestamp: double
  clock_domain: string
  frame_id: world
  position_m: [x, y, z]
  velocity_mps: [vx, vy, vz]
  attitude_quat_wxyz: [w, x, y, z]
  angular_velocity_radps: [p, q, r]
  source: mworks_plant | gazebo_plant | replay_truth
  authority: plant_truth
  validity: valid | degraded | invalid
```

TruthState may drive visualization and sensor simulation. It must not be handed
to planner as local-map evidence unless the run is explicitly truth-debug.

## 7. PlannerSetpoint

```yaml
PlannerSetpoint:
  timestamp: double
  clock_domain: string
  frame_id: world
  position_ref_m: [x, y, z]
  velocity_ref_mps: [vx, vy, vz]
  acceleration_ref_mps2: [ax, ay, az]
  yaw_ref_rad: double
  valid: bool
  mode: trajectory | hover | land | return | fallback
  source: planner_adapter | mission_manager | safety_fallback
```

P0 target stream is 20Hz. A backend must define stale-command timeout behavior.

Formation runs use a formation-level reference that is translated into one
`PlannerSetpoint` stream per UAV:

```yaml
FormationReference:
  run_id: string
  swarm_id: string
  formation_id: string
  timestamp: double
  clock_domain: string
  frame_id: world
  route: leader_follower | virtual_structure | decentralized
  members:
    - uav_id: string
      role: leader | follower
      position_ref_m: [x, y, z]
      velocity_ref_mps: [vx, vy, vz]
      acceleration_ref_mps2: [ax, ay, az]
      yaw_ref_rad: double
      valid: bool
      source: formation_manager | safety_fallback
```

FormationReference must not be treated as plant truth or motor command.

## 8. CommandPacket And RuntimeEcho

```yaml
CommandPacket:
  run_id: string
  command_id: string
  command_type: set_scene | set_controller | set_planner | set_fault |
    set_wind | set_sensor_profile | arm | start | pause | stop | land
  requested_by: mosim_operator_console | ue_console | cli | qgc | automation
  payload: object
  timestamp: double
```

```yaml
RuntimeEcho:
  run_id: string
  command_id: string
  accepted: bool
  reason: string
  active_scene_id: string
  active_controller_id: string
  active_planner_id: string
  active_flight_control_backend: string
  authority_adapter: string
  timestamp: double
```

No frontend may treat a request as active until RuntimeEcho confirms it.

The first MoSim Operator Console is a local web frontend. Its transport must
map to these existing contracts instead of inventing a UI-only state model:

```text
Browser UI
  -> FastAPI REST command endpoint
  -> CommandPacket
  -> authority adapter / ROS2 bridge / runtime backend
  -> RuntimeEcho
  -> FastAPI WebSocket state stream
  -> Browser UI
```

REST is appropriate for bounded intents such as selecting a scenario, starting
or stopping a run, opening evidence, injecting a wind profile, or clearing a
fault. WebSocket is appropriate for runtime state, command echo, topic/rate
status, stale-command/failsafe state, logs, and live metric updates.

The frontend must not publish ROS2 setpoints, Gazebo actuator commands, or
MWORKS model operations directly. It only submits operator intent and displays
accepted/rejected echoes.

Static command/echo code, schemas, fixtures, and build-readiness checkers may
prove only that a future build-only gate is ready. Build-only readiness is not
Unreal build success, and build success is not runtime command acknowledgment.
Runtime acknowledgment requires a later bounded live probe with authoritative
producer identity, pending-request capture, authoritative echo capture,
request/echo match report, no-pose-overwrite report, false-ack negative report,
and timeout cleanup evidence.

## 8.1 Controller ABI

All controller backends must map to one public controller ABI before they are
connected to ROS2, PX4, generated runtime wrappers, or future Simulink
replacement.

The public shape is:

```text
ControllerInput
  -> state estimate
  -> reference / setpoint
  -> fault state
  -> safety state
  -> parameter profile
  -> ControllerBackend
  -> ControllerOutput
      -> motor command or attitude/thrust command
      -> mode/status/saturation
```

Do not expose MWORKS-only internal variable names as the public runtime
contract. MWORKS, generated C/C++, Simulink, and PX4-compatible adapters must
translate their backend-specific signals into this ABI.

Current A8 competition controller/model evidence may finish on the
MWORKS-hosted controller, plant, and evidence route. When the claim becomes
external deployment or normal UAV SITL validation, the formal route is:
generated C/C++ from MWORKS/Sysblock, SIL equivalence, then PX4 Offboard or
PX4 module/uORB integration in PX4+Gazebo SITL. Simulink, generated C/C++,
PX4, ROS2, and Gazebo adapters must share this ABI when introduced. A
behavior-equivalent ROS2/C++ or Python controller node may be used only as a
fixture/scaffold for bridge, plant, and review debugging before formal
generated-code deployment exists; the run manifest must label it as such.

Minimum public contract:

```yaml
ControllerInput:
  timestamp: double
  clock_domain: string
  vehicle_id: string
  state_estimate:
    position_m: [x, y, z]
    velocity_mps: [vx, vy, vz]
    attitude_quat_wxyz: [w, x, y, z]
    angular_velocity_radps: [p, q, r]
    source: localization_estimate | plant_truth_debug | replay
  reference:
    position_ref_m: [x, y, z]
    velocity_ref_mps: [vx, vy, vz]
    acceleration_ref_mps2: [ax, ay, az]
    yaw_ref_rad: double
  fault_state:
    rotor_effectiveness: [e1, e2, e3, e4]
    actuator_fault_flags: optional
  safety_state:
    mode: normal | degraded | fallback | land
    constraint_status: optional
  parameter_profile_id: string
```

```yaml
ControllerOutput:
  timestamp: double
  clock_domain: string
  vehicle_id: string
  command_type: trajectory_setpoint | attitude_thrust | body_rate_thrust |
    motor_speed | motor_thrust
  command: array
  command_units: rad_per_s | newton | normalized | mixed
  actuator_order: [rotor_0, rotor_1, rotor_2, rotor_3]
  command_frame_or_convention: string
  saturation: optional
  mode: normal | degraded | fallback | land
  status: valid | degraded | invalid
  backend: mworks_equation | mworks_graphical | generated_c |
    ros2_cpp_equivalent | simulink_codegen | px4_offboard | replay
  sequence_id: integer
  max_command_age_s: double
```

Controller outputs are evaluated in three runtime interface levels. These
levels are adapter choices, not separate controller products:

| Level | Public output shape | Runtime target | Main purpose | Risk |
|---|---|---|---|---|
| L0 | `trajectory_setpoint`: position, velocity, acceleration, yaw | Sunray `UAVControlCMD` modes such as `PosVelAccYaw` or PX4 trajectory setpoints | baseline mission tracking while PX4/Sunray owns inner loops | lowest |
| L1 | `attitude_thrust`: attitude or attitude quaternion plus normalized thrust | MAVROS `setpoint_raw/attitude` or PX4 attitude setpoint surface | bypass runtime outer position loop and reduce trajectory phase/outer-loop error | medium |
| L2 | `body_rate_thrust`: p/q/r body rates plus thrust | MAVROS/PX4 body-rate setpoint surface or future uORB adapter | minimize attitude-loop error and support INDI/body-rate controller deployment | highest |

The controller core should stay behind `ControllerInput -> ControllerOutput`.
MWORKS/Sysblock may need different output blocks or wrappers for L0/L1/L2, but
the public ABI must remain stable so future Simulink code generation can
replace the backend without changing the runtime plant, localization, planner,
or evidence contracts.

MWORKS-generated controllers must expose these adapter-facing signals whenever
the selected level needs them:

```yaml
GeneratedControllerInterface:
  sample_time_s: double
  mode: takeoff | hover | trajectory | land | fallback
  reset: bool
  input_valid: bool
  stale_input: bool
  frame_convention: ENU | NED | body
  yaw_convention: string
  thrust_convention: normalized | newton | acceleration_equivalent
  saturation_flags: optional
  parameter_profile_id: string
```

Mode and reset are part of the ABI because phase changes can otherwise leave
integrator or observer state from takeoff/hover/trajectory/land in the next
phase. Frame, yaw, and thrust conventions are part of the ABI because interface
errors at this boundary look like controller errors in Gazebo.

Historical/future ROS2 direct-actuator fixture surface:

```text
topic: /mosim/sunray150/controller_output
message: mosim_msgs/msg/ControllerOutput
adapter: Scripts/ros/controller_output_to_gazebo_actuators_node.py
actuator bridge: actuator_msgs/msg/Actuators.velocity[] -> gz.msgs.Actuators.velocity[]
actuator order: rotor_0, rotor_1, rotor_2, rotor_3
current normalized max rotor velocity: 8000 rad/s
current stale guard: max_command_age_s=2.0
target controller output cadence: 20Hz for closed-loop control; 5Hz fixture
  payloads are handoff tests only
```

This surface is not the current Sunray ROS1 execution entry and is not the
formal flight-control deployment contract. It is a debug bridge for actuator
ordering, stale-command guards, plant sanity, and message/schema checks.
Formal generated-controller deployment maps the same controller ABI into PX4:

```text
L1 Offboard:
  generated C/C++ adapter
  -> PX4-compatible trajectory/attitude/body-rate setpoints
  -> OffboardControlMode + setpoint proof-of-life stream
  -> PX4 estimator, failsafe, controller/allocation, actuator pipeline

L2 PX4 module/uORB:
  generated C/C++ adapter compiled into PX4 SITL
  -> reads declared uORB state/reference topics
  -> writes declared PX4 setpoint/control uORB topics
  -> PX4 timing, mode, failsafe, allocation, and logging remain authoritative
```

Deployment rule:

```text
MWORKS/Sysblock signal names
  -> backend-private adapter
  -> ControllerInput / ControllerOutput
  -> runtime-specific adapter
```

Never let a ROS2, Gazebo, PX4, or future Simulink public contract depend on
names such as an internal MWORKS connector, sum-block input, or generated C
global variable. Those names may appear only inside the backend adapter mapping
or evidence manifest.

Backend status labels:

| Backend label | Meaning | Minimum proof before use as authority |
|---|---|---|
| `mworks_equation` | Equation-backed executable controller used by current MWORKS full-system runs | MWORKS check/simulation evidence and declared equivalence target to graphical Sysblock |
| `mworks_graphical` | Graphical Sysblock controller or module used as visible structure/review artifact | Sysblock source/layout/check evidence; full-system execution only if embedding succeeds |
| `generated_c` | MWORKS-generated C/C++ controller backend | generated source, compile/runtime smoke, and SIL equivalence for the target controller |
| `ros2_cpp_equivalent` | manually implemented behavior-equivalent ROS2/C++/Python node for fixture/pre-acceptance validation | explicit non-codegen label, ABI mapping, command echo, bounded runtime evidence, and no formal deployment claim |
| `simulink_codegen` | future Simulink-generated backend | Simulink codegen evidence and equivalence against the accepted controller specification |
| `px4_offboard` | PX4-compatible Offboard/SITL/HIL backend | mode/arming/setpoint/failsafe evidence and command echo |

Controller deployment evidence must record which backend owns authority for the
run. A run with fixture `ControllerOutput` samples, command echo, or actuator
handoff is not a controller-performance run unless it also includes the
controller input/output trace, plant truth, metrics, and gate-specific
acceptance evidence.

Current project-owned ROS2 message definition:

```text
Scripts/ros/mosim_msgs/msg/ControllerOutput.msg
```

For the direct-actuator fixture lane, `ControllerOutput` is adapted to
`actuator_msgs/msg/Actuators` / `gz.msgs.Actuators.velocity[]` by:

```text
Scripts/ros/controller_output_to_gazebo_actuators.py
Config/scenarios/system/sunray150_gazebo_ros2_smoke.yaml: ros2.controller_adapter
```

The supported source command forms are `motor_speed`,
`normalized_motor_speed`, and `mworks_signed_visual_motor_speed`. The MWORKS
signed visual-speed convention is converted to Gazebo nonnegative velocity
magnitude after checking `mworks_spin_command_sign=[1,-1,1,-1]`; Gazebo rotor
turning direction is recorded separately as `[ccw,cw,ccw,cw]`. This adapter is
not a controller-performance claim. It is a backend bridge contract that must
still be proven by a bounded Gazebo+ROS2 runtime gate before any closed-loop or
planner-handoff claim.

Backend-specific adapters may add private fields, but they must not become the

## 8.2 ROS2 Topic Contract

When the complete-system route uses ROS2, the bridge should expose contracts,
not backend internals:

| Contract | Typical ROS2 surface | Authority |
|---|---|---|
| Truth or replay state | `/mosim/<uav_id>/truth` or bag metadata | plant truth or replay truth, not planner input unless debug-labelled |
| IMU | `/mosim/<uav_id>/imu` | sensor observation |
| LiDAR point cloud | `/mosim/<uav_id>/points` | sensor observation |
| TF/static TF | `/tf`, `/tf_static` | frame relationship evidence |
| Localization | FAST-LIO odometry/path/cloud topics or namespaced equivalents | localization estimate |
| Local map | point cloud, occupancy, ESDF, or obstacle-set topic | local-map authority |
| Planner setpoint | `/mosim/<uav_id>/setpoint` or equivalent adapter topic | planner/mission reference |
| Controller output | `/mosim/<uav_id>/controller_output` or backend-specific adapter output | controller authority |
| Runtime echo | `/mosim/<uav_id>/runtime_echo` | accepted/rejected runtime state |

Topic names may change by implementation, but every run must record the actual
names, namespace, frame ids, rates, and source authority in its run manifest.

For the Gazebo validation lane, the manifest must additionally record:

```yaml
plant_backend: gazebo
sensor_backend: gazebo_lidar | gazebo_depth | gazebo_imu
controller_backend: generated_c | ros2_cpp_equivalent | px4_offboard
render_backend: ue | rviz | gazebo_gui
map_backend: octomap | voxel_grid | esdf
claim_scope: system_validation | competition_metric | debug
```

`claim_scope=system_validation` can support point-cloud/map/ROS2 innovation
claims. It cannot replace `claim_scope=competition_metric` MWORKS/Syslab
evidence for controller-performance scoring.

## 9. Clock And Rate Targets

| Signal | Target | Authority |
|---|---:|---|
| MWORKS solver/control step | >= 100Hz preferred, backend-specific accepted value required | MWORKS |
| planner/setpoint stream | 20Hz | PlannerAdapter / FlightControlAdapter |
| truth state | 20-100Hz | PlantRuntime |
| IMU | 200Hz target | SensorObservationLayer |
| MID-360 baseline LiDAR | 10Hz | SensorObservationLayer |
| enhanced LiDAR | optional 20Hz with evidence | SensorObservationLayer |
| TF / transform stream | >= 20Hz where ROS2 is used | ROS2Bridge |
| FAST-LIO odometry/cloud/path | backend dependent, must be measured | LocalizationAdapter |
| local map | 5-20Hz target, must be measured | LocalMapAdapter |
| UE render/video | visual frame rate, not control evidence | UE5 |

## 10. Frame And Extrinsic Rules

- Keep mechanical mount pose, point-cloud origin, built-in IMU position,
  FAST-LIO extrinsic, and UE raycast frame separate.
- Do not write a mechanical CAD/DAE mount directly into a FAST-LIO extrinsic
  without frame review.
- Every transform used by localization or planning must have a source label.
- If frames are mixed, the run is blocked or debug-only.
