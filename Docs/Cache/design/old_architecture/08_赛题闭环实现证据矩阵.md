# 08 赛题闭环实现证据矩阵

Status: implementation evidence audit, updated 2026-06-23.

Purpose: record what is already implemented and evidence-backed before
post-competition platform expansion. This file does not change the acceptance
rules in `07_验收Gate与交付物.md`; it maps current source/model/config/result
artifacts to the C0/C1/C2 competition gates.

## 1. Status Vocabulary

Use these statuses when reviewing competition completion:

| Status | Meaning |
|---|---|
| `evidence_backed` | Source/config/result artifacts exist and metrics or logs support the specific claim. |
| `partial_evidence` | Meaningful artifacts exist, but the gate still needs a narrower review, final choice, or missing evidence type. |
| `source_static_only` | Source/config/checker artifacts exist, but no accepted live/runtime/result claim is proven. |
| `blocked_not_accepted` | Current evidence explicitly blocks the claim or records the absence of required proof. |
| `system_validation_pre_acceptance` | Live Gazebo/ROS2/PX4-side system evidence exists, but it is not formal MWORKS generated-code deployment or final competition controller-performance evidence. |
| `formal_route_pending` | The architecture route is selected, but required generated-code, SIL, PX4 adapter, or same-run PX4+Gazebo evidence is not complete. |
| `design_only` | The design exists, but implementation/result evidence has not been accepted. |
| `post_competition_only` | The item belongs to platform expansion and must not be counted as competition closure unless a future requirement explicitly pulls it into scope. |

## 2. Competition Scope Boundary

The competition closure target is:

```text
C0 minimum MWORKS-native control loop
  -> C1 single-UAV optimized control and robustness evidence
  -> C2 minimum multi-UAV / formation evidence
```

Current execution uses three separate evidence tracks:

```text
competition evidence track:
  MWORKS/Sysplorer/Sysblock/Syslab model, controller, metrics, report evidence

current Sunray ROS1 engineering validation track:
  Sunray ROS1 / Gazebo Classic / PX4 / MAVROS / px4ctrl / MID360 / RViz

future or reopened PX4-native/ROS2 generated-code target track:
  generated-code/PX4-native target route plus Gazebo/ROS2/RViz runtime review
```

The Sunray ROS1 track is the current executable engineering baseline for
Gazebo/RViz review. The PX4-native/ROS2 track remains historical or future
unless PMO/user explicitly reopens it. Neither track may overwrite or
impersonate the MWORKS competition evidence. A Gazebo truth-feedback
controller, Python bridge, ControllerOutput actuator echo, FAST-LIO/EGO topic
gate, or RViz visualization is `system_validation_pre_acceptance` until the
target controller's generated C/C++ code passes compile, SIL, adapter
integration, and same-run Gazebo/PX4 or Sunray/PX4 gates.

QGC, HIL, physical Pixhawk/Pixracer hardware, real-sensor replay, final UE
acceptance, final platform UI, and multi-UAV beyond the existing C2 formation
evidence remain outside the current single-UAV execution slice unless PMO/user
explicitly reopens them.
