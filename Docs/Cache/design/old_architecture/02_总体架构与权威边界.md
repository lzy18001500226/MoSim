# 02 总体架构与权威边界

Status: source design, 2026-06-11. RflySim-style four-layer architecture
alignment added after user review.

## 1. Architecture Summary

MoSim is designed as an RflySim-like layered UAV simulation and verification
system. The correct long-term mental model is not "MWORKS plus UE display";
it is a four-layer system with stable contracts:

```text
Layer 1: Modeling / MIL-SIL
  -> controller design
  -> dynamics model design and verification
  -> metric extraction and report evidence
  -> optional generated C/C++ controller/runtime artifacts

Layer 2: Flight Control
  -> one active control authority per run
  -> MWORKS-native controller now
  -> PX4/Pixhawk/QGC-compatible backend later
  -> arming/mode/failsafe/setpoint semantics

Layer 3: Runtime Plant / Sensors / HIL
  -> real-time or replayed multirotor dynamics
  -> actuator/motor/plant truth
  -> sensor simulation
  -> fault injection and event log
  -> state/sensor stream publication

Layer 4: Display / Scene / Review
  -> UE5 / MoSimSceneLibrary / future RflySimUE-style display
  -> camera/collision/LiDAR oracle when authorized
  -> RViz/RViz2/QGC/operator review surfaces
  -> video and visual evidence
```

The current competition path may implement Layers 1-3 inside MWORKS/Sysplorer/
Sysblock/Syslab for speed and evidence integrity. That is an implementation
shortcut, not the final architecture boundary. The design keeps Layer 2 and
Layer 3 explicit so PX4, HIL, real sensor input, or a separate runtime plant can
be added later without rewriting scenarios, evidence, or display contracts.

For the long-term complete-system route, ROS2 remains the formal robotics
integration target. For the current executable engineering lane, however, the
runtime stack is Sunray ROS1 / Gazebo Classic / PX4 / MAVROS / px4ctrl. TF,
LiDAR/IMU, RViz/RViz2, FAST-LIO, local mapping, planner state, bags, and
robotics runtime evidence must pass through the active lane's ROS contracts.
Do not substitute the old ROS2/x500 lane for current Sunray ROS1 evidence
unless PMO/user explicitly reopens it. For the current MWORKS-first
implementation slice, MWORKS can still host Modeling/MIL-SIL, Flight Control,
and Runtime Plant roles until a task claims perception, localization,
local-map, planner handoff, or external runtime integration. PX4/QGC, HIL, and
generated C/C++ backends remain contract-compatible extension routes, not
automatic prerequisites for every present MWORKS model optimization run.

When the task claims point cloud, 3D voxel/occupancy map, current ROS/Sunray
mapping, future ROS2-native mapping, or a robotics-stack validation demo, the
preferred engineering route is not to
replace the MWORKS competition simulation and not to bypass the flight
controller. MoSim should export the accepted controller through generated
C/C++, validate it with SIL, and then integrate it through the normal
PX4+Gazebo SITL route:

```text
MWORKS controller/model evidence
  -> generated C/C++ controller backend
  -> SIL / generated-runtime schema checks
  -> current Sunray/PX4/MAVROS wrapper or future PX4 Offboard/uORB adapter
  -> PX4 SITL flight-control authority
  -> Gazebo plant/world/sensor backend
  -> ROS1 or future ROS2 TF + IMU + LiDAR point cloud + local map
  -> UE render/replay frontend
```

PX4 owns mode, arming, estimator/failsafe, control-allocation semantics, and
the actuator pipeline in this lane. Gazebo owns the validation plant and sensor
source. ROS transports observations, localization, planner, and optional
Offboard messages; ROS direct-to-Gazebo motor control is only a
fixture/debug/pre-acceptance bridge, not the formal deployment route. MWORKS
remains the formal competition platform for controller design,
baseline/optimized comparison, Syslab metrics, and report evidence.

Current decision: do not implement real-time MWORKS-Gazebo co-simulation in
the first Gazebo validation slice. The live Gazebo run should not depend on
Sysplorer/Syslab stepping synchronously with Gazebo. MWORKS participates through
accepted controller/model evidence, parameter/config provenance, Syslab metric
outputs, and a generated controller backend that is explicitly bound to the
shared ABI and PX4 integration surface when external deployment is claimed.
Behavior-equivalent runtime nodes may be used only as labelled fixtures before
that route is ready. A future MWORKS-Gazebo real-time
co-simulation or HIL-like route is a separate backend gate that must first
define a master clock, reset/step/stop API, bridge latency budget,
stale-command protection, command echo, and equivalence tests.

The old compact core still exists inside these layers:

```text
Scenario / Mission / RunManager
  -> SwarmRunManager / FormationManager when multi-UAV is active
  -> SensorObservationLayer
  -> LocalizationAdapter
  -> LocalMapAdapter
  -> PlannerAdapter
  -> FlightControlAdapter
  -> PlantRuntime
  -> EvidenceBundle
```

Multi-UAV formation is an extension of this same graph, not a separate product
architecture. Its detailed identity, reference, result-layout, database, and
acceptance contracts live in `09_多机编队架构与数据设计.md`.

## 2. Layer Authority

| Layer | Owns | Must not own |
|---|---|---|
| Modeling / MIL-SIL | MWORKS/Sysplorer/Sysblock/Syslab model design, controller design, model checks, simulations, generated C/C++ artifacts, Syslab metrics, report evidence | real-time authority unless routed through Flight Control and Runtime Plant contracts; UE/RViz/QGC visual status; hidden parameter truth |
| Flight Control | active controller authority, setpoint consumption, mode, arming, stale-command timeout, failsafe, generated-code or PX4-compatible backend semantics | plant truth, sensor truth, UE scene truth, final metrics |
| Runtime Plant / Sensors / HIL | multirotor dynamics, actuator/motor behavior, truth state, simulated sensor streams, fault injection, disturbance, HIL/replay timing, plant events | controller design ownership, display acceptance, planner access to hidden global truth |
| Display / Scene / Review | UE5/MoSimSceneLibrary rendering, UAV visual, camera/collision/LiDAR oracle when explicitly routed, RViz2/QGC/operator review surfaces, video/screenshots | controller success, final plant truth, final planner truth, final control metrics |
| ROS2/RViz2/FAST-LIO/planner stack | robotics transport, TF, IMU/LiDAR topics, localization output, local map, planner review, bags | plant truth, fake odometry, hidden access to UE global truth, final control metrics |
| Results/Evidence | run manifest, config snapshot, logs, metrics, figures, screenshots, video, blocker/acceptance records | changing simulation outputs or acting as a control backend |
| Operator Console / GUI frontend | scenario/controller/disturbance/fault selection, start/pause/reset intent, accepted echo display, review entrypoints | direct plant truth, hidden planner inputs, final pass/fail authority, bypassing command/echo |

MWORKS currently appears in more than one row because it is both the modeling
environment and the quickest competition implementation host for the runtime
plant. When writing claims, name the role precisely:

```text
MWORKS as Modeling / MIL-SIL
MWORKS as Flight Control backend
MWORKS as Runtime Plant backend
```

Do not use a generic "MWORKS success" statement when the evidence only covers
one role.

## 3. RflySim Component Mapping

| RflySim concept | MoSim long-term counterpart | Current MoSim status |
|---|---|---|
| Simulink | MWORKS.Sysblock / Syslab / Modelica modeling layer | Active competition path for controller/dynamics/MIL-SIL/metrics. |
| PX4 / Pixhawk | Flight Control backend: PX4/QGC/Offboard/SITL/HIL or generated controller runtime | Formal external deployment backend for generated-code validation; MWORKS-only controller/model optimization can still run without it. |
| CopterSim | Runtime Plant / Sensors / HIL layer | Hosted by MWORKS for current competition evidence; Gazebo can host this role for exported-controller system validation and point-cloud/map work. |
| 3DDisplay / RflySim3D / RflySimUE5 | UE5 / MoSimSceneLibrary plus RViz2/QGC/operator review surfaces | UE/RViz/QGC display/review only; cannot decide controller or plant success. |

This mapping corrects a common misunderstanding: PX4 is not required before
MoSim can optimize and validate the MWORKS quadrotor model, but a full
RflySim-like platform must eventually separate flight-control authority and
runtime plant/sensor responsibilities from the modeling environment.

## 3.1 RflySim Capability Map And MoSim Overtake Route

RflySim is a capability map and architecture reference, not a source of
Sunray150 parameter truth and not a runtime that MoSim should blindly clone.
When comparing against it, distinguish missing design surfaces from merely
unfinished implementation.

RflySim-like systems already cover these first-class capabilities:

| Capability family | Mature-system role | MoSim design location |
|---|---|---|
| Model-based controller and plant design | Simulink/MBD, MIL/SIL, generated controller code | `03`, `04`, `06`, `07` |
| Flight-control backend | PX4/Pixhawk/QGC semantics, arming, modes, failsafe, setpoint stream | `02`, `04`, `07` |
| Runtime plant and sensors | CopterSim-style multirotor dynamics, motor/actuator state, sensor output, fault injection, HIL/replay | `10`, `04`, `07` |
| Scene and display | RflySim3D/UE visualization, cameras, operator review, video evidence | `05`, `07` |
| Robotics integration | TF, LiDAR/IMU streams, local maps, planner handoff, bags, RViz-style review | `04`, `05`, `07` |
| Experiment operation | scenario/profile selection, command echo, logs, evidence bundles | `03`, `04`, `07`, `08` |
| Multi-UAV | identity, per-UAV state, formation references, swarm metrics | `09` |

MoSim must not stop at parity. The design should exceed RflySim in these
directions:

- clearer authority separation between Modeling, Flight Control, Runtime
  Plant, and Display/Review;
- evidence-first acceptance, where every claim is tied to manifests, traces,
  metrics, screenshots, videos, or blockers;
- backend interchangeability through a shared controller ABI instead of
  exposing one backend's internal variable names;
- explicit anti-truth-leak planning boundaries, so UE global scene truth is
  used as an oracle for validation, not hidden planner input;
- source-labeled parameter policy, separating geometry seeds, SDF migration
  seeds, identified parameters, replay traces, and accepted simulation results;
- multi-UAV result layout that preserves per-UAV raw traces and metrics before
  any future database or browsing layer;
- reusable CoAgent/automation governance that helps route evidence and review
  without becoming product authority.

RflySim weaknesses that MoSim should design around:

- role boundaries can be implicit in the tool stack rather than explicit in
  the evidence bundle;
- example parameters are easy to copy without proving they are the target
  aircraft's truth;
- visual or HIL surfaces can look convincing before planner/localization/error
  gates are actually satisfied;
- operator UI and runtime authority can blur unless command/echo and active
  backend ownership are enforced.

Rejected uses:

- do not copy RflySim sample mass, inertia, `Ct`, `Cm`, motor lag, or scene
  values into Sunray150 as truth;
- do not treat RflySim scenes as final editable UE5 assets unless license,
  source, collision, material, and import evidence pass;
- do not claim RflySim-like platform completion from a browser visualization,
  static point cloud, or nonzero ROS2 topic alone.

The detailed historical audits are cached under
`Docs/Cache/design/historical_snapshots/absorbed_or_superseded_20260614/`; active design decisions
belong in this file, `10_四旋翼模型与RuntimePlant设计.md`, and the gate files.

## 4. Flight-Control Authority

MoSim has one flight-control adapter with multiple backends:

```text
Planner / Mission / Setpoint
  -> FlightControlAdapter
      -> Backend A: MWORKS-native controller
      -> Backend A2: generated C/C++ controller runtime from MWORKS/Sysblock
      -> Backend B: PX4 Offboard / SITL
      -> Backend C: PX4 HIL / real flight controller
  -> Plant / Truth / Sensor / Evidence
```

Competition controller-design evidence uses the MWORKS-native backend by
default. When the claim becomes external deployment, generated-runtime
validation, or normal UAV SITL behavior, PX4+Gazebo becomes the formal runtime
route. This avoids blocking pure MWORKS model optimization on PX4 while also
prevents Gazebo/ROS2 fixture code from being mistaken for flight-controller
deployment.

Generated C/C++ is optional for MWORKS-native controller simulation but
required for formal external deployment claims. The target controller must pass
its own codegen, compile, runtime-smoke, SIL equivalence, and PX4 integration
gate; the PID demo codegen route does not certify the current LinearMPC online
fault-allocation controller or AWFF controller.

Only one backend may own the active control authority in a run. A run may not
let MWORKS-native and PX4 both issue final actuator/control authority without a
declared arbitration mode.

## 4.1 Controller Artifact Authority

Controller artifacts are intentionally split by purpose:

| Artifact | Owns | Must not own |
|---|---|---|
| Graphical Sysblock controller | visible control topology, design review, module-level behavior review, teaching/report explanation | full-system success when graphical embedding is blocked; hidden Equation-only behavior |
| Equation controller | current stable executable full-system controller backend, especially when Sysplorer graphical embedding fails on internal multi-input ports such as `x_sum.u1`, `y_sum.u1`, or `thrust_sum.u1` | replacing the graphical deliverable or skipping equivalence review |
| Generated C/C++ controller | future SIL/HIL/PX4/CopterSim-like runtime backend after codegen and equivalence gates | current MWORKS simulation acceptance unless generated-runtime authority is explicitly claimed |

The accepted current route is:

```text
one control-law/interface specification
  -> graphical Sysblock structure for review
  -> Equation executable bridge for current full-system simulation
  -> optional generated C/C++ backend later
```

This means full-system MWORKS evidence may use the Equation controller when it
is declared as behavior-equivalent to the graphical controller and the run
bundle records the active backend. It does not mean the graphical Sysblock
controller can be dropped.

## 4.2 Controller Deployment Route

Controller deployment is staged. Do not jump directly from a control-law idea
to Gazebo/PX4 authority.

```text
Stage D0: MWORKS controller design
  -> official PID baseline
  -> optimized Sysblock / Equation candidate
  -> MWORKS closed-loop run
  -> Syslab metrics

Stage D1: executable backend equivalence
  -> graphical Sysblock review artifact
  -> Equation executable backend for current full-system simulation
  -> generated C/C++ only when generated-runtime authority is claimed
  -> SIL comparison against the MWORKS reference

Stage D2: shared ABI binding
  -> ControllerInput / ControllerOutput contract
  -> backend-private signal mapping
  -> command type, motor order, saturation, mode, status, stale-command policy

Stage D3: PX4+Gazebo runtime validation
  -> choose L1 PX4 Offboard setpoint adapter or L2 PX4 module/uORB adapter
  -> PX4 mode/arming/failsafe/control-allocation path
  -> Gazebo plant/sensor response
  -> command echo, stale-command guard, and ULog/topic evidence
  -> planner/localization handoff only after command and safety gates pass
```

For the A8 competition, Stage D0 is the controller-performance authority.
Stage D1 is required when claiming behavior equivalence or generated runtime.
Stages D2-D3 are system-validation and deployment routes. They cannot replace
MWORKS/Syslab metric evidence for the competition controller claim. The older
`ControllerOutput -> Gazebo actuator` route is retained only as a bridge
fixture for plant, mixer, message, and safety debugging.

## 4.3 Exported-Controller Gazebo/ROS2 Validation Lane

Some innovation claims require an actual robotics stack rather than only
MWORKS curves and UE replay. The selected formal lane for those claims is:

```text
MWORKS/Sysblock controller design and Syslab metrics
  -> GenerateModelCode
  -> generated C/C++ controller and SIL equivalence
  -> L1 PX4 Offboard adapter or L2 PX4 module/uORB adapter
  -> PX4 SITL flight-control authority
  -> Gazebo multirotor plant, IMU, LiDAR, and world model
  -> ROS2/uXRCE-DDS topics, TF, raw LiDAR point cloud, local map, planner state
  -> UE high-quality render from the same state stream
```

Authority split:

| Surface | Owner in this lane |
|---|---|
| Competition controller evidence | MWORKS/Sysplorer/Sysblock/Syslab |
| Flight-control authority | PX4 SITL for formal external runtime validation; MWORKS-native only for MWORKS-hosted competition runs |
| System-validation plant truth | Gazebo |
| Sensor observations | Gazebo sensors by default; UE sensors only after a separate sensor-authority gate |
| Robotics transport and map | ROS2 |
| Human-facing visual render | UE |

This lane may demonstrate raw LiDAR point-cloud transport, downstream 3D
occupancy/voxel map generation, planner handoff, and ROS2/RViz evidence. It
must not be used to claim that MWORKS competition metrics are satisfied unless
the same controller/model result is also supported by the MWORKS evidence
gates.

This lane is not real-time MWORKS-Gazebo co-simulation by default. During the
run, PX4 owns flight-control timing and authority, Gazebo owns
plant/world/sensor timing, and ROS2 owns transport, perception, localization,
planner review, and optional Offboard messages. Sysplorer/Syslab may be opened
for model review, result curves, and metric evidence, but it is not assumed to
be a synchronous participant in every Gazebo physics tick.

ROS2/C++ or Python behavior-equivalent nodes may still be used as temporary
fixtures for message schema, actuator bridge, plant sanity, and visual-review
debugging. They must be labelled as `fixture`, `scaffold`, or
`pre_acceptance`. They do not prove formal controller deployment until the
target generated C/C++ controller is integrated through PX4 Offboard or PX4
module/uORB surfaces and passes same-run PX4+Gazebo gates.

## 4.4 Future Real-Time Co-Simulation Gate

Real-time MWORKS-Gazebo co-simulation is reserved as a future SIL/HIL-like
capability. It is allowed only after the simpler Gazebo validation lane is
stable. The minimum design contract is:

```text
Gazebo/ROS2 clock or declared master clock
  -> bridge samples odom/IMU/LiDAR or selected state
  -> MWORKS controller/runtime step(t, input)
  -> bounded ControllerOutput
  -> stale-command and saturation guard
  -> Gazebo actuator command
  -> RuntimeEcho and evidence log
```

Before this route can make product claims, it must provide:

- a fixed tick contract and sample-rate budget;
- deterministic reset/step/stop behavior;
- coordinate-frame and unit conversion tests;
- max/mean latency measurements;
- timeout/failsafe behavior when MWORKS or the bridge stalls;
- replay equivalence against the accepted MWORKS offline/controller run;
- hover, takeoff, landing, trajectory, wind, and rotor-efficiency smoke tests.

Until those gates exist, the project should not describe Gazebo demos as
"MWORKS real-time co-simulation." Describe them as Gazebo/ROS2 validation using
an MWORKS-derived controller backend.

## 5. Runtime Plant Authority

`PlantRuntime` is the MoSim counterpart of the CopterSim role. It may be
implemented first inside MWORKS, but its contract is independent:

```text
control command / motor command
  -> actuator and motor dynamics
  -> multirotor body dynamics
  -> disturbance and fault injection
  -> truth state
  -> simulated sensor streams
  -> event log and plant metrics
```

Responsibilities:

- own the vehicle truth state for a run;
- apply motor lag, thrust, yaw moment, rotor-center moment, drag/damping/gyro
  terms when accepted;
- simulate or route IMU, LiDAR, camera/depth, GPS/barometer/magnetometer where
  those sensors are in scope;
- publish state/sensor/event outputs to display, ROS2, evidence, or PX4/HIL
  adapters through typed contracts;
- record whether a value is a geometry seed, SDF migration seed, identified
  parameter, replayed trace, or accepted simulation result.

Runtime Plant must not:

- decide controller success without metrics;
- accept UE global truth as hidden planner input;
- let display surfaces mutate plant state;
- claim HIL/PX4/CopterSim parity before timing and interface evidence exist.

For multi-UAV runs, Runtime Plant authority is per UAV. Each vehicle has its
own truth state, actuator state, fault state, sensor state, and event stream.
Formation-level modules may generate references or safety projections, but they
must not merge or overwrite per-UAV plant truth.

## 6. Perception And Planning Authority

UE may hold complete scene geometry, but planner inputs must be observation
products:

```text
UE scene geometry
  -> sensor oracle / collision oracle
  -> LiDAR / depth / camera observations
  -> localization and local-map adapters
  -> planner
```

The rejected route is:

```text
UE global scene truth -> planner
```

Truth localization may exist for smoke/debug, but it must be labeled as a debug
backend and cannot be used as final localization/planner evidence.

## 7. ROS2 And PX4 Are Backends, Not The Core

ROS2 is the intended complete-system integration route because it connects
MoSim to real robotics tools such as RViz2, FAST-LIO, bags, TF, and planner
packages. It is not plant truth and it is not the only possible internal
transport for small competition-only runs.

PX4/QGC are valuable because they connect MoSim to real flight-control semantics
and hardware migration. They are not required for the first MWORKS-native
closed loop.

The core design therefore avoids both traps:

- do not make competition closure impossible by requiring PX4/QGC too early;
- do not ignore PX4/QGC until late enough that setpoint, mode, and failsafe
  contracts must be rewritten.

For the current MWORKS-only implementation slice, localization/local-map/
planner items may stay as debug, replay, or future-extension contracts unless
the active task explicitly needs them. Once the task claims real-time point
cloud, 3D voxel map, FAST-LIO, planner handoff, or ROS2 review, the ROS2
contracts and evidence gates become mandatory. Gazebo is the default short-term
sensor/plant source for that lane unless the task explicitly chooses a UE
raycast or replay source and accepts the extra evidence burden.

## 8. User Interfaces

All UI surfaces are frontends. They submit intent; they do not directly mutate
plant truth.

```text
UI action
  -> command packet
  -> authority adapter validation
  -> accepted/rejected runtime echo
  -> UI displays echoed state
```

This applies to MoSim Studio, CLI, UE Experiment Console, and future QGC/PX4
monitoring workflows.

## 9. Engineering Priority

Current priority remains:

```text
1. verify and improve the MWORKS quadrotor dynamics model;
2. run model-level hover/yaw/single-rotor-effectiveness smoke;
3. run controller/scenario evidence on a credible plant;
4. then add the minimum MWORKS-hosted leader-follower formation route with
   per-UAV traces and formation metrics;
5. only then expand runtime plant separation, ROS2/UE sensor routing, PX4/QGC,
   HIL, database-backed experiment browsing, and broader platform behavior.
```

This priority does not contradict the four-layer architecture. It says only
that the first implementation slice uses MWORKS to host multiple roles until
the model and controller evidence is strong enough to justify separating the
runtime plant and flight-control backends.

## 10. Sub-Agent / Department Planning For Architecture Work

Architecture changes that touch multiple layers should split review by role:

| Role | Review focus |
|---|---|
| MWORKS model/control reviewer | Whether Modeling/MIL-SIL and current MWORKS-hosted Runtime Plant claims are supported by model checks and simulation evidence. |
| Flight-control runtime reviewer | Whether MWORKS-native, generated C/C++, and future PX4/QGC backends share one active authority contract and command echo semantics. |
| Runtime plant/sensor reviewer | Whether dynamics, actuator, sensor, fault, event, and timing contracts are explicit enough to become a CopterSim-like layer. |
| Display/ROS/UE reviewer | Whether UE/RViz/QGC surfaces remain display/review/oracle surfaces and do not take over plant or controller authority. |
| PMO/context reviewer | Whether current competition scope and post-competition platform scope remain separated. |

These are planning roles. They do not require spawning a sub-agent for every
small edit, but non-trivial packets should record which reviews were needed,
used, skipped, or blocked.

## 11. Anti-Regression Rules

- No UE teleport as controller evidence.
- No fake/static point cloud as localization or map evidence.
- No browser point cloud as the primary robotics review surface.
- No planner direct access to global scene truth.
- No final success claim without an evidence bundle.
- No backend-specific shortcut that breaks the stable core contracts.
- No generic "MWORKS owns everything" wording when the evidence actually covers
  only Modeling/MIL-SIL, Flight Control, or Runtime Plant.
- No PX4/QGC dependency for current model optimization unless a task explicitly
  moves that claim into scope.
- No multi-UAV acceptance from animation, merged traces without `uav_id`, or
  database rows without raw trace and manifest references.
