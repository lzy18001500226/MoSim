# 09 Multi-UAV Formation Architecture And Data Design

Status: source design, 2026-06-12. This document defines the multi-UAV
architecture before implementation. It is not a claim that formation simulation
has already passed.

## 1. Scope

Multi-UAV formation is part of competition closure after the single-UAV
controller line is stable. It extends the existing four-layer MoSim
architecture; it does not replace it with a separate swarm platform.

The first accepted route is intentionally conservative:

```text
leader trajectory
  -> follower relative-position references
  -> per-UAV FlightControlAdapter
  -> per-UAV PlantRuntime
  -> per-UAV traces
  -> formation metrics and safety metrics
```

This route proves formation control for a declared scenario. It does not prove
general swarm autonomy, ROS2 swarm runtime, PX4 swarm control, or final platform
readiness.

## 2. Architecture Position

Formation control spans all four layers but must preserve their authority
boundaries:

| Layer | Multi-UAV Responsibility | Boundary |
|---|---|---|
| Modeling / MIL-SIL | defines formation scenario models, per-UAV controller integration, and metric extraction | does not own live flight-control authority outside the selected backend |
| Flight Control | runs exactly one active controller backend per UAV and emits per-UAV control status | does not own plant truth or formation acceptance |
| Runtime Plant / Sensors / HIL | owns per-UAV truth state, faults, disturbances, sensor streams, and plant events | does not let one UAV's hidden truth leak into another UAV's planner |
| Display / Scene / Review | renders or reviews multiple UAVs, videos, screenshots, RViz/QGC/UE views | animation alone is not formation evidence |

The current competition slice should implement the first formation route inside
MWORKS when possible:

```text
MWORKS as Modeling / MIL-SIL
MWORKS as Flight Control backend
MWORKS as Runtime Plant backend
```

This is an implementation shortcut. The contracts below keep ROS2, UE, PX4,
QGC, or a separated CopterSim-like runtime plant possible later.

## 3. Core Modules

Multi-UAV adds these modules to the existing execution graph:

```text
RunManager
  -> SwarmRunManager
  -> ScenarioManager
  -> FormationManager
  -> InterUAVSafetyLayer
  -> UAV[0].FlightControlAdapter -> UAV[0].PlantRuntime
  -> UAV[1].FlightControlAdapter -> UAV[1].PlantRuntime
  -> UAV[N].FlightControlAdapter -> UAV[N].PlantRuntime
  -> FormationMetrics
  -> EvidenceManager
```

`SwarmRunManager` binds one run-level identity with multiple UAV member
identities. It does not decide formation acceptance.

`FormationManager` owns the formation reference generator:

- leader trajectory route;
- follower relative-position route;
- virtual-structure route for later phases;
- formation switch schedule;
- communication delay/dropout labels when they are part of the scenario.

`InterUAVSafetyLayer` owns safety projection or rejection before references
reach the per-UAV controllers:

- minimum inter-UAV distance;
- collision/geofence status;
- velocity and acceleration limits;
- stale reference handling;
- emergency hold/land/return labels where the scenario includes them.

`FormationMetrics` compares references and traces after the run. It cannot
change the run output.

## 4. Identity Model

Every multi-UAV artifact must carry both run-level and member-level identity:

```yaml
SwarmRunState:
  run_id: string
  swarm_id: string
  scenario_id: string
  formation_id: string
  uav_count: integer
  clock_domain: string
  formation_route: leader_follower | virtual_structure | decentralized
  status: initialized | running | completed | blocked | failed
```

```yaml
UavMember:
  run_id: string
  swarm_id: string
  uav_id: string
  role: leader | follower | spare | observer
  vehicle_profile_id: string
  controller_id: string
  flight_control_backend: string
  plant_backend: string
  sensor_profile_id: string
  initial_pose_ref: string
  result_namespace: string
```

Per-UAV state, control, plant, sensor, and evidence files must never be merged
without retaining `uav_id`.

## 5. Reference Contracts

The minimum formation reference contract is:

```yaml
FormationReference:
  run_id: string
  swarm_id: string
  formation_id: string
  timestamp: double
  clock_domain: string
  frame_id: world
  route: leader_follower | virtual_structure | decentralized
  members:
    - uav_id: string
      role: leader | follower
      position_ref_m: [x, y, z]
      velocity_ref_mps: [vx, vy, vz]
      acceleration_ref_mps2: [ax, ay, az]
      yaw_ref_rad: double
      valid: bool
      source: formation_manager | safety_fallback
      source_reference:
        leader_uav_id: optional string
        relative_offset_m: optional [dx, dy, dz]
```

The per-UAV `PlannerSetpoint` remains the input to `FlightControlAdapter`.
`FormationReference` is translated into one `PlannerSetpoint` stream per UAV.
FormationManager must not write motor commands or mutate plant truth.

## 6. Result Layout

Formation results should be laid out so a reviewer can inspect each UAV
separately and then inspect formation-level metrics:

```text
Results/formation/<scenario_id>/<run_id>/
  RUN_MANIFEST.json
  CONFIG_SNAPSHOT.yaml
  formation_reference.csv
  formation_metrics.json
  safety_events.json
  uav_0/
    raw.csv
    controller_trace.csv
    plant_truth.csv
    metrics.json
  uav_1/
    raw.csv
    controller_trace.csv
    plant_truth.csv
    metrics.json
  figures/
  screenshots/
  videos/
```

`RUN_MANIFEST.json` records source labels for every layer. A metric table or
video that cannot be traced to this manifest is report material only, not
formation acceptance evidence.

## 7. Database Policy

No runtime database is required for the first formation implementation.
Scenario YAML, raw traces, metrics JSON, and manifests remain the source of
truth.

A lightweight database may be added later only as an experiment index:

```text
run_id
scenario_id
swarm_id
formation_id
uav_count
uav_id
controller_id
formation_route
raw_trace_path
metrics_path
status
created_at
```

If added, prefer SQLite or DuckDB for local indexing. Do not make PostgreSQL,
an ORM, or a service database a prerequisite for running MWORKS formation
scenarios. The database must be rebuildable from manifests and result files.

## 8. Metrics

Minimum formation metrics:

- per-UAV trajectory RMSE and maximum error;
- leader trajectory tracking error;
- follower relative-position error;
- formation RMSE;
- maximum formation error;
- minimum inter-UAV distance;
- count and duration of safety-distance violations;
- collision/geofence status;
- controller effort and saturation summary per UAV;
- disturbance/fault recovery metrics if the scenario injects a fault.

Optional later metrics:

- communication delay/dropout effect;
- role-switch transient error;
- virtual-structure rigidity error;
- decentralized consensus error;
- localization/local-map quality per UAV where ROS2/FAST-LIO is used.

## 9. Phase Plan

### Phase F0: Design And Static Contract

- define YAML scenario schema for formation runs;
- define per-UAV identity and output layout;
- define formation metric schema;
- add checker that rejects merged traces without `uav_id`.

No live formation success may be claimed in this phase.

### Phase F1: MWORKS Leader-Follower Smoke

- three UAVs or two UAVs if three is too heavy for first check;
- one leader trajectory such as figure-8 or spiral;
- followers track fixed relative offsets;
- one active MWORKS-native controller backend per UAV;
- output per-UAV traces and formation metrics.

This phase proves only the declared MWORKS-hosted route.

### Phase F2: Safety And Fault Formation

- add minimum-distance constraint;
- add one rotor-efficiency or wind disturbance case;
- preserve per-UAV safety and fault events;
- compare formation stability with and without the safety/fault layer.

### Phase F3: Display And Robotics Integration

- UE renders multiple UAVs from MWORKS truth state;
- ROS2 topics include namespaced UAV states and sensor streams;
- RViz/QGC review is optional and claim-scoped;
- no display surface may become controller or plant authority.

### Phase F4: Post-Competition Platform Expansion

- PX4 Offboard/SITL/HIL backend per UAV;
- swarm communication timing;
- real sensor or bag replay;
- database-backed experiment browsing if result volume justifies it.

## 10. Acceptance Boundary

Formation acceptance requires:

- single-UAV controller line selected or explicitly named as still provisional;
- multi-UAV scenario id and formation id;
- per-UAV run identity;
- per-UAV reference, controller, plant truth, and metrics traces;
- formation metrics;
- safety-distance and collision status;
- source labels for all layers;
- screenshots/video only as supporting visual evidence.

Do not accept formation from:

- animation without per-UAV traces;
- one merged trace without `uav_id`;
- reused single-UAV metrics with duplicated names;
- UE global scene truth used as hidden planner input;
- ROS2 topic presence without same-run frame, namespace, and metric evidence;
- database rows without raw trace and manifest references.
