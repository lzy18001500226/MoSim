# 03 核心模块设计

Status: source design, 2026-06-11. Aligned with the RflySim-style four-layer
architecture in `02_总体架构与权威边界.md`.

## 1. Module Map

MoSim modules sit under four architecture layers:

```text
Layer 1: Modeling / MIL-SIL
  -> VehicleProfile
  -> controller/dynamics model sources
  -> metric extraction
  -> generated controller/runtime artifacts where accepted

Layer 2: Flight Control
  -> FlightControlAdapter
  -> MWORKS-native controller backend
  -> generated C/C++ controller runtime backend
  -> future PX4/QGC/SITL/HIL backend

Layer 3: Runtime Plant / Sensors / HIL
  -> PlantRuntime
  -> SensorObservationLayer
  -> fault/disturbance/event runtime
  -> state and sensor stream publication

Layer 4: Display / Scene / Review
  -> UE5/MoSimSceneLibrary review/oracle surfaces
  -> MoSim Operator Console / UE Experiment Console frontends
  -> current Sunray ROS1 Gazebo/RViz windows
  -> future/reopened ROS2/RViz2/FAST-LIO/planner review windows
  -> QGC/operator status review where in scope
  -> EvidenceManager display assets
```

The execution graph is:

```text
RunManager
  -> SwarmRunManager when uav_count > 1
  -> ScenarioManager
  -> FormationManager when formation_id is set
  -> InterUAVSafetyLayer when inter-UAV constraints are in scope
  -> VehicleProfile
  -> SensorObservationLayer
  -> LocalizationAdapter
  -> LocalMapAdapter
  -> PlannerAdapter
  -> FlightControlAdapter
  -> PlantRuntime
  -> EvidenceManager
```

Each module exposes typed inputs and outputs. Modules may have different
backends, but the contracts must remain stable.

The current competition implementation may host Modeling, Flight Control, and
Runtime Plant functions in MWORKS. When reporting status, name the exact role
being validated.

The long-term complete-system route may use ROS2 for robotics transport,
localization, local mapping, planner integration, and RViz2 evidence. The
current executable runtime lane is Sunray ROS1 / Gazebo Classic / PX4 / MAVROS
/ px4ctrl. Do not route current single-UAV Sunray review work through the old
ROS2/x500 lane unless PMO/user explicitly reopens it. The current MWORKS-first
implementation can still make model/control progress without PX4/QGC, HIL, or
generated C/C++ until those backends are explicitly claimed. The active
competition default is:

```text
MWORKS-native or Equation-backed FlightControlAdapter
  -> MWORKS-hosted PlantRuntime
  -> Results/EvidenceManager
```

The active Gazebo validation route is deliberately different from real-time
MWORKS-Gazebo co-simulation:

```text
MWORKS model/controller evidence
  -> generated C/C++ or audited C++ controller core where deployment is claimed
  -> Sunray/PX4/Gazebo or future ROS2/PX4 validation plant and sensor lane
  -> ROS/RViz maps, planner, and review evidence
  -> UE or Operator Console review frontend
```

In this route, Sysplorer/Syslab are not synchronously stepped by Gazebo. They
remain the formal model/control/metric source, while the runtime backend carries
the accepted controller behavior into Gazebo.

For multi-UAV formation, read `09_多机编队架构与数据设计.md` before changing
module contracts. That document defines `SwarmRunManager`, `FormationManager`,
`InterUAVSafetyLayer`, per-UAV result namespaces, and formation metrics.

## 2. RunManager

Responsibilities:

- create `run_id`;
- bind scenario, scene, map, vehicle, controller, planner, sensor, disturbance,
  fault, and backend choices;
- freeze config snapshots;
- start or replay module backends;
- record source labels and version identifiers;
- collect metrics, logs, screenshots, videos, and blockers.

RunManager does not decide controller success directly. It orchestrates and
records evidence.

For multi-UAV runs, RunManager delegates member binding to `SwarmRunManager`
and records `swarm_id`, `formation_id`, `uav_count`, and per-UAV result
namespaces in the run manifest.

## 3. ScenarioManager

Responsibilities:

- define mission type, start/goal, trajectory target, obstacles, disturbance,
  fault, sensor profile, and review mode;
- provide scenario-level acceptance intent;
- map scenario intent into backend-specific configuration.

ScenarioManager must not bypass the authority boundary. It cannot give planner
direct access to UE global truth unless the run is explicitly labeled as a debug
or oracle-only run.

For multi-UAV runs, ScenarioManager defines the formation route, member roles,
initial poses, relative offsets, safety constraints, and communication
delay/dropout labels when those effects are in scope.

## 4. VehicleProfile

Responsibilities:

- identify vehicle geometry, mass, inertia, rotor centers, motor constants,
  sensor mounts, and visual assets;
- attach provenance labels such as `DAE_geometry`, `SDF_migration`,
  `bench_identified`, `ulog_identified`, or `manual_review`;
- define which parameters are design seeds and which are accepted truth.

Sunray150 can start from SDF/DAE-derived seeds, but final claims need parameter
source labels and evidence gates.

Layer role: Modeling / MIL-SIL plus Runtime Plant configuration. It defines
what vehicle is being modeled; it does not itself prove runtime behavior.

## 5. SensorObservationLayer

Responsibilities:

- generate or replay IMU, LiDAR, camera, depth, collision, and other
  observations;
- attach timestamp, frame, extrinsic, source, and validity metadata;
- support multiple backends:
  - UE raycast / camera / collision oracle;
  - MWORKS sensor model;
  - recorded bag or dataset replay;
  - future real sensor input.

This layer produces observations. It does not provide planner with global scene
truth.

Layer role: Runtime Plant / Sensors / HIL. UE, MWORKS, bag replay, and future
real sensors are backends that must all emit the same observation contract.

## 6. LocalizationAdapter

Backends:

- `TruthDebugLocalization`: smoke/debug only, labeled as truth-derived;
- `FastLIO_SunrayROS1`: current Sunray ROS1 FAST-LIO candidate backend;
- `FastLIO_ROS2`: future or explicitly reopened ROS2/FAST-LIO backend;
- future native localization or real estimator backend.

Responsibilities:

- consume IMU/LiDAR/TF or replay inputs;
- output odometry, path, validity, covariance/quality where available;
- expose failure and degraded states;
- record whether output is estimator-derived or truth-derived.

## 7. LocalMapAdapter

Responsibilities:

- convert sensor/localization outputs into planner-readable local map products;
- support point-cloud map, occupancy, ESDF, or simplified local obstacles;
- attach update rate, frame, timestamp, validity, and source labels.

LocalMapAdapter is the firewall between UE global geometry and planner input.

## 8. PlannerAdapter

Backends:

- waypoint / minimum-snap;
- local A* plus smoothing;
- EGO-inspired local planner;
- GCOPTER/MINCO-style advanced optimizer;
- ROS/Sunray planner backend where useful;
- future ROS2 planner backend after explicit route reopening.

Responsibilities:

- consume odometry/local-map/mission constraints;
- output trajectory or 20Hz setpoint stream;
- mark setpoints as valid, stale, fallback, or rejected;
- record `setpoint_trace`.

PlannerAdapter must not command the plant directly. It writes into
FlightControlAdapter.

In formation runs, `FormationManager` may generate a formation-level reference,
but the final input to each controller remains one per-UAV `PlannerSetpoint`.
FormationManager must not emit motor commands.

## 9. FlightControlAdapter

Backends:

- MWORKS-native controller backend;
- generated C/C++ controller runtime backend from accepted MWORKS/Sysblock
  codegen;
- current Sunray ROS1 PX4/MAVROS/px4ctrl engineering backend;
- post-competition or explicitly reopened PX4 Offboard/SITL backend;
- post-competition PX4 HIL or real flight-controller backend.

Responsibilities:

- accept mission and planner setpoints;
- manage flight mode, arming, stale-command timeout, failsafe, estimator
  validity, collision/geofence status, and control status;
- dispatch to exactly one active control authority backend;
- emit runtime echo and control status.

Competition closure should use the MWORKS-native backend unless a later
requirement explicitly pulls PX4/QGC into the competition claim. The PX4/QGC
contract is still designed now so post-competition migration does not rewrite
the core interface.

Within the MWORKS-native backend, a graphical Sysblock controller and an
Equation controller are not competing product routes. The graphical controller
is the structure/review artifact. The Equation controller is the current stable
full-system execution artifact when graphical Sysblock embedding is blocked by
tool limits. Both must share the same controller interface and behavior target.

Generated C/C++ belongs to a later backend unless codegen, SIL/HIL,
Sunray/PX4, ROS2/PX4 runtime integration, or external flight-control deployment
is explicitly in scope. Every generated backend must map into the shared controller ABI in
`04_接口数据契约与时钟频率.md` and pass the backend gates in
`07_验收Gate与交付物.md`.

Layer role: Flight Control. Exactly one backend owns control authority in a
run. PX4 is not required for the current model-optimization slice, but the
mode, arming, stale-command, failsafe, and command echo contracts should
already be compatible with a future PX4/QGC backend.

## 10. PlantRuntime

Responsibilities:

- simulate or represent vehicle dynamics;
- apply control allocation, motor/actuator dynamics, disturbance, and fault
  effects;
- output truth state, events, and plant-level metrics.

Layer role: Runtime Plant / Sensors / HIL, equivalent to the CopterSim role in
an RflySim-style system. It may initially be implemented as MWORKS models, but
it should be described as a runtime plant contract, not merely as a design-time
model file.

The model should evolve toward realistic four-rotor behavior:

- command-to-speed mapping;
- motor speed limit;
- motor first-order lag;
- `thrust = k_f * omega^2`;
- `yaw moment = k_m * omega^2`;
- rotor-center moment;
- body drag and angular damping;
- battery/ESC/thrust-margin effects when required.

Accepted Runtime Plant claims require:

- model/source path and parameter provenance;
- `check_model` or equivalent structural validation where MWORKS is used;
- smoke or scenario simulation evidence for claimed behavior;
- truth-state, event, and key actuator/force/moment outputs;
- explicit source labels for simulated sensors and faults.

## 11. EvidenceManager

Responsibilities:

- write `RUN_MANIFEST`;
- save config snapshots;
- collect MWORKS results, ROS2 bags/summaries, FAST-LIO outputs, planner
  traces, UE logs, screenshots, videos, and metrics;
- record accept/blocker decisions with evidence paths.

EvidenceManager cannot turn weak evidence into acceptance. It only packages and
indexes what the run produced.

Layer role: cross-layer evidence. EvidenceManager records outputs from all
four layers, but cannot grant authority to a layer that did not produce the
required evidence.

For multi-UAV runs, EvidenceManager must preserve member separation:

```text
Results/formation/<scenario_id>/<run_id>/uav_<id>/
```

Formation-level metrics may summarize per-UAV traces, but the raw traces,
controller traces, plant truth, and per-UAV metrics remain inspectable by
`uav_id`.

## 12. Operator Console And GUI Surfaces

MoSim uses multiple GUI surfaces with different authority. Do not collapse them
into one "MWORKS GUI" claim.

| Surface | Primary use | Authority boundary |
|---|---|---|
| Sysplorer/Sysblock GUI | model topology, controller structure, wiring/layout review, MWORKS-native simulation setup | MWORKS model/control evidence only |
| Syslab plots/apps | metrics, comparison figures, report-ready curves, offline analysis | analysis and reporting, not live plant authority |
| MoSim Operator Console | scenario, controller, planner, wind, fault, start/pause/reset intent; echo and status dashboard | sends intent through command packets; cannot bypass authority adapters |
| UE Experiment Console | in-scene demonstration controls and visual status | frontend/review surface only |
| RViz/RViz2/QGC windows | robotics estimator/map/planner/operator review where in scope | review/status surfaces, not final controller metrics |

The short-term implementation does not need a large GUI before Gazebo works.
Use scenario YAML, launch scripts, and evidence bundles as the authoritative
entrypoint. Add a lightweight Operator Console only after the command/echo
schema and Gazebo/Sunray or future Gazebo/ROS2 run path are stable enough that the UI is a thin
frontend over existing commands.

Minimum Operator Console controls:

- scenario, vehicle, map, controller, and planner selection;
- start, pause, stop, reset, land, and record intent;
- wind profile selection and clear;
- per-rotor efficiency fault injection and clear;
- accepted/rejected command echo;
- active backend, clock/rate, stale-command, failsafe, and evidence path status.

The console must not directly edit hidden plant state, publish setpoints outside
the active adapter, label a run passed without evidence, or make planner inputs
from hidden global truth.

### 12.1 Web Operator Console Technology Decision

The approved Operator Console route is a local browser application, not a
MWORKS app and not a first-pass UE-only widget.

Target stack:

```text
Frontend
  -> React + TypeScript + Vite
  -> lightweight component library for forms, tables, tabs, status cards, and charts

Backend
  -> Python FastAPI
  -> REST endpoints for config/run commands and evidence browsing
  -> WebSocket stream for runtime state, command echo, logs, and metric updates

Runtime bridge
  -> current Sunray ROS1/rospy bridge or future ROS2/rclpy bridge process
  -> Gazebo/ROS topic checks, command publication, command echo, and status capture

Storage
  -> scenario YAML, run manifest, and Results directory first
  -> no database for the first implementation
  -> SQLite or DuckDB only after run volume and browsing needs justify it
```

The console should open as `http://localhost:<port>` during development. A
desktop executable or packaged app is not part of the first milestone.

### 12.2 Console Phasing

V0 is not a UI milestone. It is the prerequisite command/runtime layer:

```text
scenario YAML
  -> launch script
  -> CommandPacket
  -> RuntimeEcho
  -> run manifest
  -> evidence bundle
```

V1 is the minimum useful web console:

- select map, UAV model, controller, scenario, and planner;
- start, pause, stop, reset, land, and record;
- select no wind, crosswind, gust, or random disturbance profiles;
- inject or clear rotor1-4 effectiveness faults;
- display Gazebo, ROS topic-rate, UAV pose/velocity/attitude, active backend,
  command echo, stale-command, failsafe, and current evidence path;
- open review entrypoints for Gazebo, RViz point cloud, RViz voxel/local map,
  result curves, and the run manifest.

V2 adds report/demo productivity:

- live altitude, attitude, trajectory-error, control-output, and RMSE charts;
- controller/scenario comparison tables;
- one-click recording hooks;
- experiment summary and report-figure entrypoints.

V3 is the UE in-scene demonstration panel:

- show scene, controller, wind/fault state, task progress, and key metrics;
- optionally forward limited operator intents through the same
  CommandPacket/RuntimeEcho path;
- never bypass the Operator Console backend or authority adapters.

MWORKS integration in the web console is intentionally limited at first. The
first web console controls current Gazebo/Sunray validation runs or future
Gazebo/ROS2 validation runs after that route is reopened, and opens MWORKS
evidence artifacts when needed. It does not drive Sysplorer/Syslab live
simulation until a separate MWORKS automation gate is designed.
