# MoSim系统架构历史草案

> 状态：历史草案 / reference-only，2026-06-24。
>
> 当前Level 0架构入口是 `Docs/Design/架构.md`。本文保留旧版系统骨架、
> 术语和迁移前设计输入，不能作为当前执行入口。若本文与
> `Docs/Design/README.md`、`Docs/Design/架构.md` 或 `Docs/Design/架构/`
> 下专题规范不一致，以活动文档为准。

## 1. 架构结论

MoSim 当前不是通用机器人导航栈，而是面向 A8 四旋翼赛题的控制系统工程。
主线是：

```text
MWORKS/Sysblock 控制器建模与代码生成
  -> 标准 C/C++ controller core
  -> Controller ABI / Adapter
  -> PX4/MAVROS 飞控仿真接口
  -> Sunray/Gazebo plant、传感器和执行器
  -> FAST-LIO / EGO / EGO-Swarm 自主飞行组件
  -> RViz/Gazebo/UE/前端展示与证据
```

其中 MWORKS 是控制算法建模、MIL/SIL、代码生成、等价性测试和报告证据
的主体；Sunray/PX4/Gazebo 是工程级运行基线；FAST-LIO、EGO、EGO-Swarm
是外部自主飞行组件，不搬进 MWORKS 重写。

## 2. 当前运行基线

当前可执行审核路线冻结为：

```text
Ubuntu-20.04 / ROS1 Noetic
  -> References/Sunray
  -> reviewed sunray150_with_mid360
  -> Gazebo Classic
  -> PX4 + MAVROS
  -> px4ctrl
  -> MID360 / FAST-LIO / EGO / RViz review
```

当前不得把以下路线作为正式进度：

```text
Ubuntu-22.04 / ROS2 Humble / PX4 x500
ROS2 直接写 Gazebo motor/actuator topic
Python truth-feedback 控制器
MWORKS CSV 开环回放
fake/static point cloud
只看 RViz/Gazebo 非空画面
```

这些只能作为诊断夹具或历史参考，不能替代当前 Sunray/PX4/Gazebo 主链路。

## 3. 四层职责

| 层 | 权威内容 | 当前规则 |
|---|---|---|
| MWORKS 建模层 | 控制器模型、MIL/SIL、参数优化、代码生成、离线一致性 | 是比赛控制算法主体，但不单独证明工程闭环 |
| 飞控接口层 | PX4、MAVROS、Offboard、EKF、模式、解锁、failsafe | 每次运行只允许一个主动控制后端 |
| Plant/传感器层 | Sunray/Gazebo 机体、动力学、执行器、MID360、IMU、定高、摄像头 | 是当前工程验证 plant 权威 |
| 自主飞行与展示层 | FAST-LIO、EGO/EGO-Swarm、RViz、Gazebo GUI、UE、前端 | 证明感知/规划/展示接入，不拥有控制成功判定 |

任何结果必须说明自己验证的是哪一层。显示层画面对，不等于控制器或定位闭环
通过；MWORKS 模型跑通，也不等于已进入 PX4/Gazebo 工程闭环。

## 4. 最小大系统闭环

当前先完成“最小大系统”，再批量控制器迁移。

最小大系统不是MoSim全部系统，只是后续控制器族、MWORKS代码生成、
规划/集群和展示工作的共同验证台。它只覆盖项目级任务主表中的以下子集：

```text
S1 运行基线与机型环境
S2 状态源、传感器和定位的独立评价子集
S3 单机基础控制基准
S4 轨迹和任务发生器
S5 单机规划与局部地图
S6 多机与集群官方基线子集
S7 MWORKS Golden Slice和代码生成
```

最小大系统包括：

```text
Sunray150 + MID360 装配模型
PX4 + MAVROS + px4ctrl 基线
Gazebo Classic 起飞、悬停、降落、8字、螺旋、阶跃
RViz 默认轨迹、累计点云、栅格/规划显示
FAST-LIO 独立定位与 PX4 EKF 融合门禁
EGO 单机
EGO-Planner-v2 单机
Diff-Planner 单机
EGO-Swarm 2机 / 3机基础隔离与避碰
```

最小大系统完成后，才能把它作为后续控制器和 MWORKS 代码生成的统一验证台。

完整MoSim系统还包括：

```text
S8 控制器族扩展：PID、SE3、DFBC、LMPC/NMPC、INDI、L1等逐个释放
S9 鲁棒、安全和故障容错：扰动、故障、控制分配、安全过滤
S10 真机化与C++化收尾：实时闭环关键路径迁到C++/生成代码
S11 UE/前端/可视化展示：点云、栅格、轨迹、多机、摄像头和报告画面
S12 自动评估、报告和交付：指标、图表、视频、交付包
```

项目级能力任务主表以 `MoSim研发工作流与Agent任务编排规范.md` 的 0.3 节为准。

## 5. 控制器推进顺序

控制器不批量铺开。当前顺序是：

```text
1. px4ctrl 作为黄金基线
2. 官方 PID 作为简单替换模板
3. SE3 Basic 作为结构不同的代表控制器
4. MWORKS Golden Slice
5. 后续控制器逐个释放
```

这样可以先证明：

```text
状态源一致
轨迹参考一致
ATTITUDE_THRUST 输出一致
推力映射集中在 Adapter
Gazebo/Sunray plant 一致
评价指标一致
```

再迁移增强 PID、LQI、DFBC、LMPC、NMPC、INDI、L1、安全滤波、故障容错等
控制器。

## 6. 第一阶段控制接口

第一阶段只实际实现：

```text
ATTITUDE_THRUST
```

控制器 core 输出：

```text
desired_attitude_quaternion
desired_collective_thrust_N
controller_status
controller_diagnostics
```

物理总推力到 MAVROS/PX4 归一化推力的映射只允许放在公共 Adapter 中，
不得散落到各个控制器模型里。

以下接口只保留为规划枚举，不进入第一阶段实现：

```text
BODY_RATE_THRUST
WRENCH
ROTOR_THRUST
ROTOR_SPEED
```

## 7. 状态源边界

当前 px4ctrl 基线状态源：

| 数据 | Topic | 用途 |
|---|---|---|
| 位置、速度、姿态 | `/mavros/local_position/odom` | 控制器主要状态输入 |
| 角速度 / IMU | `/mavros/imu/data` | 控制器角速度输入 |
| 模式、解锁、有效性 | `/sunray/uav_state` | 状态机、显示和诊断 |
| Gazebo truth | 实际 truth pose/odom topic | 评价真值，不静默输入控制器 |

FAST-LIO 不能因为 RViz 点云可见就直接进入控制。正确路线是：

```text
MID360 点云 + 雷达 IMU
  -> FAST-LIO
  -> 输出对齐到飞控中心 / base_link
  -> 完整 pose、quaternion、velocity、covariance、timestamp、status
  -> PX4 EKF external odometry / vision 融合
  -> /mavros/local_position/odom
  -> 同一个 px4ctrl
```

`/mosim/fastlio/odom_aligned` 在定位门禁通过前只能作为被测候选，不得直接
作为控制状态源。

## 8. MWORKS Golden Slice

MWORKS 不等到所有控制器都做完才接入。正确时机是：

```text
最小大系统闭环通过
  -> px4ctrl / PID / SE3 三个代表控制器模板通过
  -> 立即做 MWORKS Golden Slice
  -> 再批量控制器迁移
```

Golden Slice 路线：

```text
冻结上游 px4ctrl 与 Sunray px4ctrl
  -> 差异审计
  -> 抽取 px4ctrl_core
  -> 原包装层 / 抽取 core 离线对齐
  -> MWORKS 重建 px4ctrl_core
  -> MWORKS 生成 C/C++
  -> 四方离线一致性
  -> 接回同一个 Sunray/ROS 包装层
  -> Gazebo 闭环 A/B 对齐
```

离线一致性未通过，不允许进入 Gazebo 闭环。

## 9. 规划与集群边界

EGO、EGO-Planner-v2、Diff-Planner、EGO-Swarm 保留为 ROS 外部规划组件。
它们只输出轨迹或规划参考，不直接拥有 MAVROS 控制话题。

规划链路：

```text
Gazebo/MID360/FAST-LIO 或当前基准状态源
  -> planner map / occupancy / bspline
  -> TrajectoryReference
  -> px4ctrl 或 MWORKS 生成 controller core
  -> ATTITUDE_THRUST Adapter
  -> PX4/MAVROS
  -> Gazebo plant
```

集群第一阶段只做官方链路和工程隔离：

```text
2机 / 3机启动
PX4实例隔离
MAVROS实例隔离
px4ctrl实例隔离
规划Topic隔离
FAST-LIO/点云/地图Topic隔离
基础目标导航与避碰
```

暂不做自研一致性控制、Leader-Follower、CBF、故障成员退出和复杂队形重构。

## 10. 真机化边界

在线闭环关键路径最终必须是 C++ 或 MWORKS 生成 C/C++：

```text
T0: controller core
T1: FAST-LIO odom alignment、PX4 external odometry、trajectory server、
    Controller Adapter、safety/failsafe
T2: 上游 C++ 组件，如 FAST-LIO、EGO、px4ctrl
T3: Python launch、metrics、plot、review、offline compare
```

Python 可以作为实验和证据工具，但不能长期作为正式控制律、状态源适配、
external odometry 发布或安全门禁。

## 11. 当前执行顺序

当前推荐执行流：

```text
G0 文档和路径入口冻结
G1 Sunray/PX4/MAVROS/px4ctrl 基线
G2 起飞、悬停、降落、8字、螺旋、阶跃
G3 FAST-LIO 独立定位与 PX4 EKF 融合门禁
G4 EGO / EGOv2 / Diff-Planner 单机复现
G5 EGO-Swarm 2机 / 3机工程隔离
G6 px4ctrl / PID / SE3 代表控制器模板
G7 MWORKS Golden Slice
G8 后续控制器逐个迁移
G9 UE / 前端 / 报告展示
```

每个 Gate 的完成必须有日志、指标、截图、结果包或源码/静态检查证据。文档
本身不是运行成功证据。

## 12. 禁止事项

当前禁止：

```text
遇到问题后静默换主线
把 Python truth-feedback 当正式控制器
把 ROS2/x500 历史路线当当前 Sunray 证据
把 RViz 点云可见当 FAST-LIO 定位闭环
把 Gazebo truth 静默混入 FAST-LIO 后宣称全雷达定位
把 planner 输出当闭环飞行成功
把 MWORKS 模型仿真当 PX4/Gazebo 部署成功
在离线一致性失败时继续做 Gazebo 闭环
批量铺开控制器后再补接口
```

## 14. 完整系统骨架设计

当前阶段的目标是“对标真机”，不是宣称已经完成真机部署。对标真机的含义是：

```text
用Sunray/Gazebo作为当前工程plant权威；
用真机传感器配置和飞控接口约束仿真系统；
用MWORKS完成控制器建模、参数优化和代码生成验证；
用PX4/MAVROS/Gazebo/RViz证明算法能进入接近真机的闭环链路；
为后续Orin NX、雷迅V6X和真实传感器部署保留C++/生成代码路径。
```

因此完整架构不能只由控制器清单组成，必须包含以下骨架级子系统。

### 14.1 Runtime Plant与真机参数对标

Sunray/Gazebo是当前工程plant权威，MWORKS plant后续向Sunray/Gazebo和真机参数靠拢。
该层需要明确区分：

```text
真机参数：
  质量、惯量、轴距、电机、桨叶、推力/力矩系数、传感器安装位置。

Gazebo参数：
  机体模型、碰撞体、执行器模型、传感器模型、噪声、延迟、地效或阻力近似。

MWORKS参数：
  控制器设计模型、MIL/SIL plant、参数辨识结果、鲁棒性扫描范围。
```

设计原则：

```text
Gazebo/Sunray用于工程闭环验收；
MWORKS用于控制器设计、参数搜索、代码生成和离线一致性；
MWORKS模型应逐步拟合Gazebo/Sunray和真机参数，而不是要求Gazebo强行匹配理想MWORKS模型；
参数不确定性必须进入鲁棒性测试，而不是只追求单一参数下的最小误差。
```

该层最终需要形成：

```text
plant_profile
motor_profile
sensor_profile
disturbance_profile
fault_profile
model_identification_record
```

### 14.2 Trajectory Server与高阶参考统一

所有任务和规划器输出必须先进入统一Trajectory Server，再进入控制器。
控制器不得直接依赖某一个规划器或某一种离散命令格式。

统一链路：

```text
手写任务 / EGO / EGOv2 / Diff-Planner / EGO-Swarm / MWORKS回放
  -> Trajectory Server
  -> 100Hz或控制周期解析求值
  -> p_d, v_d, a_d, jerk_d, snap_d, yaw_d, yaw_rate_d
  -> Controller Core
```

设计原则：

```text
8字、螺旋、阶跃、圆形、目标点必须和规划器轨迹走同一个接口；
EGO等规划器可以低频重规划，但控制器必须拿到时间参数化轨迹的控制周期求值结果；
DFBC、NMPC、INDI等高阶控制器需要jerk/snap时，由Trajectory Server统一提供；
禁止把离散位置点线性插值后宣称支持高阶轨迹跟踪。
```

该层最终需要形成：

```text
trajectory_source_profile
trajectory_evaluation_profile
trajectory_continuity_check
reference_timeout_policy
reference_switch_policy
```

### 14.3 State Estimation与多源状态策略

完整系统必须明确哪些状态进入控制器，哪些进入PX4 EKF，哪些只用于评价或显示。

当前基线：

```text
/mavros/local_position/odom
  -> 控制器主要状态输入

/mavros/imu/data
  -> 角速度/IMU输入

/sunray/uav_state
  -> 模式、解锁、有效性和显示

Gazebo truth
  -> 评价真值，不静默输入控制器
```

FAST-LIO路线：

```text
MID360点云 + 雷达IMU
  -> FAST-LIO
  -> 对齐到飞控中心/base_link
  -> pose、quaternion、velocity、covariance、timestamp、status
  -> PX4 EKF external odometry / vision融合
  -> /mavros/local_position/odom
  -> 同一个Controller Core
```

定高路线：

```text
当前仿真阶段可使用Gazebo定高作为真机激光定高替身；
该定高替身必须标记为height_source_profile；
不得把Gazebo定高混入FAST-LIO后宣称完全由FAST-LIO提供定位；
后续真机切换为实际定高传感器时，控制器接口不应改变。
```

设计原则：

```text
控制器默认只订阅统一StateAdapter输出；
FAST-LIO直接输出只能作为对照实验，主路线应经PX4 EKF融合后进入控制；
Gazebo truth只能作为评价或显式定高替身，不能静默混入XY/yaw；
每次实验必须记录state_source_profile、height_source_profile和truth_profile。
```

### 14.4 控制器平台分层

完整控制器平台必须按链路位置组织，而不是按算法名字平铺。

```text
外环控制器：
  px4ctrl、PID、LQI、SE3、SMC、DFBC、LMPC、NMPC

增强/观测模块：
  AWFF、INDI、L1、DOB/ESO、NN/RBF、Fuzzy gain

安全与故障模块：
  Safety Filter、CBF、Reference Governor、Fault Allocation、控制分配重构

执行器/分配层：
  WRENCH、ROTOR_THRUST、ROTOR_SPEED、故障电机分配
```

第一阶段只实际打通：

```text
Controller Core
  -> ATTITUDE_THRUST
  -> Adapter
  -> MAVROS/PX4
  -> PX4姿态环/角速度环/控制分配
```

后续扩展原则：

```text
SMC第一版优先外环ATTITUDE_THRUST；
INDI不作为普通外环控制器平替，优先作为姿态/角速度或高动态增强模块；
Fuzzy/NN/RL优先作为增益调度、扰动补偿或有界残差，不直接端到端替代飞控；
BODY_RATE_THRUST、WRENCH和ROTOR级接口必须在ATTITUDE_THRUST模板稳定后再释放。
```

每个控制器或模块必须进入同一张实现覆盖矩阵：

```text
链路位置
输入需求
输出层级
是否复用PX4内环
是否替换PX4某一环
MWORKS模型状态
C/C++生成状态
Gazebo/Sunray闭环状态
指标证据状态
禁止声明
```

### 14.5 故障、扰动与安全实验层

风扰、故障注入和安全约束不是前端装饰，而是系统架构中的实验与控制层。

```text
扰动注入：
  常风、阵风、拖曳、地效近似、负载变化、模型参数摄动。

执行器故障：
  电机推力衰减、单电机失效、响应延迟、饱和。

传感器退化：
  定位噪声、延迟、丢帧、FAST-LIO漂移、定高异常。

安全过滤：
  位置/速度/倾角/推力约束、避障安全距离、failsafe触发条件。

控制分配：
  WRENCH到电机/旋翼分配、故障重构、饱和处理。
```

每个扰动或故障必须有：

```text
profile
注入时刻
注入幅值
持续时间
影响对象
评价指标
恢复判据
```

### 14.6 规划、地图与集群汇合点

规划器和集群算法不拥有控制权。它们通过统一轨迹接口和状态/地图接口接入。

```text
Gazebo / MID360 / FAST-LIO
  -> 点云地图 / 局部栅格 / planner map
  -> EGO / EGOv2 / Diff-Planner / EGO-Swarm
  -> Trajectory Server
  -> Controller Core
  -> PX4/MAVROS
```

EGO-Swarm第一阶段只证明官方工程链路和多机隔离：

```text
2机/3机启动
PX4实例隔离
MAVROS实例隔离
```

### 14.7 UE/前端实验平台

UE/前端目标是RflySim式实验平台，而不是只做独立网页或静态可视化。
该平台负责实验编排、可视化和证据采集，不拥有控制器、定位或规划成功判定。

实验平台至少应覆盖：

```text
地图/场景选择
控制器选择
增强模块开关
状态源Profile显示
轨迹任务选择
扰动/故障滑块
安全约束开关
单机/多机模式选择
运行/暂停/停止/重置
```

显示窗口至少包括：

```text
RViz累计点云地图
RViz栅格地图/规划结果
RViz飞机三轴和轨迹
Gazebo动画
UE场景和状态面板
多机摄像头第一视角
指标曲线和实验报告入口
```

三机展示时，目标窗口结构可以是：

```text
2个公共窗口：
  点云/栅格/轨迹综合窗口
  Gazebo或UE总览窗口

3个机载视角窗口：
  UAV1 camera
  UAV2 camera
  UAV3 camera
```

即3架飞机时可以形成2+3=5个审核窗口。

### 14.8 统一评价与证据包

完整系统最终靠统一实验证据包验收，而不是靠单次截图或口头描述。

每次实验必须生成：

```text
run_id
scenario_profile
plant_profile
controller_profile
state_source_profile
trajectory_profile
disturbance_profile
fault_profile
raw_log
metrics
plots
rviz/gazebo/ue screenshots或video
acceptance_summary
```

基础任务：

```text
起飞-悬停-降落
阶跃
8字
螺旋
圆形
目标点
EGO单机
EGOv2单机
Diff-Planner单机
EGO-Swarm 2机/3机
```

评价指标：

```text
RMSE
稳态窗口误差
最大误差
超调量
调节时间
控制输出饱和
能耗或推力积分
最小安全距离
故障恢复时间
定位误差增量
轨迹中断次数
丢帧率
```

所有控制器、状态源和规划器都必须在同一评价框架下比较。高级控制器不能
用单独指标绕过基础基线，也不能用容错模块掩盖基础控制器或状态源问题。

## 15. 结论

当前架构可以概括为：

```text
先把 Sunray/PX4/Gazebo/FAST-LIO/EGO/EGO-Swarm 组成的最小大系统跑通；
再用 px4ctrl、PID、SE3 建立控制器替换模板；
随后立即做 MWORKS Golden Slice；
最后逐个迁移高级控制器、故障容错、集群和展示系统。
```
