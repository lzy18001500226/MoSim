先给结论：

**固定翼，甚至“战斗机外形”的六自由度仿真，是能做的；但不应该以 Gazebo 的 LiftDrag 插件作为主要飞行动力学模型。**
你们更合理的主线应当是：

```text
ArduPlane
    负责固定翼飞控、舵面输出、任务与安全逻辑

JSBSim
    负责固定翼六自由度动力学、气动、发动机、舵面、起落架和风场

ROS2
    负责制导算法、任务管理、载荷管理、数据记录和系统通信

UE
    负责高质量战斗机、舵面、起落架和发射过程的显示

Gazebo
    不再作为固定翼主动力学后端
    仅在特定机器人传感器、场景交互或几何碰撞需求中辅助使用
```

你描述的“固定翼搭载、空中释放、涵道火箭、制导算法”已经接近武器系统范畴。我不能协助设计真实目标捕获、末制导、杀伤、发射包线或可部署武器参数。下面按**非武器化空投飞行试验体、探空试验体或通用制导算法验证平台**讨论架构和开源工具。

# 一、固定翼比四旋翼难在哪里？

你的感觉是对的。

四旋翼的基础动力学主要是：

```text
质量与惯量
4个电机位置
4个推力系数
4个反扭矩系数
电机响应时间
机身阻力
```

即使模型比较粗，只要总推力、控制分配和惯量大致合理，往往就能飞起来。

固定翼尤其是战斗机，需要的不只是几个参数，而是一个**高维气动数据库**：

```text
Cx、Cy、Cz
Cl、Cm、Cn

这些系数又可能依赖：
    马赫数 Mach
    迎角 α
    侧滑角 β
    滚转角速度 p
    俯仰角速度 q
    偏航角速度 r
    襟翼偏角
    副翼偏角
    升降舵偏角
    方向舵偏角
    鸭翼偏角
    前缘襟翼偏角
    起落架状态
    减速板状态
    外挂状态
```

因此真正困难的不是“让 UE 里的鸭翼转起来”，而是：

> **鸭翼转动以后，到底会对升力、阻力、俯仰力矩、侧向力矩产生多大影响。**

现代战斗机还可能存在：

```text
放宽静稳定
飞控增稳
高迎角非线性
涡升力
气动耦合
跨声速激波
进气道和发动机耦合
推力矢量
外挂物干扰
```

这些才是高保真战斗机模型真正昂贵的部分。

```text
A-4
F-4N
F-104
F-15
F-16
F-22
T-37
T-38
X-15
XB-70
P-51D
C-130
Concorde

```

这些都是直接可研究的六自由度模型。JSBSim 官方也明确说明，名称对应现实军用或商用飞机的模型，均是依据教材、NASA 技术报告和公开资料制作的近似模型，仅适合教育、研究和娱乐用途，不包含敏感或专有数据。([GitHub][1])

例如 JSBSim 自带的 F-16 模型，其说明列出了 NASA TP-1538 风洞/模拟研究等公开资料来源，并包含几何、气动和飞控系统文件。([GitHub][2])

```text
参考模型
控制算法基准
文件结构示例

```

但不能把它们当作：

```text
真实F-16数字孪生

真实作战包线模型

```

# 三、襟翼、舵面、鸭翼、起落架能不能模拟？

## 3.1 舵面和鸭翼

可以。

JSBSim 不要求飞机只能具有传统的“副翼—升降舵—方向舵”三套控制面。其飞控系统由 XML 中的控制通道、执行机构、滤波器、限幅器、混控器和气动系数共同定义；官方文档明确指出，不同飞机可以有不同数量和布置的控制输入。([JSBSim Team][3])

所以可以定义：

```text
left_aileron
right_aileron
left_flap
right_flap
rudder
elevator
left_canard
right_canard
leading_edge_flap
speed_brake
thrust_vector_pitch
thrust_vector_yaw
```

鸭翼在动力学里并不一定非要成为一个真正独立刚体。常见做法是：

```text
鸭翼执行机构输出 δc
    ↓
进入气动系数查表或函数
    ↓
改变升力、俯仰力矩、阻力
```

可视化端再根据同一个 `δc` 属性转动 UE 或 FlightGear 中的鸭翼模型。

也就是说：

```text
JSBSim：
    计算鸭翼气动影响

UE：
    显示鸭翼转动
```

两者使用同一个舵面状态，但职责不同。

## 3.2 舵机动态

JSBSim 具有执行机构和机械运动组件，可以表示：

```text
最大偏转角
最小偏转角
偏转速率
响应延迟
滞后
死区
饱和
故障卡死
```

`FGKinemat` 就用于模拟舵面、起落架机构等运动部件，`FGActuator` 则负责执行机构的动态和限制。([JSBSim Team][4])

所以不只是：

```text
指令 20°
    → 舵面瞬间到20°
```

而可以是：

```text
指令20°
    ↓
舵机以60°/s运动
    ↓
受最大偏角限制
    ↓
实际舵面逐渐到位
```

## 3.3 起落架

JSBSim 原生具有地面反作用和起落架模型，可以计算：

```text
轮胎接触
弹簧与阻尼
地面摩擦
刹车
转向
接触点受力
起落架相对质心的位置
```

`FGGroundReactions` 管理起落架接触，`FGLGear` 计算起落架作用产生的力和力矩。([JSBSim Team][5])

但是要区分两件事：

```text
动力学上的起落架：
    接触点、弹簧、阻尼、摩擦、刹车

视觉上的起落架：
    舱门动画、收放机构、轮子转动
```

动力学由 JSBSim 处理，复杂收放动画更适合 UE 或 FlightGear 处理。

## 3.4 ArduPlane 是否支持这些输出？

ArduPlane 可以配置传统副翼、升降舵、方向舵，也支持 elevon、flaperon、V-tail、airbrake 和可收放起落架等输出功能。([ArduPilot.org][6])

鸭翼没有必须叫作“Canard”的专用核心物理概念。可以通过：

```text
自定义Servo Function映射
飞控混控
或者外部控制分配
```

把俯仰、滚转等控制量映射到鸭翼和其他舵面。

因此 AP 不是主要瓶颈，真正的瓶颈还是：

```text
鸭翼偏转对气动力矩的真实影响数据
```

# 四、为什么不建议用 Gazebo 作为战斗机主动力学？

Gazebo 并非完全不能模拟固定翼。

新 Gazebo 提供 `LiftDrag` 和 `AdvancedLiftDrag` 系统，可以配置：

```text
翼面积
零迎角升力
阻力
升力曲线斜率
侧滑导数
俯仰/滚转/偏航力矩导数
失速迎角
平均气动弦
翼效率
控制舵面关节
```

还可以通过 `control_joint_name` 把某个关节的偏转加入气动计算。([Gazebo][7])

这对以下对象已经足够：

```text
普通固定翼无人机
低速小飞机
滑翔机
基础翼面控制验证
简单VTOL转换机
```

但对战斗机的问题是，Gazebo 的这种模型本质上更接近：

```text
每个翼面一个简化升阻模型
+
若干线性/分段气动导数
```

很难自然覆盖：

```text
大迎角涡升力
跨声速激波
高马赫数气动表
强烈侧向耦合
放宽静稳定
鸭翼—主翼干扰
发动机进气畸变
复杂舵面调度
```

所以我的判断是：

| 用途             |  Gazebo |       JSBSim |
| -------------- | ------: | -----------: |
| 普通固定翼无人机       |      可用 |          更合适 |
| ArduPlane SITL |      可用 |       官方成熟路线 |
| 起降与简单地面碰撞      |      较强 |        原生也支持 |
| 战斗机气动数据库       | 不适合做主模型 |          更合适 |
| 高迎角、跨声速查表      |    很难维护 |     可通过气动表表达 |
| 飞控系统与舵面调度      |  需要自研插件 |    原生 FCS 体系 |
| 批处理与参数扫描       |      一般 |           很强 |
| UE高质量渲染连接      |     可桥接 | 官方已有 UE 接口参考 |

JSBSim 本身就是数据驱动、非线性六自由度飞行动力学模型，可以配置气动、推进、起落架和飞控系统，并支持独立批处理或嵌入 UE 等应用。([JSBSim Team][8])

**所以固定翼主线应该从 Gazebo 切换到 JSBSim。**

Gazebo仍可保留，但不要让它和JSBSim同时计算同一架飞机的六自由度状态，否则会形成“双物理真值”。

# 五、AP 固件能不能形成可迁移路线？

可以，而且 **ArduPlane + JSBSim 是官方支持的组合**。

ArduPilot 官方文档支持使用标准 JSBSim 运行 Plane SITL，并允许通过自定义模型名称加载自己的 JSBSim 飞机模型。([ArduPilot.org][9])

合理链路是：

```text
ArduPlane SITL
    输出舵面和油门命令
            ↓
JSBSim
    舵机动态
    气动力
    发动机
    起落架
    风场
    六自由度积分
            ↓
虚拟IMU/GPS/空速/状态
            ↓
ArduPlane SITL
```

后续迁移硬件时：

```text
仿真：
    ArduPlane SITL + JSBSim

硬件在环：
    真实飞控硬件 + JSBSim

实机：
    真实飞控 + 真实飞机
```

上层 ROS2 任务和控制接口尽量不变。

不过这里有一个重要限制：

> **ArduPlane 可以负责普通固定翼、飞翼、高速模型机和复杂舵面配置，但不能因为用了 ArduPlane，就自动拥有真实战斗机的增稳、包线保护和高迎角控制律。**

现代战斗机往往依赖全权限数字电传飞控。AP 可以作为基础固定翼载机飞控，但若模型本身是放宽静稳定的战斗机，需要额外设计增稳和控制分配，而不能简单套用普通 RC 固定翼参数。

因此建议最初选择：

```text
静稳定或弱放宽静稳定的通用喷气固定翼模型
```

而不是一开始做高度不稳定的鸭式战斗机。

# 六、气动参数到底怎么获得？

这是最关键的问题。

## 6.1 已有公开模型

最快的路线是先用公开模型：

```text
JSBSim F-16
JSBSim F-15
JSBSim F-104
JSBSim A-4
JSBSim T-38
JSBSim X-15
```

这些可以帮助验证：

```text
ArduPlane接口
ROS2接口
舵面动画
起落架动画
UE显示
控制算法
状态和数据结构
```

JSBSim 官方提供的 F-16 模型就引用了 NASA TP-1538 等公开资料；NASA 还公开了多篇关于 F-16、F-16XL 和衍生构型的风洞、气动建模与控制面数据报告。([GitHub][2])

但这些只适合做：

```text
算法基准模型
公开资料近似模型
```

## 6.2 从几何初步估算

对于自研固定翼，可以使用 OpenVSP / VSPAERO：

```text
输入：
    机身
    主翼
    尾翼
    鸭翼
    舵面
    几何尺寸

输出或估计：
    升阻特性
    稳定性导数
    控制面导数
    配平趋势
```

VSPAERO支持控制面分组、稳定性导数以及亚声速和超声速薄面/面板分析。([OpenVSP][10])

但要清楚其边界：

```text
适合：
    初始概念设计
    小迎角
    附着流
    趋势分析
    控制面相对效果
    初始稳定性导数

不够可靠：
    大迎角分离流
    强涡流
    跨声速激波
    进气道耦合
    鸭翼—主翼强干扰
    外挂分离气动
```

因此 VSPAERO 生成的是**第一版模型**，不是最终真值。

## 6.3 Aeromatic

JSBSim 的 Aeromatic 可以根据飞机类别、尺寸、质量和发动机等信息生成一个“合理但简化”的起始模型。官方也明确说明，它使用简化假设生成可用的初始配置。([JSBSim Team][11])

它适合：

```text
先把模型跑起来
验证接口
建立基础配平
验证飞控闭环
```

不适合：

```text
直接作为高保真战斗机模型
```

## 6.4 CAD估算质量和惯量

质量和惯量至少可以分层获得：

```text
几何模型：
    计算体积和初始惯量

部件质量：
    发动机
    燃料
    电池
    飞控
    载荷
    起落架

组合：
    得到总质心和惯量矩阵
```

对于实物缩比机，可以通过：

```text
称重
支点测质心
摆动试验
转动惯量试验
```

获得更可信参数。

## 6.5 飞行试验系统辨识

真正可迁移模型最终要依赖飞行数据：

```text
输入：
    舵面命令
    油门
    飞行速度
    姿态
    角速度
    加速度
    高度

识别：
    稳定性导数
    控制面效率
    阻尼导数
    发动机响应
    阻力模型
```

NASA 公开研究也表明，F-16 气动模型可通过风洞或飞行数据建立非线性参数模型，并对力和力矩系数进行识别。([NASA技术报告服务器][12])

因此正确流程是：

```text
公开资料/几何估算
    ↓
初始模型
    ↓
仿真配平
    ↓
缩比试验机飞行数据
    ↓
参数辨识
    ↓
更新模型
    ↓
重复验证
```

# 七、不要把“完全精确”设为第一阶段目标

你真正需要先明确的是模型用途。

## Level 0：动画模型

```text
目的：
    看起来像战斗机
    舵面、起落架和载荷会动

不要求：
    动力学可信
```

## Level 1：控制算法模型

```text
目的：
    验证姿态控制
    轨迹跟踪
    自动起降
    AP接口

要求：
    质量惯量合理
    基础气动导数合理
    舵面方向和效率合理
```

## Level 2：飞行包线模型

```text
目的：
    不同速度、高度、迎角下控制
    失速
    跨马赫区间
    起降和大机动

要求：
    多维气动表
    发动机模型
    控制面调度
    风洞或公开试验数据
```

## Level 3：真实战斗机数字孪生

```text
目的：
    精确预测真实军机性能和任务结果

需要：
    专有气动数据库
    发动机数据
    电传飞控律
    结构弹性
    进气道与外挂数据
    实飞辨识数据
```

最后一级对个人或普通开源团队基本不现实。

但你要做算法验证，通常 **Level 1～2 的代理模型就足够**。

# 八、你这个需求最合理的系统架构

把项目拆成两个相互独立的飞行器实体。

## 8.1 载机

```text
Carrier Aircraft
    Flight Dynamics:
        JSBSim

    Autopilot:
        ArduPlane SITL / HITL

    Control Surfaces:
        副翼
        升降舵
        方向舵
        襟翼
        鸭翼，可选
        减速板
        起落架

    Rendering:
        UE

    System Bus:
        ROS2
```

## 8.2 非武器化空投试验体

```text
Released Test Vehicle
    Flight Dynamics:
        JSBSim
        或 RocketPy/OpenRocket用于早期无制导火箭轨迹基准

    Guidance:
        ROS2/C++算法模块
        仅验证通用轨迹跟踪和姿态稳定

    Control Surfaces:
        独立执行机构模型

    Propulsion:
        简化、公开、非武器化推力模型

    Rendering:
        UE
```

OpenRocket 是开源的模型火箭设计与六自由度仿真工具；RocketPy 则提供非线性六自由度、变质量、天气、分级和离散度分析，适合探空或高功率研究火箭的轨迹分析。([OpenRocket][13])

不过它们主要针对：

```text
模型火箭
探空火箭
垂直或常规发射
弹道与回收分析
```

如果试验体具有：

```text
主动舵面
升力体
复杂制导
空中释放
强气动机动
```

统一使用 JSBSim 往往更合适，因为 JSBSim本身可以描述飞机、火箭、推进系统以及任意外力和力矩。([GitHub][14])

# 九、空中释放应该怎么建模？

为了避免“双物理真值”，不建议让 Gazebo 算载机，而 JSBSim 算释放物。

更清晰的方式是使用一个**仿真编排器**：

```text
Simulation Orchestrator
    ├── Carrier JSBSim Instance
    └── Test Vehicle JSBSim Instance
```

## 释放前

```text
试验体状态：
    由载机位姿
    + 挂点相对位姿
    计算得到

试验体不独立积分
```

## 释放瞬间

```text
初始化试验体：
    位置 = 挂点世界位置
    姿态 = 载机姿态 × 安装姿态
    速度 = 载机线速度 + 挂点转动速度
    角速度 = 载机角速度
```

## 释放后

```text
载机：
    继续由Carrier JSBSim积分

试验体：
    由自己的JSBSim实例独立积分

UE：
    显示两个Actor
```

释放阶段真正困难的是短时间内的近场气动干扰和碰撞。如果第一阶段只是验证通用控制算法，可以先采用：

```text
简化挂点释放
初始扰动随机化
安全间隔监测
不做复杂载机尾流
```

后续再增加：

```text
载机尾流近似
随机释放扰动
舵机延迟
质量和质心误差
气动系数不确定性
```

Gazebo确实提供可动态解除父子模型连接的 `DetachableJoint`，适合机器人载荷分离演示。([Gazebo][15])
但如果你的主要飞行动力学在JSBSim中，最好不要再让Gazebo负责释放后的六自由度物理，否则状态权威会混乱。

# 十、涵道推进部分应怎样处理？

这是整个需求中最难获得可信参数的部分。

涵道类推进系统的推力通常不只是：

```text
推力 = 常数
```

而可能受到：

```text
时间
马赫数
高度
进气状态
质量流量
燃料状态
压力
温度
姿态和迎角
```

影响。

如果你的目的只是**验证通用制导和控制算法**，第一阶段完全没有必要建立内部燃烧和进气道模型。

可以使用一个代理模型：

```text
输入：
    时间
    Mach
    高度

查表输出：
    推力
    质量流率
    推力作用点
```

并增加不确定性：

```text
推力 ±10%～20%
点火延迟随机
燃烧时间随机
质心随质量变化
推力方向误差
```

这样验证的是：

```text
算法在推进不确定条件下是否稳定
```

而不是：

```text
推进系统内部设计是否正确
```

精确涵道推进模型通常需要专业试验数据、燃烧模型和进气道数据，不应成为你们平台第一阶段的阻塞项。

```text
ArduPlane
```

```text
JSBSim F-16或F-15

独立控制器或AP适配
```

```text
验证舵面
```

这里不要先修改成自己的战斗机构型。

```text
Generic Canard-Delta Research Aircraft
```

通过：

```text
OpenVSP几何
VSPAERO初始导数
JSBSim气动模型
```

实现：

```text
鸭翼
三角翼
方向舵
襟副翼
起落架
喷气推进代理模型
```

## 阶段四：空投惰性试验体

先不加推进和主动制导：

```text
载机飞行
挂载
释放
自由飞行

```

只解决：

```text
多实体状态
释放初始化
坐标转换
UE显示
数据同步
```

增加：

```text
参数随机化
```

不涉及目标搜索、末制导或真实武器发射包线。

```text
公开数据

飞行日志
```

逐步更新：

```text
气动系数
舵面效率

质量与惯量
```

# 十三、最终判断

**固定翼和四旋翼不应该共用同一个物理主后端。**

你们长期平台更合理的多后端架构是：

```text
四旋翼工程仿真：
    Gazebo + PX4

固定翼工程仿真：
    JSBSim + ArduPlane

高保真显示：
    UE

系统通信：
    ROS2

强化学习：
    MuJoCo / Genesis / JSBSim Python

火箭与研究飞行体：
    JSBSim
    RocketPy/OpenRocket作为独立基准
```

最重要的原则是：

```text
共享：
    ROS2接口
    VehicleState
    SensorData
    SimulationClock
    UE Renderer
    Experiment Manager
    日志和评价体系

不强行共享：
    飞行动力学后端
```

所以固定翼并不会破坏你们现在的架构，反而说明之前设计的：

```text
Core API
    +
可插拔Physics Backend
    +
独立Renderer
```

是正确的。

真正困难的不是代码框架，而是模型可信度。你不需要一开始得到“真实战斗机的全部参数”，而应先建立一个**公开、可解释、可校准的通用固定翼/鸭式研究模型**，用它验证系统、控制与多实体释放流程，再逐步提高气动精度。
