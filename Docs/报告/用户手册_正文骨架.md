# MoSim Studio 用户手册

> 证据收敛稿，2026-07-31。Studio 是 MWORKS 的任务配置与手动打开入口，不是
> 自动仿真器，也不以界面显示代替模型检查、仿真或性能结论。

## 1. 使用范围与当前状态

### 1.1 本手册覆盖的工作流

```text
选择任务和控制器 -> 写入配置 -> 打开 FormalRunner
-> 在 MWORKS 中 CheckModel -> 用户人工点击仿真
-> 查看 Result.msr/metrics -> 需要时在 MWORKS 中点击代码生成
```

Studio 不会因为窗口打开、配置写入或模型被打开而自动加载结果，更不会自动启动
仿真。MWORKS 授权、Syslab/TyAppDesigner 环境和用户在原生 MWORKS 窗口中的操作
是前置条件。

### 1.2 功能状态表

| 功能 | 当前状态 | 证据/权威源 | 使用时的边界 |
|---|---|---|---|
| 控制器目录 | 48 个设计条目 | `Config/control_platform/control_scheme_catalog.json` | 目录条目不等于实现或性能通过 |
| MWORKS 实现模块 | 46 个，且其 `current_model_file` 均存在 | `Config/control_platform/current_model_entry_map.json` | 实现不等于性能通过 |
| Studio 正式入口 | 44 条 FormalRunner 手动打开入口 | `Config/control_platform/model_studio_task_routes_v1.toml` | 可打开不等于已仿真或通过 |
| 名义 ClimbPath 50 s | G2 17/48 通过；G3 有效通过 28/48、失败 20/48 | `Results/control_platform/phase2_full_48_climbpath/g3_repair/G3_STATUS.json` | 失败按原始四类保留 |
| 七场景 | 14 条总记录，12 条有效、2 条无效负样本 | `Results/control_platform/seven_scenario_ab_v2/` | 仅 Official PID 与 px4ctrl 两条代表控制器 |
| 灵敏度 | 24 条：17 通过、3 物理门限失败、4 执行阻塞 | `Results/control_platform/sensitivity_analysis_long_v1/SENSITIVITY_LONG_V1_CLOSEOUT.json` | 只代表已测网格 |
| px4ctrl 代码生成与 SIL | 已完成图形模型到 C、构建及 50 s MWORKS SIL | `src/control/codegen/px4ctrl/`；`Results/control_platform/px4ctrl_codegen_sil_v1/` | Gazebo/PX4 运行时部署待独立验证 |

### 1.3 不应从 Studio 界面推断的事项

以下状态必须从原始记录确认，不能由按钮、窗口、动画或日志文字推断：

1. 某控制器是否通过位置误差门限；
2. 结果文件是否已生成且指标完整；
3. 生成 C 是否已在目标平台构建；
4. Gazebo/PX4、QGC、RViz 或 UE 运行时是否已完成部署验证。

## 2. 环境与启动

### 2.1 设置项目根变量

将项目解压或克隆到任意目录后，先定义 `MOSIM_ROOT`。不要把本手册中的路径替换为
某一台机器的固定用户目录。

Windows PowerShell：

```powershell
$MOSIM_ROOT = (Resolve-Path '<解压目录>\MoSim').Path
$env:MOSIM_ROOT = $MOSIM_ROOT
Set-Location $MOSIM_ROOT
```

Linux/WSL：

```bash
export MOSIM_ROOT="/path/to/MoSim"
cd "${MOSIM_ROOT}"
```

后续 Windows 示例使用 `$MOSIM_ROOT\...`，Linux/WSL 示例使用
`${MOSIM_ROOT}/...`。

### 2.2 前置条件

1. MWORKS、Sysplorer、Sysblock 与 Syslab 已安装并已完成当前机器的授权。
2. Syslab 环境可加载 Julia 模块 `ObjectOriented` 与 `TyAppDesigner`。
3. 正式模型包根为 `$MOSIM_ROOT\Models\MoSimQuadrotorModel\package.mo`。
4. 不要把其他 `package.mo` 作为第二个项目根重复加载。

### 2.3 启动 Model Studio

`apps/model_studio/` 当前没有 `Project.toml`，因此不要使用
`julia --project=. src\app.jl` 作为启动方法。应在已授权的 MWORKS Syslab 环境中
执行（Windows 与 Linux/WSL 均使用环境变量）：

```julia
include(joinpath(ENV["MOSIM_ROOT"], "apps", "model_studio", "src", "app.jl"))
```

出现 Studio 窗口不代表 MWORKS 已加载模型或已运行仿真。窗口启动失败时，先核查
MWORKS 授权和 Syslab/TyAppDesigner 可用性，而不是假定控制器或模型失败。

### 2.4 Codex CLI 构建（可选）

Model Studio 提供基于 Codex CLI 的 AI 辅助功能（第四栏）。该功能为**可选**；
跳过此步骤不影响核心仿真流程。

#### 2.4.1 依赖安装

**Windows：**

访问 <https://rustup.rs/> 下载 `rustup-init.exe` 并安装。安装完成后重启终端使
环境变量生效。

**Linux / macOS：**

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"
```

验证安装：

```bash
cargo --version
# 预期输出：cargo 1.x.x 或更高
```

#### 2.4.2 构建

Windows PowerShell：

```powershell
Set-Location "$env:MOSIM_ROOT\src\Agent"
.\build_codex.ps1
```

Linux / macOS：

```bash
cd "${MOSIM_ROOT}/src/Agent"
./build_codex.sh
```

两个构建脚本均调用 `cargo build --locked --release --bin codex`，首次构建可能在
本地 Cargo 缓存未就绪时下载锁定依赖。

#### 2.4.3 验证

Windows PowerShell：

```powershell
& "$env:MOSIM_ROOT\src\Agent\codex-main\codex-rs\target\release\codex.exe" --version
```

Linux / macOS：

```bash
"${MOSIM_ROOT}/src/Agent/codex-main/codex-rs/target/release/codex" --version
```

预期输出为非空的 Codex 版本字符串，例如 `codex-cli 0.0.0`。只有目标机器实际
通过该检查后，才可将本机 Codex CLI 视为可用。

#### 2.4.4 认证（首次使用）

构建完成后，需要登录 Codex CLI 以启用 GPT 功能：

Windows PowerShell：

```powershell
& "$env:MOSIM_ROOT\src\Agent\codex-main\codex-rs\target\release\codex.exe" login
& "$env:MOSIM_ROOT\src\Agent\codex-main\codex-rs\target\release\codex.exe" login status
```

Linux / macOS：

```bash
"${MOSIM_ROOT}/src/Agent/codex-main/codex-rs/target/release/codex" login
"${MOSIM_ROOT}/src/Agent/codex-main/codex-rs/target/release/codex" login status
```

认证状态由 Codex 的用户配置保存（通常在 `~/.codex/` 或
`%USERPROFILE%\.codex\`），不写入 `MOSIM_ROOT`。AI 助手无法使用不影响
MWORKS 核心仿真、结果复核或 px4ctrl 代码生成。

#### 2.4.5 故障排查

| 错误 | 原因 | 解决方案 |
|---|---|---|
| `cargo: command not found` | Rust 未安装 | Windows：重新从 <https://rustup.rs/> 安装并重启终端；Linux/macOS：执行 `curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs \| sh`。 |
| `linker 'cc' not found` | 缺少 C 编译器（Linux） | Ubuntu：执行 `sudo apt install build-essential`。 |
| 找不到 MSVC 工具链（Windows） | 缺少 C++ 构建工具 | 安装 Visual Studio Build Tools，并勾选 “Desktop development with C++”。 |
| 构建超时 | 网络慢或磁盘空间不足 | 检查网络连接与磁盘空间（建议至少预留约 2 GB）。 |
| `codex login` 失败 | 网络问题或用户配置错误 | 检查网络连接；参考 `src/Agent/README.md` 中的配置说明。 |

## 3. 配置权威源与入口口径

### 3.1 唯一权威配置源

Studio 实际读取的任务路由表是：

```text
$MOSIM_ROOT\Config\control_platform\model_studio_task_routes_v1.toml
```

该结论来自 `apps/model_studio/src/app.jl` 中的
`MODEL_TASK_ROUTE_CATALOG` 与 `TOML.parsefile`，并与
`Scripts/ui/model_studio_task_config.py` 的读取路径一致。路由表声明任务、
控制器 ID、FormalRunner 全类名、源文件和输出边界；`available=true` 的 44 条
即为可写配置并手动打开的正式入口。

`$MOSIM_ROOT\Config\control_platform\mworks_app_entrypoints.json` 是历史设计
文件，不是当前 Studio 运行时的权威配置源。它保留在仓库用于追溯，不应据此判断
当前可打开入口数量或代码生成状态。

### 3.2 44 条正式入口如何理解

44 条是路由表中 `available=true` 并且 `runner_file` 实际存在的记录。它们覆盖
PID、线性鲁棒、非线性自适应、滑模、预测控制、几何/平坦和自研控制器等家族。
完整的 “控制器 ID -> Runner 全类名 -> 文件路径” 索引见
`$MOSIM_ROOT\RELEASE_CHECKLIST.md`。

下列事实应分别理解：

| 项目 | 含义 |
|---|---|
| 48 个目录条目 | 设计清单，不表示全部实现或通过 |
| 46 个实现模块 | 有 MWORKS Modelica 源码，不表示性能通过 |
| 44 个 Studio 入口 | 可以写配置并手动打开的正式全机入口 |
| 28/48 G3 有效通过 | 当前名义 ClimbPath 50 s 的结果状态 |

## 4. 在线建模验证页

### 4.1 可配置项目

在“在线建模验证”页中，用户可选择：

1. UAV 数量：1 至 9；
2. 验证任务：基础 ClimbPath 50 s、悬停保持、阶跃响应、8 字轨迹、螺旋上升，
   以及单机/三机的专用任务；
3. 控制器家族与实例；
4. 风扰、参数失配、电机效率、故障开始时刻和故障目标；
5. 输出边界及由路由表确定的 FormalRunner。

任务与故障/风扰/参数失配是可组合的输入。选择三机任务或自主避障任务时，页面会
按已登记的专用路由限制可选控制器；这不是对其他控制器性能的否定。

### 4.2 写入配置

选择完成后点击“写入配置”。该操作将当前组合交给项目配置写入脚本，并冻结当前
任务的手动交接信息。写入成功只意味着配置文件已被更新；仍需在 MWORKS 中打开
模型并自行执行 CheckModel 和仿真。

若按钮不可用，优先检查：

1. 所选控制器是否在权威路由表中 `available=true`；
2. 所选任务是否是该入口允许的正式任务；
3. 控制器实例切换后是否重新选择了有效任务；
4. 控制台是否报告缺失 Runner 或边界合同。

不要通过修改旧 `mworks_app_entrypoints.json` 绕过这些条件。

### 4.3 打开仿真模型与人工仿真

点击“打开仿真模型”后，Studio 只请求打开当前 `runner_class`。若 MWORKS 原窗口
从最大化变为普通窗口，这是原生窗口管理行为，不改变模型、配置或结果。打开后由
用户完成：

1. 在 MWORKS 中确认模型类、Profile 与场景参数；
2. 运行 CheckModel；
3. 人工点击仿真；
4. 在结果查看器读取 Result.msr 或由指标脚本读取 `metrics/METRICS.json`；
5. 将结果状态与 `G3_STATUS.json` 或对应场景记录区分保存。

## 5. 实时联合仿真页

“实时联合仿真”页使用与在线建模页相同的任务选择和控制器路由概念，但它不把
后端连接、运行时发布或窗口出现视为控制性能验收。该页的配置需要由当前后端的
实际连接状态确认；无法连接时保留为连接问题，不应改写 MWORKS 名义或七场景
结果。

## 6. 代码生成页

### 6.1 操作原则

代码生成页只负责引导用户打开 MWORKS 中已登记的代码生成模型。导出动作由用户
在 MWORKS 原生“代码生成”功能区中执行；Studio 不自动替用户点击导出，也不
把页面状态写成编译通过。

### 6.2 px4ctrl 交付物

已导出的 px4ctrl C 代码和独立构建文件位于：

```text
$MOSIM_ROOT\src\control\codegen\px4ctrl\
```

其中 `README.md` 说明模型来源、C ABI、MWORKS GenerateModelCode 步骤、
Windows/WSL 差异和 SIL 复核；`CMakeLists.txt`、`test_px4ctrl_c.c` 与
`codegen_manifest.json` 用于独立重建和哈希核验。已有 Linux `.so` 只表明该
WSL Linux 环境曾完成构建，目标机器必须重新构建。

### 6.3 代码生成后的必要检查

1. 核对 MWORKS 生成模型类与导出目录；
2. 重新构建 C 静态库/共享库并运行最小 C 测试；
3. 执行 `hash_check.ps1` 或 `hash_check.sh`；
4. 需要整机数值一致性时，使用现有 CFunction 路径复核 50 s SIL；
5. 不将该 SIL 写为 Gazebo/PX4 运行时部署成功。

## 7. 结果解释

### 7.1 名义筛查

当前 G3 总账有 28/48 有效通过和 20/48 有效失败。20 条失败必须按
`terminal_position_error_exceeds_5m`、`simulation_timeout`、`simulate_failed`、
`check_model_failed` 四类查看。目录存在、Studio 可打开或 CheckModel 通过都不能
自动改变该状态。

### 7.2 七场景和灵敏度

七场景 14 条总记录中，Official PID 与 px4ctrl 的电机效率故障记录均为无效
负样本。灵敏度 24 条中 3 条物理门限失败和 4 条执行阻塞也不是“零结果”。
详细数值、表格和边界见：

```text
$MOSIM_ROOT\Docs\报告\仿真分析报告_正文骨架.md
$MOSIM_ROOT\Docs\Design\报告手册交付证据总账_P0_20260731.md
```

## 8. 常见问题

### 8.1 下拉框没有可选实例

先选择控制器家族，再选择该家族中的实例。若实例标记为待接入或路由表中
`available=false`，Studio 不会给出可打开 Runner；这属于路由状态，不应手工用
历史配置文件强行指向不存在入口。

### 8.2 “写入配置”或“打开仿真模型”不可用

检查当前任务、控制器 ID 和 FormalRunner 是否是权威 TOML 中允许的组合。对于
三机或单机自主避障等专用任务，控制器选择由专用任务路由限制；先切换到已登记的
任务/控制器组合，再写入配置。

### 8.3 结果查看器没有数据

先确认 MWORKS 中的人工仿真确实完成，并检查当前 Runner 的 Result.msr 与指标
路径。Studio 日志只记录配置/打开请求，不能替代结果文件。

### 8.4 如何获得完全可复现的交付

遵循 `$MOSIM_ROOT\RELEASE_CHECKLIST.md`：设置根变量，只加载正式包根，使用
当前 TOML 写配置、打开模型、CheckModel、人工仿真、读取结果，再构建并测试
px4ctrl C 交付物。已知失败、执行阻塞和运行时部署边界必须随交付一并保留。
