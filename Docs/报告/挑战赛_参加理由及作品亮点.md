## 一、参加挑战赛理由

本团队接受初赛未晋级下一阶段的结果，并按照大赛挑战赛通知要求，在初赛作品基础上继续整理和优化。申请参加挑战赛并非对初赛评审结果提出异议，而是希望在规定窗口内提交一个证据更完整、结构更清晰、复现路径更明确的作品版本，使评审能够直接看到项目已经完成的工程工作及其适用边界。

本作品面向 A8 四旋翼无人机位姿控制系统设计优化赛题，工作重点不是只完成某一个控制器的单次仿真，而是围绕云纵150参照机体，建立从多领域建模、控制器接入、场景配置、结果分析到代码生成的可追溯工程链。初赛版本已经形成了较大的模型和控制器工程规模，但不同层级的数量、不同类型的仿真证据以及 MWORKS 与运行时部署边界仍容易被混读。挑战赛版本将进一步统一报告、用户手册、源码、配置和结果的对应关系，降低评审阅读和复核成本。

参加挑战赛的主要原因有三点：

1. **补充完整的工程证据链。** 对模型来源、接口合同、FormalRunner 入口、场景 Profile、指标结果和代码生成产物进行一一回链，让每个结论都能落到项目包内的源码或结果文件。
2. **呈现可复现的国产工具链实践。** 作品以 MWORKS.Sysplorer/Sysblock/Syslab 为主线，展示从图形化控制器模型到 C99 生成、编译和 MWORKS CFunction SIL 复核的连续工程过程。
3. **以真实边界说明成果。** 对已经完成、正在复核和仍需独立运行时验证的内容分层说明，同时保留异常记录和负样本，不以单张截图或未经同条件验证的结果替代正式证据。

因此，本团队希望通过挑战赛提交优化后的作品和材料，请组委会依据更新后的工程包、报告和复现说明，对作品的完整性、可扩展性和工程实践价值进行再次评估。

## 二、作品概述

MoSim 是一个基于 MWORKS 构建的四旋翼位姿控制与智能仿真验证平台。项目以云纵150实物的结构、装配关系、旋翼位置和传感器安装关系为参考，建立可追溯的虚拟机体与参数 Profile；在统一的四旋翼动力学 Plant 上接入多类位置、姿态和力矩控制器，并通过 Adapter、Runner 和 Profile 约定不同控制器的输入输出边界。

平台覆盖名义轨迹、风扰、参数失配、电机效率故障和多机参考任务等配置入口，支持在 MWORKS 中进行模型检查、人工仿真和结果复核。对其中的 px4ctrl 工程复现路线，项目还完成了图形化模型到 C99、编译共享库、CFunction 接入和 50 s SIL 对比链路。MoSim Studio 则将配置编写、模型入口、代码生成入口和本地引导集成到一个面向操作者的界面中。

## 三、作品亮点

### 1. 以云纵150为参照的可追溯虚拟机体

项目不是采用抽象的理想四旋翼作为唯一对象，而是以云纵150实物的结构和装配关系为参照建立虚拟机体。机架尺寸、旋翼中心、机臂和传感器安装位姿按照实物测量与装配关系组织到参数 Profile 中，质量、惯量、推力/反扭矩系数和电机动态则按来源分层记录。

这种分层方式把“物理结构来源”和“工程种子参数”明确区分：当前模型可以用于控制器接口、闭环行为和场景注入的统一验证；后续如果获得动力台数据或飞行日志，也可以逐项替换参数而不破坏控制器和 Runner 接口。项目因此形成了从装配关系到 Modelica 参数的回溯路径，而不是把参数作为无法解释的常数散落在代码中。

### 2. 多控制器规模与统一接入合同

项目建立了 48 条控制器目录条目，形成 46 个 MWORKS Modelica 控制模块，并提供 44 条可由 Studio 手动打开的正式全机入口。这三个数字分别对应设计目录、源码模块和 FormalRunner 入口三个层级，不能理解为 48 条控制器全部通过性能测试；项目在报告中将设计存在、实现存在、可打开和性能证据分开登记。

不同控制器通过统一合同接入公共 Plant，主要输出边界包括：

- `ATTITUDE_THRUST`：姿态与总推力输出；
- `BODY_RATE_THRUST`：角速度与总推力输出；
- `WRENCH`：合力与合力矩输出；
- `ROTOR_COMMAND`：四路旋翼命令输出。

Adapter 负责控制器边界适配，Runner 负责整机实验入口，Profile 负责轨迹、采样、扰动和故障参数。这样的结构使控制器可以在保持被控对象、指标和结果读取方式一致的前提下替换，支持后续继续接入和比较不同控制算法。

### 3. Official PID 基线与 px4ctrl 图形化工程复现

项目首先复现了 Official PID 作为同条件比较基线，在此基础上开展其他控制器的统一接入和筛查。px4ctrl 的定位是本团队自研的 **MWORKS 图形化工程复现、统一接口、代码生成与 SIL 闭环实现**：其位置/速度外环参考 PX4 开源飞控思路，在 MWORKS 中以图形化方式建模，经 EquationBridge 接入姿态环、角速度环和控制分配，形成可审查的整机闭环。

这里的亮点在于工程复现和接口贯通，而不是把 px4ctrl 表述为另一个未经边界说明的新型控制律。项目同时保留了 Official PID 与 px4ctrl 的独立入口、模型结构和结果证据，便于评审比较连续控制边界、离散采样边界以及不同输出接口的实现差异。

### 4. 可组合的七类场景与故障注入接口

项目将任务轨迹和场景扰动拆开配置，形成可组合的实验 Profile。当前七类场景包括悬停、阶跃响应、Figure8、螺旋爬升、风扰、参数失配和电机效率故障；风扰、质量/惯量缩放和四路电机效率可以作为独立参数注入，不必为每一种组合重复设计控制器模型。

已冻结的两控制器七场景 A/B 证据集包含 Official PID 与 px4ctrl 各 7 条记录，共 14 条记录，其中 12 条为有效记录；两条 50% 转子1 Figure8 故障记录作为异常负样本保留，并在结果中单独说明。该处理方式强调可审计性：失败或异常结果不被删除，也不通过改变故障幅值、开始时刻或判定规则来重新标记为通过。

多机部分以**固定三角队形 Figure8 离线参考接入**为证据边界，展示多机模型和参考轨迹的组织能力。该证据不扩大解释为在线自主避障、分布式 MPC 或实时可重构编队。

### 5. 图形模型到 C99 与 SIL 的连续交付链

项目对 px4ctrl 建立了明确的代码生成链：

```text
MWORKS 图形 Sysblock
  -> GenerateModelCode 导出 C99
  -> CMake 编译静态库/共享库
  -> CFunction 包装与 FormalRunner 接入
  -> 相同初始条件、求解器和 50 s ClimbPath SIL 对比
```

在 MWORKS 全机 CFunction SIL 中，生成 C 与图形基线的差异记录为：位置 RMSE 差 `1.1481051588325626e-13 m`，姿态最大差 `3.2070318622956506e-12 rad`，旋翼指令最大差 `7.354117315117037e-11 rad/s`。这些数值说明当前生成代码在该 MWORKS SIL 条件下与图形模型保持数值一致。

该等价性证据的边界也被明确记录：它证明的是 MWORKS 图形模型到 CFunction 的 SIL 链路，不自动等同于生成 C 已完成 Gazebo/PX4 运行时部署。运行时部署需要按照独立的 ROS1/Gazebo/PX4 证据链复核。

### 6. 面向操作者的 MoSim Studio 工作区

MoSim Studio 基于 MWORKS.Syslab TyAppDesigner 构建，提供四个工作区：在线建模验证、实时联合仿真、代码生成和 MoSim 助手。APP 负责实验 Profile 编写、控制器和任务选择、能力状态提示以及 MWORKS 模型/结果/代码入口组织；模型检查、人工仿真、原生结果查看和代码导出仍由操作者在 MWORKS 原生界面中确认和触发。

这种设计把复杂工程入口集中到配置层，同时保留 MWORKS 原生工具作为最终操作界面。内置助手是本地上下文引导层，可以读取项目源码、配置和已有证据，帮助用户定位模型、任务和结果；它不直接 arm/takeoff、不发送飞行命令，也不把界面提示当作控制性能证据。

### 7. 证据、源码与复现路径分离管理

项目以 `Models/MoSimQuadrotorModel/package.mo` 作为正式 Modelica 包根，将源码、配置、结果、APP 和文档分别组织。结果目录中的运行配置、`Result.msr`、原始数据、指标和截图保持同一实验目录归属；代码生成目录另有 CMake、固定向量测试、manifest 和哈希检查脚本。

在交付材料中，项目将同时提供：

- 可加载的模型源码与统一接口实现；
- 可复用的场景和控制器配置文件；
- 已完成实验的结果与指标文件；
- C99 代码生成和构建说明；
- MWORKS/Syslab 前置条件、人工操作步骤和故障排查说明。

这样，评审可以分别检查“代码是否存在”“模型能否打开”“仿真是否有结果”和“结论是否有指标依据”，避免把截图、静态检查和运行性能混为一项结论。

## 四、挑战赛提交版本的重点优化

针对初赛版本的评审可读性和复现成本，挑战赛提交版本重点完成以下整理：

1. **统一正文口径。** 将控制器目录规模、Modelica 模块数、FormalRunner 入口数和有效实验记录数分层列出，删除容易引起误解的合并数字。
2. **加强公式到实现的回链。** 每个控制器单元同时给出设计说明、核心公式、Modelica 图形结构和源码入口；Official PID 与 px4ctrl 另行给出推导和工程边界。
3. **完善场景证据登记。** 统一记录任务轨迹、风扰、参数失配、电机故障、开始时刻、求解器、采样和结果路径，保留有效记录与负样本。
4. **收敛代码生成交付。** 提供生成类名、C 文件清单、SHA-256 manifest、跨平台构建命令、固定向量测试和 SIL 对比结果。
5. **降低使用门槛。** 同步完善用户手册、APP 入口说明和干净目录复现步骤，明确 MWORKS/Syslab、C 编译器和可选 Gazebo/ROS/PX4 环境的依赖关系。
6. **明确能力边界。** 对 MWORKS 形式化模型证据、CFunction SIL 证据、Gazebo/PX4 运行时证据和显示层截图分别标注，不使用展示层画面替代控制器指标。

## 五、结语

MoSim 的目标是把四旋翼控制算法从公式和单个模型，进一步组织成可配置、可比较、可复现的工程平台。项目已经完成云纵150参照机体建模、统一控制器接口、多场景配置、MWORKS 图形化验证、px4ctrl 代码生成与 SIL 复核以及 Studio 操作入口等多项工作。挑战赛版本将以更清晰的证据索引和更严格的边界说明呈现这些成果。

本团队希望获得参加挑战赛的机会，提交经过优化的作品、报告、用户手册和复现材料，请组委会基于完整工程包对作品的技术实现、工程规模、可扩展性和国产工具链实践价值进行再次评估。
